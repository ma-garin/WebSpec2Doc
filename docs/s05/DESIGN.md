## 業務フロー（実データで 1 本通す経路）

入口 /healing/runs/<run_id> → healing-run.js renderRun → healing-trace.js
→ GET /api/healing/runs/<run_id>/trace（web/routes/healing.py api_get_run_trace）
→ web/services/healing/trace.py build_trace(run_store.run_to_dict(run))
→ 出力: steps（6 工程）・defects（根拠/修正差分/再検証/判断）・gate（全体／今回の変更分）・audit（誰がいつ）
→ 保存: 既存の <out>/.healing/runs/<run_id>.json を読むだけ（新規保存なし）
→ エラー: 404「実行が見つかりません。一覧から開き直してください。」／500「処理に失敗しました」
  → 画面は「工程と証跡を読み込めませんでした: …　『再読み込み』を押してください。」

## 判定規則（AI が「修正済み」を宣言しない）

- 再検証: その周回の verify_after の失敗一覧にケースが無ければ「再検証で通過」、あれば「失敗のまま」、未実行は「未検証」、実行不可は「判定不能」。
- 差分の無い修正案で通過したものは「差分なしで通過（修正の根拠なし）」として今回の変更分に名指しする。
- 判断 3 値: 人の記録（approve/merge=採用、reject=不採用）だけ。記録が無ければ「要確認」。
- 判定帯: 全体＝最後の検証結果（合格／不合格／判定不能／未判定）。今回の変更分＝この実行の欠陥の再検証。失敗ケース・重大度高の未解消・未検証を名指し。

## 変える点
- 工程バー（検証→欠陥→修正案→再検証→PR→人の判断）を実行ツールバー直下に追加。
- 「欠陥ごとの証跡」: 左＝欠陥一覧（重大度・再検証・判断のチップ）、右＝根拠・修正差分・再検証・判断の 4 区画。
- 判断の記録（誰が・いつ・理由）を証跡の下に表示。
- サイドバーの件数バッジを削除（固定メニュー。共通契約 §2.1）。
- 768px 高で証跡領域が 0 に潰れていたため、実行ビューを縦スクロールにし最低 520px を確保。

- 上部バー・殻・共通 CSS/JS。
