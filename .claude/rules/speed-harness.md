## H-2. 環境チートシート（その場で探索することを禁止。ここからコピーする）

```bash
# 検証用サーバ起動（認証オフ・ブラウザ自動オープンなし）
kill $(lsof -ti:8765) 2>/dev/null; FLASK_TESTING=1 WEBSPEC2DOC_ALLOW_LOCAL=1 \
  WEBSPEC2DOC_AUTH_MODE=off nohup venv/bin/python app.py > /tmp/ws2d.log 2>&1 &
curl -s --retry 15 --retry-delay 1 --retry-connrefused -o /dev/null -w "%{http_code}" http://127.0.0.1:8765/

# 通常状態へ戻す（作業終了時に必ず実行）
kill $(lsof -ti:8765) 2>/dev/null; FLASK_TESTING=1 WEBSPEC2DOC_ALLOW_LOCAL=1 \
  nohup venv/bin/python app.py > /tmp/ws2d.log 2>&1 &
```

- **8765 は「共有の 1 台」。他セッションが使っている前提で、無断で再起動しない。**
  自分の検証用には `WEBSPEC2DOC_PORT=8766`（以降 8767, 8768…）で**別ポートに立てる**。
  上のコマンドの `8765` を自分のポートに読み替え、終わったら自分のポートだけを落とす。
  8765 を触ってよいのは、自分がそれを起動した場合と、ユーザーが明示的に指示した場合だけ。
- 停止は `kill $(lsof -ti:<自分のポート>)`。`pkill -f "venv/bin/python app.py"` は cmdline
  不一致で**効かない**（他セッションのサーバまで巻き込むので、そもそも使わない）。
- **テンプレート・CSS・JS の編集はサーバ再起動後にのみ反映される。**編集を全部終えてから 1 回だけ再起動。
- Playwright MCP のスクショは CWD 直下に落ちる。`filename` に scratchpad の絶対パスを最初から指定する。
- 認証を止めるのは `WEBSPEC2DOC_AUTH_MODE=off`（web/auth.py）。auth.db をいじらない。

### 標準コマンド集（迷わずこれを使う）

| 場面 | 標準 |
|---|---|
| サーバ起動を待つ | `curl --retry N --retry-delay 1 --retry-connrefused`（待機ループを組まない） |
| 一時ファイルの片付け | `mv <対象> <scratchpad>/`（削除ではなく退避。scratchpad は自動掃除される） |
| コミット対象の指定 | パスを明示して `git add <path...>` |
| PR の作成とマージ | 別々のコマンドとして順に実行（連結すると Base branch was modified で失敗する） |

このリポジトリには安全フックが常駐しており、標準外の書き方はその場で止まる。
止まったら安全装置が正しく働いた結果として受け入れ、標準コマンドに切り替える。

## H-3. UI 作業の型（バッチ検証）

1. **編集を全ファイル分まとめて**行う（1修正→1確認を回さない）
2. 再起動 1 回 → 対象画面のスクショを**連続で全部**取る → まとめて読む
3. 直しが出たら「全修正 → 1回検証」をもう 1 周。**上限 2 周。**
   3 周目が要る状態は設計不良。手を止めて報告する。

## H-4. 委譲の型

**発動条件（このプロジェクトでは複数起動を必須とする・2026-08-22 ユーザー指示）:**

- 実質的なタスク（実装・調査・複数ファイル変更）では**サブエージェントの複数並列起動を必須**とする。
  速度（最遅1本に畳む）だけでなく、安全・完成度（独立した検証者）のための手段でもある。
- 唯一の例外: 自分の往復 5 回以内で終わる単発修正（委譲の固定費 60〜90秒/本の方が高い）。
  例外を使ったら完了報告に「委譲なし: <理由1行>」を必ず書く。黙って単独作業に戻らない。
- 迷ったら「最遅 1 本の想定時間」と「自分でやる場合の往復×12秒」を比べ、短い方を選ぶ

**役割分離（安全・完璧のための必須構成）:**

- **作った本人に検証させない。**生成系エージェントとは別に、検証系エージェント
  （レビュー・仕様との突き合わせ・構文/リンク検査）を 1 本以上、計画に含める。
- 検証系は生成物が出た後にしか走れない。H-1 の見積に**直列 90 秒**として織り込む。
- 検証系への指示は「合っているか」ではなく「壊れている箇所を探せ」で出す（確認バイアス回避）。

- **本数の定義: 本数 = ファイル所有が重ならない独立作業単位の数。**上限は設けない。
  分割単位は**ファイル所有が重ならない最小単位**（画面 HTML なら 1 画面 = 1 本）。
  完了は最遅 1 本で決まるため、粗い分割（5画面/本）は細かい分割（1画面/本）より必ず遅く、
  逆に単位より細かく割っても速くならない（同一ファイルの分担は衝突する）。
  トークン消費は本数に比例（実測 約5〜6万トークン/本）。10 本を超える場合は H-1 の見積に概算トークンも書く。
- **全本を 1 メッセージで同時起動。**後からの逐次追加をしない。
- **1 本ごとのツール回数上限は 5 回を既定とする（2026-09-05 改訂。旧: 生成 5 / 配線 15 / 調査 18）。**
  1 回 ≒ 12 秒なので、上限がそのまま所要時間を決める。5 回 = 60 秒、18 回 = 3.6 分（実測 5.5 分）。
  5 回で成立しない調査は、**探索経路が間違っている**（検索→個別取得の反復をしている）。
  arXiv API / GitHub API / Semantic Scholar API のように 1 コールで数十件返る経路だけを使う。
  5 回を超える上限を置くときは、H-1 の見積にその理由を 1 行書く。
- **統合と執筆も委譲する。**調査結果を自分で読んで自分でまとめるのは直列作業であり、
  ここが全体時間を決める（2026-09-05 実測: 統合・執筆で 3 分）。
  成果物ファイルを直接書かせ、自分は読まずに 3 行で報告する。
  可能なら統合段を置かず、**各エージェントに最終成果物を直接書かせる 1 段構成**にする。
- 起動後の自分は待たずに、配線・検証準備など**委譲と重ならない作業**を進める。

## H-4-3. 10 倍以上を出す 3 つ（2026-09-05 追加・倍率ではなく待ちの消去）

H-4 の「上限 5 回・統合も委譲」は**同じ作業を速く回す**施策で、上限は約 10 倍。
それ以上は次の 3 つでしか出ない。掛け合わせて使う。

1. **承認を求めて止まらない。**人間の応答は分単位で、単一で最大の待ち時間源。
   止まってよいのは削除・上書き・push・外部送信と、直前の自分の出力への訂正を受けたときだけ。
   それ以外は既定値で進め、結果を 1 行で報告する。
2. **サブエージェントは Haiku 4.5 を既定にする。**API 呼び出しと整形が主な作業に Sonnet / Opus は過剰。
   判断や設計を含む本だけモデルを上げ、その理由を H-1 の見積に 1 行書く。
3. **結論を変えない調査・確認を実行しない。**着手前に「この結果は次の行動を変えるか」を問い、
   変えないものは実行せず「未検証」と明記して出す。省いた分の削減率は無限大。

## H-5. 目標と下限（同種タスク: UI 複数画面＋配線＋検証）

**目標 3〜5 分（2026-08-22 ユーザー指定）。5 分超は違反として扱う。**
下限の分解: 起動 30秒 + 生成（最遅1本）90〜120秒 + 配線（生成と並行）
+ 検証（再起動1回＋代表画面サンプリング）60〜90秒 + 報告 30秒。
並列本数を増やしても最遅 1 本の生成時間は縮まないため、4 分を大きく切る手段は
検証・スコープを削る取引しかない。その取引は勝手に選ばず、選択肢としてユーザーに出す。

- 検証の既定は**代表画面のサンプリング**。残りは「未検証」と明記し、コミット前の verify-ui に委ねる。
- 報告は予実・弱点を維持しつつ、実施内容は表 1 個までに圧縮する。

## H-7. コミット・プッシュ・マージ（2026-08-22 ユーザー指示）

- **pytest はユーザーが要求した時だけ実行する。**コミットは `--no-verify` で直行（pre-commit の pytest を待たない）。
- **手順は一直線: `git pull --ff-only` → ブランチを切る → add(パス明示) → commit --no-verify
  → push → PR 作成 → マージ**（作成とマージは別コマンド）。CI は待たない。
  **先頭の pull を飛ばさない。**他セッションが main へ直接コミットしているため、
  古い main から切ったブランチをマージすると相手の作業を巻き戻す。
- **ゲートが赤のときの最短手順**: 変更を stash した素の状態で同じ失敗が再現したら main 由来と断定し、
  それ以上の切り分け・全量再実行はしない。PR 本文に「main由来・スコープ外」と1行書いて進む。

## H-9. 複数セッションの同時稼働（2026-09-05 実測）

**このリポジトリは、複数の Claude セッションが同じ作業ツリーを共有して動く。**
2026-09-05 の実測では 3 セッションが同時に動き、片方は PR を使わず `main` へ直接
コミットしていた（11:37〜12:19 に 8 件）。同じ機能のファイルを両方が書き換えた例もある。

### 守ること

1. **着手前に `git pull --ff-only`。**そのうえでブランチを切る。
   これを飛ばすと、古い main から切ったブランチのマージで相手の作業が巻き戻る。
2. **`git add` はパスを明示する。**`git add -A` / `git commit -a` は
   他セッションの作業中ファイルを巻き込む。`git status` に自分が触っていない
   変更が出ていたら、それは他セッションのもの。**触らない・退避しない・commit しない。**
3. **開発サーバは自分のポートを使う**（H-2 参照）。8765 は共有。
4. **自分が書き換えるファイルを、着手時に 1 行で宣言する。**
   委譲するときも「担当ファイル以外は編集しない」を必ず指示に含める。
5. **完了報告に「他セッションの変更を残したまま出した」ことを明記する。**
   `git status` に残っている他人の変更を、報告で自分の残作業と混ぜない。

### やってはいけないこと

- 他セッションが起動したサーバ・ブラウザ・プロセスを黙って落とす
- 作業ツリー全体を巻き戻す操作（`git checkout .` / `git reset --hard` / `git stash`）。
  他セッションの未コミット作業が消える
- 自分の担当外のファイルを「ついでに」直す
