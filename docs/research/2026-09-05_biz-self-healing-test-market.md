## 「セルフヒーリング」の意味の分布

| 段階 | 意味 | 該当ツール |
|---|---|---|
| 1. ロケータ張替 | UI 変更で要素が見つからないとき、代替要素を推定してテストを通す。製品もテストの意図も変えない | MagicPod、Autify、mabl、Functionize、Virtuoso、Testim、Katalon、Healenium、BrowserStack Low-code、Momentic（意図ベース） |
| 2. テストコード修正 | テストの手順・期待値そのものを書き換えて保守する。人手またはサービスで担保 | testRigor（自然文でロケータ不要＝実質「修正不要」訴求）、QA Wolf（人＋AI の保守代行）、Rainforest QA（人手オプション） |
| 3. 製品コード修正 | 失敗原因が製品側にあると判定し、製品コードを直して PR を出す | **本調査の検索範囲では該当なし**（ツール名＋"self-healing"＋"pull request"／"fix the app" では見つからず） |

- 全ツールの前提は「**製品は正しく、テストが古い**」。失敗＝テスト保守の問題として扱う。
- 段階 3 に近いのは AI コーディングエージェント（Copilot coding agent、Devin、Claude Code 等）だが、これらは「テスト失敗→検証→修正 PR」のループを QA スイートとして製品化していない（本調査では未検索・一般知識）。

## 本件が入り込める隙間

**差別化になる（根拠付き）:**

1. **意味の空白**: 上表のとおり段階 3（製品コード修正→PR）を訴求するツールは 13 製品中 0。既存ツールが解く「テスト保守コスト」とは別の「欠陥修正リードタイム」を売れる。
2. **故障帰属の逆転**: 既存ツールは失敗をテスト側の問題として自動吸収するため、**本物のバグをロケータ張替で隠すリスク**を構造的に持つ。「テストは正しい・製品を直す」の立場は、その弱点の対偶にある。
3. **ローカル実行**: 主要商用ツールはクラウド必須（MagicPod のローカルは「端末」であり、作成・管理はクラウド）。ローカル PC 完結＋自社リポジトリへの PR は、クラウドに製品コードを出せない層（Enterprise 料金帯の理由でもある）に刺さる。

**差別化にならない・注意すべき点:**

- **買い手が変わる**: 段階 1〜2 の買い手は QA チーム（テストの維持が KPI）。段階 3 の買い手は開発チーム／EM（欠陥修正が KPI）。QA ツールの営業導線・比較表に載っても、財布が違う。
- **競合は QA ツールではなく AI コーディングエージェント**: 「失敗テスト→修正 PR」は Copilot coding agent 等でも人が指示すれば可能。差はループの自動化（検証→欠陥→並列修正→再検証→PR）と、仕様書・テスト生成との一体性。**この差の価値は本調査では未検証**（顧客インタビュー未実施）。
- **信頼の壁**: 製品コードの自動 PR は誤修正コストが高く、QA ツールの「ロケータ張替」より導入抵抗が大きい。人の承認を挟む現設計（PR で止める）は必須だが、それが「結局レビューする手間」と受け取られる可能性。

**判断（既定値）**: 「テストを直す」市場の後追いはしない。「欠陥→製品修正 PR」を主訴求とし、対象は**QA 組織を持たない 10〜50 人規模の開発チーム**（Rainforest QA・Momentic・QA Wolf と同じ買い手）。価格は MagicPod（¥4 万/月）ではなく QA Wolf 側（サービス単価）を参照して上に置く。**根拠は上表の分布のみで、顧客検証は未実施**。
