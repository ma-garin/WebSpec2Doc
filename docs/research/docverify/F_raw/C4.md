# C4 開発基盤上の AI 要件レビュー（調査日 2026-10-18）

## 結論（3 行）
- 開発基盤上の AI（Copilot4DevOps・Rovo・Kiro/Spec Kit・M365 Copilot・Notion AI）は「生成・変換・要約」が主で、V 字の対（要件⇔システムテスト）を突き合わせて欠陥を指摘する検査は確認できなかった（未確認を含む）。
- 汎用 LLM 単体は要件欠陥の検出が不十分（最良モデルでも専門家指摘の 47% 検出・誤検出 11%）で、LLM 補助が初心者の検出精度を下げた実験もある。「汎用 AI で代替」の脅威は限定的だが、未成熟ゆえに差別化は「根拠付き・再現可能・人が確定」で取る必要がある。
- 脅威は「基盤に既に入っている」配布力と、EARS 等の書式で欠陥を入口で減らす spec 駆動。日本語・QA 視点・指摘の根拠追跡で勝つ。

## 勝つための示唆
1. 対文書の突き合わせ（要件⇔基本設計⇔テスト観点）を中核にする。各基盤 AI は生成・要約・校閲止まりで、対検査は見つからなかった。根拠: 発見 1〜4。
2. 全指摘に原文の引用箇所と基準名（INCOSE・ISO/IEC/IEEE 29148 等）を付け、再現可能にして人が確定する構成にする。汎用 LLM は見逃し約半分・誤検出ありで、無監督は不可。根拠: 発見 6・8・9。
3. 見逃しが多い「必要性・正しさ」は AI 任せにせず、QA がチェックリストで確認する導線と網羅度（検査済み／未検査）の表示を持つ。根拠: 発見 6。
4. QA 初心者を誤誘導しない設計（AI の指摘を先に見せずに自力検査してから照合する等）を検討する。LLM 支援で検出精度が下がった実験がある。根拠: 発見 7（要検証、本ツールで A/B 評価）。
5. 基盤への取り込み（Confluence・Word・Azure DevOps からの取込と、指摘の Jira／ADO への返却）を用意し、配布力の差を埋める。EARS・Gherkin 等の書式変換を受け入れる。根拠: 発見 1〜3。

## 引用してはいけない数値
- G2 の 64 件・平均 4.9（Copilot4DevOps Plus、小標本・AI 要約・Plus 版で本体と別の可能性）。
- Copilot4DevOps の「誤り削減」「高速化」の主張（ベンダー主張、数値の根拠なし）。
- 47%／11%、20.2%、3.84/5 は要旨・スニペット由来で、本文の条件（要件セット規模・評価基準）を未確認。単独で優劣の根拠にしない。
- Mahbub・Fantechi の結果は旧モデル（GPT-3.5/4）で、現行モデルに当てはめない。
