# ドキュメント検証（System 01 docverify）商用化に向けた調査の統合（2026-10-15）

詳細: [A 競合](A_competitors.md) / [B 研究](B_research.md) / [C 規格・プロセス](C_standards.md)。
数値は各ファイルの「引用してはいけない数値」に従う。ここには数値を転記しない。

## 1. 競合が共通して持つもの（無いと商用で比較に乗らない）
- 要件文ごとの曖昧語・弱語の指摘と、該当箇所の提示
- スコアまたは優先度による品質の見える化（QuintSpect は 5 観点）
- カスタム観点・チェックリストのプリセット
- 複数文書間の矛盾検知、要件→設計→テストの追跡と完全率（QuintSpect）
- 採否は人が決める（AI は提案のみ）

## 2. 誰もやっていない空白（確認できた範囲。存在しないことの証明ではない）
1. 検出精度の公開（適合率・再現率・誤検知率）— 6 製品とも確認できず
2. 実画面・実挙動と仕様の突合 — 当製品は match で既に持つ
3. 網羅性（書かれていない要求）の扱い
4. 指摘ごとの根拠（原文引用・規則 ID）と再現可能な判定記録
5. 日本語仕様に特化した規格準拠の検査
6. 規格（IEEE 1028 / ISO/IEC 20246 / ISTQB）に沿ったレビュー工程・役割・メトリクスの管理

## 3. 研究から採る構成
- 検出は決定的なルール（辞書・パターン）で行い、LLM は説明と書き換え案の作成に使う二段構成
- EARS 型の書式パターンからのずれを指摘し、書き換えテンプレートを示す
- 同じ要求を複数回言い換えさせ、結果が揺れた箇所を曖昧さの合図として人に回す
- 矛盾・重複は「確認候補」として出し、確定扱いにしない。網羅性は常に「未検証」と表示する

## 4. 推奨ロードマップ（PR 単位）
| 順 | 内容 | 位置づけ |
|---|---|---|
| P1 | 指摘に ISO/IEC/IEEE 29148 の特性タグと規則 ID・原文引用を付与し、観点別スコアを出す。カスタム観点のプリセット | 追いつく＋空白 4・5 |
| P2 | LLM（OpenAI / Ollama）による説明・書き換え案。複数回の言い換えで揺れを検出し、未決定事項を質問票へ送る | 追いつく＋差別化 |
| P3 | 要求集合の検査：重複・矛盾の候補、要件→設計→テストの追跡と完全率 | 追いつく |
| P4 | レビュー工程の管理：種別・役割（作者≠議長）・入口/出口基準・Fagan / ISTQB の指標（検査速度・欠陥密度）・変更できない記録 | 空白 6 |
| P5 | 自社データセットで精度を測り、適合率・再現率を公開する | 空白 1 |
