# レンズ2: 段階承認の判断者

対象: `.playwright-mcp/05-stages.png`（STEP 1 テスト目的）、`.playwright-mcp/page-2026-07-26T03-45-11-702Z.yml`（当該画面のアクセシビリティツリー）、`templates/partials/view-auto-run.html`、`static/js/autorun-stages.js`、`static/js/autorun-review.js`。
注記: 指定された `.playwright-mcp/dom-stage1.json` は 0 バイトで内容が無かったため、同一画面のページスナップショット YAML を代替の可視要素ダンプとして使用した。

## 指摘一覧

### F2-1 [深刻度: 致命] 同じ画面に未確認件数が 2 つ（4 件 / 1 件）あり、承認条件がどちらか確定しない
- 場所: 画面上部の主導線バー「STEP 1 テスト目的 — 未確認 4 件」「未確認が 4 件あります」と、その直下の要確認パネル「要確認 0 / 1 件」「未確認が 1 件あります。すべて確認すると確定できます。」
- 事実: スナップショット上に `未確認 4 件`（f1e503）と `要確認 0 / 1 件`（f1e513）が同時に存在する。`autorun-stages.js:505` の pending は「段階の items のうち approved でない数」、`autorun-review.js:260` の note は review-queue の `review_pending` を数えており、母集団が別。要確認パネルは「実測・低リスクの 3 件は自動承認」と表示しているが、主導線バーの 4 件はその 3 件を未確認として数えている。
- 原則: 一貫性と標準（Consistency and standards）
- 影響: 「あと何件見れば承認してよいか」という承認判断の一次情報が矛盾する。ユーザーは 3 件を「自動承認済み」と読むか「未確認」と読むかを自分で決めるしかなく、承認の根拠が画面から得られない。

### F2-2 [深刻度: 致命] 「確定する」の実効範囲がラベルより広く、レビューキューに載る全段階を一括承認する
- 場所: 要確認パネル右下の「確定する」ボタン（f1e532）
- 事実: `autorun-review.js:312-351` の `signOff()` は、`state.entries` に含まれる全 `stage_id` を重複排除して列挙し、それぞれに `/api/autorun/stages/approve` を順次 POST する。画面上のラベルは「確定する」、直前の説明文は「未確認が 1 件あります。すべて確認すると確定できます。」のみで、承認対象が現在の STEP 1 に限られるのか複数段階に及ぶのかはどこにも書かれていない。
- 原則: ユーザーの制御と自由（User control and freedom）
- 影響: 表示中の 1 件をチェックしただけで、画面に出ていない段階まで承認済みになりうる。承認は品質責任の所在を移す操作であり、範囲が不明なまま押させるのは判断の前提が欠落している。取り消し導線も同パネルには無い。

### F2-3 [深刻度: 高] 主導線の「承認して次へ」が押せる状態のまま、直下の「確定する」は無効。押すべきボタンが一意に定まらない
- 場所: 主導線バー「承認して次へ」（f1e506、スクリーンショット上は活性の青ボタン）と要確認パネル「確定する」（f1e532、`[disabled]`）
- 事実: 同一スナップショットで、`承認して次へ` に disabled 属性は無く、`確定する` にのみ `[disabled]` が付く。`autorun-stages.js:506` では blocked 判定に `stage.can_approve` を使い、`autorun-review.js:266` では `counts.review_pending` を使っており、活性条件が別系統。両ボタンとも最終的に同じ `/api/autorun/stages/approve` を呼ぶ。
- 原則: エラーの予防（Error prevention）
- 影響: 「未確認が 4 件あります」という警告と、押せる承認ボタンが同時に提示される。未確認のまま先へ進む操作が最短経路になっており、確認を促す設計が実質的に無効化されている。

### F2-4 [深刻度: 高] 自動承認された 3 件が既定で畳まれ、中身を見ないまま承認が成立する
- 場所: 「▸ 自動承認された 3 件（実測・低リスク）」の折りたたみ（f1e529）
- 事実: `autorun-review.js:377-381` の `load()` は、画面表示前に `/api/autorun/review-queue/auto-approve` を自動 POST する。`state.showAuto` の初期値は false（同 :9）で、既定では 3 件のタイトルすら表示されない。展開しても表示されるのはタイトル・確信度バッジ・段階名だけで、`detail` と `reason` は自動承認分には描画されない（同 :192-204）。
- 原則: システム状態の視認性（Visibility of system status）
- 影響: 確定版に含まれる項目の 4 分の 3 が、ユーザーが一度も読まないまま承認済みになる。「実測・低リスク」という分類の妥当性を検証する材料が画面上に無く、承認の署名が形骸化する。

### F2-5 [深刻度: 高] STEP カード 4 件のうち出所バッジが付くのは 1 件のみで、残り 3 件が実測由来か AI 生成かを区別できない
- 場所: STEP 1 の 4 カード「欠陥の摘出」「カバレッジの確保」「リスクの低減」「基準の確立」（f1e541/f1e548/f1e555/f1e562）
- 事実: バッジ `前提` が付くのは「基準の確立」のみ（f1e565）。`autorun-stages.js:163-178` はバッジを `item.assumed` / `source === 'user'` / `source === 'llm'` / `approved` の場合にのみ付与するため、それ以外の生成物は無印になる。無印 3 件の本文には「実測した 6 画面・12 入力項目」「画面 6 / 遷移 19」などの数値があるが、その数値がどの観測に基づくかを示すリンクやアンカーは無い（成果物 iframe f1e574 は別セクションで、項目とは紐付いていない）。
- 原則: 認識であって記憶ではない（Recognition rather than recall）
- 影響: 「AI が作った下書きのうち、根拠が弱い項目だけを確認します」という前提の分類が、画面上では検証できない。ユーザーは無印＝実測と信じるしかなく、AI の推測を実測として承認するリスクを負う。

### F2-6 [深刻度: 中] 「基準の確立」が 2 箇所に重複掲載され、それぞれ操作セットが異なる
- 場所: 要確認パネル内の行（f1e517、チェックボックス＋「アシスタントに相談」）と、STEP 1 カード（f1e562、「修正」＋「アシスタントに相談」）
- 事実: 同一タイトル・同一本文「前回スナップショットが無いため、今回は比較の基準を作る回とする。現新比較は次回以降に成立する。」が同一画面に 2 回描画される（f1e524 と f1e566）。要確認パネル側には「修正」が無く、STEP カード側には承認チェックボックスが無い（`autorun-stages.js:189` の per-item 承認ボタンは `requires_item_approval` が真の場合のみ）。
- 原則: 一貫性と標準（Consistency and standards）
- 影響: 同じ項目の 2 表現が別物に見え、「上でチェックすれば下も承認されたのか」が分からない。修正したい場合は下、承認したい場合は上、と操作場所を使い分ける必要があるが、その関係は画面上で説明されていない。

### F2-7 [深刻度: 中] 承認しなかった場合に何が起きるかが示されず、却下・保留の操作も存在しない
- 場所: 画面全体（要確認パネルおよび STEP カードのアクション群）
- 事実: 承認系の操作は「チェック（＝承認）」「確定する」「承認して次へ」「修正」「アシスタントに相談」のみ。`autorun-stages.js` 全体を検索しても却下・保留に相当するハンドラは無く、`skipStage`（:595）を呼ぶ「スキップ（2回目以降）」ボタンは `stage.skippable_on_rerun && state.pipeline.is_rerun` の条件付きで、本スナップショットでは描画されていない。承認済み時にのみ「この段階は承認済みです。修正すると再承認が必要です。」（:455）が出るが、これは承認後の事後説明。
- 原則: ヘルプとドキュメント（Help and documentation）
- 影響: 「この項目は納得できない」と判断したときの出口が「修正して自分で書き換える」しかない。承認を保留したまま次段階の材料を見に行く、という現実の判断プロセスに対応する操作が無く、結果として承認が既定動作になる。

### F2-8 [深刻度: 低] 確定後の記録先が本文で言及されるだけで、参照導線が無い
- 場所: 確定後に表示される `arv-confirmed` テキスト
- 事実: `autorun-review.js:353-362` は「確定しました。確認 N 件 / 自動承認 M 件。記録はアクティビティログに残ります。」という文字列のみを追加する。リンク・ボタンは生成されず、スクリーンショット内のサイドナビにも「アクティビティログ」項目は無い（ホーム／新規解析／テストケース／品質観点／観点管理／ユーザーガイド／参考／設定）。
- 原則: システム状態の視認性（Visibility of system status）
- 影響: 誰が何をいつ承認したかを後から確認する手段が画面から辿れず、承認の説明責任を果たせない。承認をためらう要因になる。

## 見落としの自己申告

- `.playwright-mcp/dom-stage1.json` が 0 バイトだったため、指定された DOM ダンプそのものは確認できていない。代替として同一画面のページスナップショット YAML を用いたが、属性（disabled 以外）や ARIA 詳細は網羅していない。
- ブラウザ操作が禁止のため、チェックボックス操作後に主導線バーの「未確認 4 件」が実際にどう変化するか、`確定する` が活性化する条件、`承認して次へ` を先に押した場合の挙動はいずれも未検証（コード上の推論のみ）。
- STEP 2〜8 の承認画面は素材が無く未確認。STEP 1 固有の問題か、全段階に共通かは判別できていない。
- サーバ側（`/api/autorun/review-queue`、`/api/autorun/stages/approve`）が返す `needs_review` / `confidence` / `risk` の判定ロジックは未確認。自動承認の分類が妥当かどうかは評価していない。
- 画面下部の操作バー（← 前へ / 作り直す / 抜けをLLMに聞く）はスクリーンショットの表示域外にあり、実際にどの位置に見えるかは未確認。
- LLM 未接続時など、`reason` や `confidence` が欠落した場合の表示は未確認。
