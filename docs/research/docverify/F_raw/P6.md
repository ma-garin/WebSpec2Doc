# P6 ソフトウェアインスペクションの有効性研究と、LLM 文書レビュー・人と AI の協働

調査状況: ツール 9 回使用。arXiv API は 3 回成功、Semantic Scholar と arXiv の後続 4 クエリは HTTP 429 で失敗。古典研究（Fagan・IEEE 1028・PBR・速度と検出率）は今回一次確認できていない。

## 結論（3 行）
1. 要件インスペクションに LLM 支援を付けた人間は、欠陥（requirements smell）の検出精度が下がった（n=34、2026 年の統制実験）。「AI を足せば見落としが減る」は実証されていない。
2. コードレビューでは、LLM は人の指摘の約 10% しか拾わず、独自の指摘の約 40% が有意義だった（240 PR）。LLM は人の代替でなく、人と別の欠陥を拾う補完として働く。
3. 古典のインスペクション知見（読み方技法・速度と検出率）は今回未確認。本ツールの設計根拠には、一次資料での追加確認が要る。

### 1. Human-AI Collaboration in Requirements Engineering: Evidence of the Negative Effect of LLMs on Requirements Inspection
- 著者: Broccia, Frattini, Arora, ter Beek, Fantechi, Vogelsang, Ferrari
- 年・ID: 2026 / arXiv 2608.21298
- 手法: 統制クロスオーバー実験、n=34。仕様書の smell を LLM 支援あり／なしで特定・分類。ベイズ回帰で分析

### 2. Studying Quality Improvements Recommended via Manual and Automated Code Review

### 3. The Impact of LLMs on Code Review Process
- 著者: Collante, Abedu, Khatoonabadi, Abdellatif, Alor, Shihab

## 勝つための示唆
1. **AI の指摘を人の判断の前に出さない設計を選べるようにする。** 根拠: 発見 1（LLM 支援で smell 検出精度が低下、n=34）。人が独立に読んだ後で AI の指摘を重ねる順序を既定にし、効果は自社データで測る。
2. **AI は人と別の欠陥を拾う補完として位置づけ、指摘の精度を絞る。** 根拠: 発見 2（人の指摘の約 10% しか拾わず、独自指摘の約 40% が有意義）、発見 7（候補列挙後の絞り込みで 7.2 から 3.1 に減少）。指摘数を増やさず、採用された割合を指標にする。
3. **速さを訴求しない。品質を示す。** 根拠: 発見 3・4（速度は上がるが品質向上は示されない）。「検出できた欠陥数」「人が採用した割合」を可視化する。
4. **新人 QA の学習を損なわない設計にする。** 根拠: 発見 1（初めから LLM 支援だと学習が小さい）。AI 支援を後出しにする「学習モード」を持つ。
5. （未確認の前提）読み方技法（観点別・チェックリスト）を機能にする案は、一次資料の確認後に採否を決める。
