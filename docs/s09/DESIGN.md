## 業務フロー
- 入口: /impact?sys=<id>&cr=<code>（tab 省略＝判断）
- API: GET /api/impact/v2/systems/<sid>/crs/<code>/decision（web/routes/impact_api_cr.py get_decision）
- service: web/services/impact/decision.py build → impacts.list・links/items 照合
- 出力: source（起票元）／impacts（risk_score 付き・リスク順）／retest（再実行・新規）／missing_links／verdict（overall・change）
- 保存: 読み取りのみ（impact.db）。判断の変更は既存の影響タブ（POST /impacts/<id>/resolve）
- エラー: 404「変更要求が見つかりません。一覧から選び直してください。」／403 既存文言

## 並び順（件数順にしない）
リスク点 = 到達可能性（段数 0→3・1→2・2 以上→1）× 変更の強さ（影響度。上書きがあれば上書き値）× 未検証（つながるテストが無ければ 2）。
「対応不要」にした影響は 0 点で末尾。理由文を行ごとに出す。

## 判定帯（共通語彙）
- 全体: 要件が無い→判定不能／設計・テストのつながりが無い要件あり→不合格（名指し）／他→合格
- 今回の変更分: 未分析→未判定／候補 0 件→判定不能／対応要で未検証 or 欠落要件に触れる→不合格（名指し）／要確認残→未判定（名指し）／他→合格

## S06 からの受領
links_sys09.submit_changes が題名「System06 要件変更 <iid>」で起票する。decision.source が接頭辞で判別し、一覧・ヘッダー・判断画面に「ドキュメント検証から受領」と検査 ID を出す。

## CR 重複起票（analyze 失敗後の再実行）の確認結果
- 結果: **409 で防いでいない**。同じ iid・同じ差分で submit_changes を 2 回実行すると CR-002・CR-003 が両方 draft で作られた（2026-10-24 実測、impact.db）。
- 原因: submit_changes（S06 所有）が毎回 crs.create を呼び、crs.create に重複判定が無い。analyze 失敗時も CR は残る。
- 対応: S06 所有のため本作業では変えない。docs/change-requests/S09-1.md で要求。
