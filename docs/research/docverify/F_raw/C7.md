# C7 要件・仕様書からのテスト設計 AI 生成ツールと V 字の左右連結

## 結論（3 行）
- 主要ツールは「要件/チケット → テストケース草案 → 人が承認」まで。要件の欠陥を先に指摘して修正まで追う設計は Katalon（Requirement Analyzer）と Jama 程度で、日本語の仕様書・設計書に対する欠陥指摘 → テスト条件の連結は未確認（空白地帯の可能性）。
- 入力は Jira/ADO チケットが中心。長文の要件定義書・基本設計書そのもの（章構造・版・図表）を扱う製品は Autify Genesis（仕様書アップロード）とバルテス TestScape が目立つが、欠陥指摘との連結は公開情報で未確認。
- 学術側も「曖昧さ処理・トレーサビリティ・幻覚抑制を同時に満たす手法は無い」と報告。ここに商用で勝つ余地がある。

## 勝つための示唆
1. 欠陥指摘の ID をテスト条件の根拠に引き継ぐ（指摘 → 確認質問 → 解消 → テスト条件）。既存は「分析してから生成」の直列で、指摘とケースの双方向リンクの記載は確認できない（根拠: 1, 3, 8）。
2. 曖昧・矛盾・テスト不能と判定した要件は、確定前に「暫定テスト条件」と「確認待ち」の印を付けて出す。Katalon は信頼度で自律実行を止めるだけで、人への差し戻しは質問止まり（根拠: 1, 11）。
3. 要件定義書・基本設計書の本文（章・版・図表・日本語）を直接の入力とし、チケット前提にしない。Katalon はリンク先を辿れず、Jira/ADO 中心（根拠: 1, 3, 5, 6）。
4. 根拠の可視化と網羅表を標準にする: 生成した観点ごとに原文の該当箇所、要件 × テストの対応表、未カバー要件を出す（根拠: 6, 3, 10）。
5. 幻覚抑制と精度の自己計測を示す: 原文に無い条件を混ぜない検査、日本語コーパスでの欠陥検出の再現率/適合率を公開（根拠: 10, 11。英語・単一データでの数値しか無い）。

## 引用してはいけない数値
- Autify「作業時間 55% 削減」: 社内実証のベンダー主張、元データ未確認。
- Jama「草案は約 80% 完成」: ベンダー想定値、検索要約経由で原文未確認。
- 学術サーベイの「21 件」: 本文で 26 件とも書かれ不整合。UMTG 95%、LLM4Fin 98.18% は個別論文の値で孫引き。
- Poulsen の精度 0.75 / 誤検出 62: 英語・NASA 要件 492 件のみでの値。日本語の仕様書へ一般化しない。
- 各社のテスト作成時間短縮率の類（第三者ブログ記載）は一次データ無しで引用しない。
