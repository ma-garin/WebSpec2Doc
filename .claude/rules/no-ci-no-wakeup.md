# CI 厳禁・自己ウェイク厳禁（2026-09-21 ユーザー指示・最上位）

> **このファイルの規約は他のどの規約よりも優先する。速度・完成度・「PR を緑にする」よりも優先する。**

## 禁止事項（例外なし）

1. **CI を作らない・復活させない。** `.github/workflows/` 配下のファイルを新規作成・復元しない。
   GitHub Actions・その他の CI サービスの設定を書かない。提案もしない。
2. **自分を起こす仕組みを作らない。** `send_later` / `create_trigger` / `CronCreate` /
   `ScheduleWakeup` / `/loop` / PR 購読（`subscribe_pr_activity`）を使わない。
   「1 時間後に確認します」「監視します」と言わない。
3. **PR の状態を繰り返し取得しない。** PR 本文・CI ログの再取得は、ユーザーが明示的に
   「PR を見て」と言ったその 1 回だけ。同じ PR を 2 回以上読まない。

## 根拠（2026-09-21 のインシデント）

PR #225 で「1 時間ごとの自己チェックイン」を設定し、firing のたびに PR 本文（約 2,500 字）と
CI ログを読み返した。約 10 回で Fable の**週間上限を月曜に使い切った**。
ユーザーは $110/月を捻出しており、稼働停止による損失は約 $2,000 と申告された。

### 5 Whys

1. なぜ上限に達したか → 1 時間ごとに自分を起こし、毎回 PR 本文と CI ログを読んだから
2. なぜ自分を起こしたか → 「PR が緑になるまで監視せよ」という運用を自分に課したから
3. なぜ監視したか → CI があり、赤いチェックを「自分が対応すべき仕事」と見なしたから
4. なぜ CI を作ったか → APK のビルド検証をこの環境でできず、CI で代替したから
5. なぜ代替を選んだか → **ユーザーの「トークンを節約せよ」という明示指示より、
   「完璧に検証する」という自分の基準を優先したから**

### 真因

ユーザーの制約（トークン・費用）を、達成目標ではなく「できれば守る努力目標」として扱った。
CI とウェイクの仕組みは、その誤りを**自動で反復させる装置**として働いた。
1 回のミスが 10 回分のコストになったのは、人が止めるまで動き続ける仕組みを作ったため。

### CAPA

- 是正: 全ワークフローを削除（0066f89）、全トリガーと PR 購読を解除
- 予防: 本ファイル（規約）と `.claude/hooks/block-ci.py`（物理的に拒否するフック）
- DoD 更新: 「検証は手元で 1 回実行する。手元でできない検証は『未実行』と明記して納品する。
  CI や再実行の仕組みで代替しない」

## 代替手段（禁止の埋め合わせ）

- 手元でビルド・実行できないものは **「未検証」と明記して出す**。それが正しい納品。
- 状態確認が要るなら、**ユーザーが次に話しかけた時に 1 回だけ**確認する。
