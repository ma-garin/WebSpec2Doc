# テスト活動支援（System 02）機能スコープ

作成日: 2026-08-22 / 状態: ドラフト（UI 枠は別途作成中のため、本メモは中身＝機能スコープのみを対象とします）

## 1. このシステムが解く問題

ドキュメント作成システム（System 01）が生成した仕様・観点・テスト条件は、そこから先の「テスト活動」に接続していません。テスト計画を立て、方針を決め、設計し、自動化コードに落とし、実行し、落ちた原因を分類し、コードを直すところまでが人手で分断されています。

本システムは、その分断を埋めることを目的にします。具体的には次の 3 点です。

- **入力を仕様書だけに限定しない。** GitHub のリポジトリ・PR・Issue、実際のソースコード、社内の開発標準（規約文書）も入力に取り、テスト設計の根拠にします。
- **工程をまたいだトレーサビリティを保つ。** 要求 → 観点 → テスト条件 → テストケース → 実行結果 → 不具合 → 修正コミット、を 1 本の鎖にします。
- **AI の出力を人がレビューできる形で止める。** AutoRun の段階承認と同じく、工程の切れ目で人が確認・修正できる状態を作ります。

なお「テスト設計をドキュメントから自動生成する」という機能単体では、後述のとおり既に商用製品が存在します。本システムの差別化は**コード・GitHub・開発標準との接続**と**不具合分析からコード修正までの後工程**に置きます。

## 3. 本システムのスコープ — テスト活動 8 工程

工程名は ISTQB のテストプロセス（計画・モニタリング/コントロール・分析・設計・実装・実行・完了）と、依頼された 8 工程を対応付けています。

| 工程 | この工程でシステムがやること | 入力 | 出力 | 外部連携 |
|---|---|---|---|---|
| 計画 | テスト対象範囲・テストレベル・リソース・スケジュールの草案を作る。変更差分（前回リリースとの diff）からテスト範囲を絞り込む | 仕様書、リリース範囲、GitHub のコミット/PR 差分、過去の実行実績 | テスト計画（範囲・レベル・優先度・終了基準） | GitHub（差分・マイルストーン）、開発標準（テストレベルの定義） |
| 分析 | フィーチャーを識別し、テスト条件を抽出する。品質特性ごとに漏れを点検する | 仕様書、画面定義、API 定義、開発標準 | フィーチャー一覧、テスト条件一覧、リスク評価 | ドキュメント、開発標準、コード（実装済み機能の突合） |
| 方針 | テスト条件ごとに、どのテストレベル・どの技法・自動化するか手動かを決める | テスト条件、リスク評価、既存の自動テスト資産 | テスト方針表（レベル×技法×自動化可否）、対象外の明示 | コード（既存テストの有無）、開発標準（自動化ポリシー） |
| 設計 | 観点図とテスト技法（同値分割・境界値・デシジョンテーブル・状態遷移・組合せ）を適用し、テストケースを生成する | テスト条件、観点カタログ、方針表 | テストケース（前提・手順・期待結果・観点ID・要求ID） | ドキュメント、開発標準（記述フォーマット） |
| 実装 | テストケースを実行可能な形（Playwright スクリプト、API テスト、テストデータ）に落とす | テストケース、画面の DOM 構造、API スキーマ | 自動化スクリプト、テストデータ、手動テスト手順書 | コード（セレクタ・ルーティング）、GitHub（ブランチへの PR 作成） |
| 実行 | 自動テストを実行し、証跡（スクリーンショット・ログ・HAR）を残す。手動分は結果を記録する | 自動化スクリプト、実行環境 | 実行結果、証跡、カバレッジ、消化状況 | GitHub（CI の実行結果取り込み） |
| 不具合分析 | 失敗を「製品欠陥 / テスト欠陥 / 環境起因 / フレーク」に分類し、ODC 属性を付ける。同一原因をクラスタリングする | 実行結果、証跡、コード、変更履歴 | 不具合レポート（分類・被疑箇所・再現手順）、傾向分析 | GitHub（Issue 起票、blame による変更者・変更時期の特定）、コード |
| コード修正 | 被疑箇所に対する修正案を提示する。修正後に該当テストのみ再実行して確認する | 不具合レポート、コード、開発標準 | 修正パッチ案、再実行結果、回帰対象の提示 | GitHub（ブランチ・PR）、コード、開発標準（コーディング規約への適合） |

**スコープ外（明示）**: 本番環境への修正の自動適用、テスト環境そのものの構築・運用、性能負荷試験の実施基盤。これらは扱いません。

## 4. 外部連携の設計

### 4.1 ドキュメント（ドキュメント作成システムの成果物）

- **何を読み取るか**: System 01 が生成した画面仕様・API 仕様・観点・テスト条件、およびユーザーがアップロードした要件定義書・設計書。
- **何に使うか**: 分析工程のフィーチャー識別とテスト条件抽出の一次入力。設計工程での期待結果の根拠。要求 ID とテストケースの紐付け。
- **必要な権限・秘密情報**: 同一テナント内のデータ参照権限のみ。テナント境界を越えた参照は禁止します。外部から取得した文書は信頼できない入力として扱い、既存の無害化経路を通します。

### 4.2 GitHub（リポジトリ・PR・Issue）

- **何を読み取るか**: コミット差分、PR の変更ファイルと説明、Issue の本文とラベル、CI の実行結果、`git blame`、ブランチ構成。
- **何に使うか**: 計画工程での影響範囲特定（差分ベースのテスト絞り込み）、実装工程でのテストコード PR 作成、不具合分析工程での Issue 起票と変更者特定、コード修正工程でのパッチ提出。
- **必要な権限・秘密情報**: GitHub App もしくは PAT。読み取りは `contents:read` / `pull_requests:read` / `issues:read`、書き込みを行う場合のみ `pull_requests:write` / `issues:write`。**トークンはテナント単位で暗号化保管し、平文でログ・生成物に出さないこと**を必須条件にします。既定は読み取りのみ、書き込みは明示的な有効化を要します。

### 4.3 ソースコード（静的解析）

- **何を読み取るか**: ルーティング定義、関数・クラスのシグネチャ、分岐条件、既存テストの有無とカバレッジ、UI テンプレート内のセレクタ（`id` / `data-*`）。
- **何に使うか**: 方針工程で「仕様にあるが実装がない／実装にあるが仕様にない」を検出。実装工程で安定したセレクタを選ぶ。不具合分析工程で被疑箇所を絞る。
- **必要な権限・秘密情報**: リポジトリの読み取り権限。**解析はローカルまたは自社管理環境で完結させ、コード全文を外部 LLM へ送らない**方針を既定とします（送る場合は対象ファイルを限定し、テナント設定で明示同意を取る）。

### 4.4 開発標準（規約文書）

- **何を読み取るか**: コーディング規約、命名規約、テストレベルの定義、テストケース記述フォーマット、レビュー基準、リリース判定基準。
- **何に使うか**: 設計工程での出力フォーマット統一、方針工程でのテストレベル判定、コード修正工程での修正案の規約適合チェック、完了判定の終了基準。
- **必要な権限・秘密情報**: テナント配下にアップロードされた文書の参照権限のみ。社外秘の可能性が高いため、既定で外部送信の対象外とし、要約や抜粋の生成もテナント内に閉じます。

## 6. 作る順序（推奨）

| 段階 | 範囲 | この段階で動くようになること |
|---|---|---|
| **P0** | 分析・設計・実行の 3 工程を、既存の観点管理・テスト設計・AutoRun 実行基盤の上に「テスト活動」として束ねる。GitHub は読み取りのみ（差分取得） | 仕様書と GitHub の差分を入れると、観点図・テスト条件・テストケースが出て、Playwright で実行され証跡が残る |
| **P1** | 計画・方針・不具合分析を追加。ODC 分類と Issue 起票、差分ベースのテスト絞り込み、静的解析による仕様と実装の突合 | 変更範囲からテスト計画が立ち、失敗が製品欠陥／テスト欠陥／環境／フレークに分類され、GitHub に Issue が立つ |
| **P2** | 実装（テストコードの PR 提出）とコード修正の支援。開発標準への適合チェックを設計・修正の両方に効かせる | テストコードと修正パッチが PR として出て、規約適合と該当テストの再実行結果が PR に添付される |

P0 を先に置く理由は、既存資産の流用率が最も高く、実データを 1 周させて設計の誤りを早く検出できるためです。GitHub の書き込み権限を要する P2 を最後に置き、権限リスクを後ろ倒しにしています。

## 7. 参照した外部基準

網羅性を自分の記憶だけで判断しないため、以下の体系に照らして節を点検しました。

| 体系 | 効かせた節 | 用途 |
|---|---|---|
| ISTQB テストプロセス（計画・モニタリング/コントロール・分析・設計・実装・実行・完了） | 3 | 8 工程が標準プロセスを覆っているかの照合。**「モニタリング/コントロール」と「完了」に相当する工程が 8 工程に無い**ことを、この照合で検出しました（第 8 節に記載） |
| ISO/IEC/IEEE 29119（テストドキュメント: テスト計画、テスト設計仕様、テストケース仕様、テスト手順仕様） | 3, 4.1 | 各工程の「出力」が標準的な文書種別に対応しているかの照合 |
| ODC（Orthogonal Defect Classification） | 3（不具合分析）, 5 | 不具合の分類軸を自作せず既存体系に寄せるため。`failure_classifier.py` の拡張方針 |
| ISO/IEC 25010（システム及びソフトウェア品質モデル） | 3（分析）, 5 | 品質特性ごとの観点漏れ点検。既存の `nonfunctional_judge.py` が対応 |
| ISTQB テスト技法（同値分割・境界値・デシジョンテーブル・状態遷移・組合せ） | 3（設計） | 設計工程で適用する技法の列挙を記憶ベースにしないため |

**注記**: 上記はいずれも体系名レベルの照合です。各規格の条項番号・最新版の改訂内容は本メモ作成時に一次文書で確認していないため、**条項単位の準拠を主張するものではありません。**

## 8. 未確認・要判断

**未確認（一次確認できなかった事項）**

- TESTRA の「工数約60%削減」の測定条件・母数・対象工程の内訳。ベンダー表明のみで、原データは公開を確認できませんでした。**本システムの目標値としてこの数字を流用しないこと。**
- TESTRA の GitHub / CI / 課題管理との連携有無。公式サイト・プレスリリースには記載を確認できませんでした（「連携しない」と確認したわけではありません）。
- TESTRA の対応入力ファイル形式、価格、テナント分離やデータの学習利用ポリシー。いずれも公表を確認できませんでした。
- TESTRA の「テスト観点データベース」の規模・粒度。非公開のため、当リポジトリの観点カタログとの比較はできていません。
- Qase の 2026 年前半のアップデート内容は第三者記事が出典で、ベンダー一次文書での確認は未実施です。
- 「不具合分析からコード修正まで環にする製品が存在しない」は、今回の検索範囲（TESTRA・Qase・MagicPod と関連記事）で確認できなかったという意味であり、市場全体に無いことの証明ではありません。

**要判断（ユーザーに確認したい事項）**

1. 8 工程に「モニタリング／コントロール」と「完了（終了基準の判定・振り返り）」を工程として足すか、既存 8 工程の中に畳み込むか。ISTQB との照合で欠けが出ています。
2. ソースコードを外部 LLM へ送ることを許容するか。既定は「送らない」で設計していますが、精度とのトレードオフになります。
3. GitHub への書き込み（Issue 起票・PR 作成）を P1 で解禁するか、P2 まで読み取り専用で通すか。
4. 対象とする GitHub のホスティング形態。github.com のみか、GitHub Enterprise Server も対象か。
5. 「開発標準」の入力形式。文書アップロードのみで足りるか、既存の社内 Wiki 等からの取り込みが要るか。
6. System 01（ドキュメント作成）とのデータ受け渡し方式。同一 DB を直接参照するか、エクスポート／インポートで疎結合にするか。
