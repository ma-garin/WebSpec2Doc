## 2. 各論

### 2.1 AI事業者ガイドライン（経産省・総務省）
- 主張: 第1.0版 2024/4/19、第1.1版 2025/3/28 公表。開発者・提供者・利用者の3主体ごとに「共通の指針」を示す。7原則（人間中心・安全性・公平性・プライバシー・セキュリティ・透明性・アカウンタビリティ）、リスクベース。法的拘束力なし。出典: https://www.soumu.go.jp/main_content/001002576.pdf （2025、検索結果は表紙・目次のみ）、https://tenbin.ai/media/ai_insights/ai-business-guideline-1-1-practical-points （二次）
- 主張（二次1件のみ）: 第1.2版が 2026/3/31 公表で現行最新。要確認。
- 未確認: 提供者/利用者それぞれの条文レベルの義務。本文を読めていない。本SaaSは「AI提供者」（AIを組み込んだサービス提供）に該当する見込みだが、条文での裏取りは未実施。
- 設計への示唆（推論）: 透明性（AI生成であることの明示、出力の根拠表示）、アカウンタビリティ（ログ・問合せ窓口）、プライバシー（入力データの扱い開示）、セキュリティ、人間関与（最終判断は人）。

### 2.2 ISMAP / ISMAP-LIU
- 主張: ISMAP-LIU は 2022/11 運用開始。機密性2情報を扱うSaaSのうち、リスクの小さな業務・情報向けで、ISMAP本体より監査・管理策が緩い。政府機関が調達する場合の登録制度。出典: https://www.soumu.go.jp/menu_news/s-news/01cyber01_02000001_00150.html （2022）、https://www.soumu.go.jp/main_content/000843545.pdf
- 未確認: 登録要件の詳細、費用、期間、仕様書検査が「リスク小」と判定される見込み。
- 示唆（推論）: 民間向けでは必須でない。自治体・官公庁向け販売を狙う場合のみ。民間は ISMS(ISO/IEC 27001) やSOC2 が先に問われる可能性が高い（本調査では未検証）。

### 2.3 個人情報保護法と生成AI（個人情報保護委員会）
- 主張: 2023/6/2 注意喚起。個人情報を含むプロンプトは利用目的の達成に必要な範囲か確認。本人同意なく個人データを入力し応答出力以外の目的で扱われると法違反のおそれ。事業者は入力データが機械学習に使われないことを確認するよう求める。出典: https://content.mlex.com/Attachments/2023-06-02_O42QLHNS4K18KVCJ%2FPPC%20Generative%20AI%20230602%20J.pdf （2023、公式PDFの転載）、https://scan.netsecurity.ne.jp/article/2023/06/13/49506.html
- 示唆（推論）: 設計書内の個人情報（テストデータ、担当者名）が外部LLMへの提供・委託に当たりうる。利用規約・DPA・マスキング機能が必要。

### 2.4 外部LLM送信の懸念（実態）
- 主張: JIPDEC/ITR「企業IT利活用動向調査2025」（2025/1実施、1,110社）で、生成AI全社利用企業の59.9%が機密情報の漏えいを懸念（最多）。2024年調査では会社契約の生成AI利用企業で67.3%。出典: https://www.nttdata.com/jp/ja/trends/data-insight/2025/0703 等の二次記事経由。一次資料（JIPDEC原本）は未確認。
- 未確認: JUAS・IPA・ガートナーの原データ。今回の検索では到達せず。「設計書」に限定した懸念の調査は見つからなかった。

### 2.5 ローカル/オンプレLLM需要
- 未確認: 国内企業の採用割合を示す一次調査は見つからなかった。出てきたのは導入支援会社の解説（機密保持が動機とする定性記述）のみ。出典例: https://www.issoh.co.jp/column/details/12964/ （ベンダー記述、数値は引用しない）
- 定量需要は未確認。需要検証は自社インタビューで行う必要がある。

### 2.6 LLM各社の公式条件（実証・取得日 2026-10-15）
- OpenAI API: 既定で学習に使わない。不正利用監視ログは最大30日保持。ZDR/修正監視は事前承認制。日本の保存地域指定は可（jp.api.openai.com）だが「地域内処理は不可」、日本利用にはMAMまたはZDRの承認が必須。国外で処理・一時保存される場合がある。出典: https://developers.openai.com/api/docs/guides/your-data
- Azure OpenAI（Foundry Models）: プロンプト/出力は他顧客・OpenAIに非公開、学習に使わない。標準デプロイは指定ジオグラフィ内で処理（Global/DataZone は例外）。不正利用監視のため一部が保存・人手レビューされうる。承認済み顧客は修正監視でオフ可。出典: https://learn.microsoft.com/en-us/legal/cognitive-services/openai/data-privacy （最終更新 2026-06）。日本リージョン(Japan East)での提供モデルは本調査で未確認。
- Gemini（Vertex AI）: 許可なく学習・ファインチューンに使わない。キャッシュは最大24時間で削除。不正利用監視でプロンプトをログする場合があり、例外申請でZDR可（一部機能は不可）。地域/マルチリージョン エンドポイントでは指定場所内。グローバルエンドポイントでは任意リージョンで処理。取得ページに東京リージョンの記載なし（未確認）。出典: https://docs.cloud.google.com/vertex-ai/generative-ai/docs/data-governance
- 共通の落とし穴: 「学習不使用」と「保持ゼロ」は別。国内保存と国内処理も別。いずれも承認・契約が要る。

### 2.7 競合 QuintSpect（バルテス）
- 主張: 2026/7/6 正式版。Excel/PDFの要件定義書・設計書を5観点（正確性・理解性・視覚性・深層性・信頼性）でスコア化し改善提案、複数文書の矛盾検知。出典: https://cloud.watch.impress.co.jp/docs/news/2122699.html （2026）、https://aipicks.jp/tool/quintspect
- 未確認: 「Gemini・国内リージョン」の依頼前提は今回の検索で確認できなかった。料金も資料間で不一致。公式 https://service.valtes.co.jp で要確認。

## 4. 「送信しない（ローカルLLM）」選択肢の判断

判断: 差別化になりうるが、単独の主軸にはしない。オプション提供として検証する（推論。需要は未確認）。

根拠:
- 懸念は実在する（主張）: 全社利用企業の59.9%が機密漏えいを懸念（JIPDEC/ITR 2025、二次経由）。
- ただし設計書特化の定量データなし（未確認）。ローカル需要の割合も未確認。
- クラウドLLMでも学習不使用・地域指定は契約で得られる（実証）。「送信しない」の優位は、承認手続き不要・説明が一言で済む点に限られる。
- 損益: 実装コスト（品質低下のリスク、顧客側GPU/運用、サポート）が増える一方、取り消し可能（オプション化）。放置した場合は、機密性の高い顧客（金融・官公庁・防衛等）を取りこぼす。
- 競合（QuintSpect）はクラウド前提と見られる（未確認）。比較で「送信ゼロ」を打ち出す余地はあるが、品質差で負ければ逆効果。

次の一手（推奨）:
1. 見込み顧客5〜10社に「設計書を外部LLMへ送れるか」を聞く（需要の一次データ化）。
2. ローカルLLM(Ollama)での検査精度をクラウドLLMと同一データで比較する。
3. 結果が良ければ「送信先選択式（クラウド/ローカル）」を打ち出す。

引用してはいけない数値: ローカルLLM導入率など、導入支援会社記事の数値（原データなし）。
