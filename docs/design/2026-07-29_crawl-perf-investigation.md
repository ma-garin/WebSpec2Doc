# クロール速度の調査（P2-6）

- 実施日: 2026-07-29 ／ 対象: 同梱デモサイト（`demo/demo_site.py --port 8767`・7 画面）
- 発動条件: P0-1 で「TTFV の支配項はクロール本体（全体の約 88%）」と判明したため
- **結論: 大きく安全に削れる箇所は無かった。所要時間の大半は成果物を作る解析処理そのもの。**

## 2. 内訳の判明分（1 画面あたり）

| 内訳 | 所要 | 性質 |
|---|---|---|
| アクション探索（`explore_page_actions`） | 約 0.44 秒 | モーダル・タブ等の**画面状態を検出**する。最大 10 要素をクリックし各回 300ms 待つ |
| `networkidle` 待ち | 約 0.07 秒 | クロールでは既に静止済みのことが多く、discover ほどの税は無い |
| **残り（未分解）** | **約 1.9 秒** | スクリーンショット・フォーム/ジオメトリ抽出・必須入力の dry-run 検証 |

## 3. 見送った施策とその理由

| 候補 | 削減量 | 見送った理由 |
|---|---|---|
| 礼儀待ちの短縮 | **0 秒** | 実測で効果なし。そもそも支配項ではない |
| 並列数の既定引き上げ | −7% | 効果が小さいのに**対象サイトへの負荷は確実に増える**。割に合わない |
| a11y 監査の既定オフ | −1% | 効果がほぼ無い上に、監査結果は成果物の価値そのもの |
| アクション探索の削減 | −19% | **最大の削減余地だが、モーダル・タブの検出結果は成果物に載る**。速度と引き換えに網羅性が落ちるため、既定を変えるべきではない |
| discover と同じ「安定待ち」への置換 | 未計測 | クロールはフォーム抽出のため安定した DOM を必要とする。discover（URL とタイトルのみ）とは要件が違う |

## 4. 結論

**残り約 1.9 秒/画面は、スクリーンショット・フォーム抽出・入力検証の観測という、成果物を作るための処理そのものである。**
ここを削ることは出力の質を落とすことと同義で、「速いが中身が薄い」方向への変更になる。
P0-1 の目標「TTFV −30%」は、**クロールの高速化ではなく達成できない**と判断する。

代わりに次のいずれかで体感を改善すべきと考える（いずれも**別途デザイン承認が必要**）。

1. **P1-1 残り時間の動的表示** — 待ち時間そのものではなく「終わりが見えない」ことを解消する
2. **P3-1 ゼロ待ちサンプル** — 事前生成済みの成果物を先に見せ、初回の価値到達を待ち時間ゼロにする

## 5. 速度と網羅性を切り替える既存の環境変数（利用者向けの逃げ道）

コードを変えずに調整できる。**既定は網羅性を優先している。**

| 環境変数 | 既定 | 効果 |
|---|---|---|
| `WEBSPEC2DOC_MAX_ACTIONS_PER_PAGE` | 10 | 0 にすると約 19% 短縮。モーダル・タブの検出を行わない |
| `WEBSPEC2DOC_FULL_SCREENSHOT` | 有効 | 無効にすると拡大表示用の全体スクショを撮らない |
| `WEBSPEC2DOC_CRAWL_INTERVAL_SEC` | 1.0 | 対象サイトへの間隔。**短縮は相手への負荷増**なので推奨しない |
| `WEBSPEC2DOC_STABILITY_TIMEOUT_MS` | 3000 | networkidle の上限 |

## 6. 弱点

1. **残り 1.9 秒/画面を内訳まで分解していない。** スクリーンショット単体・フォーム抽出単体の計測は行っておらず、「解析処理そのもの」と括った。ここを分解すれば、さらに削れる箇所が見つかる可能性は残る
2. 計測は**ローカルの静的サイト 7 画面のみ**。外部サイト・SPA・大規模サイトでは支配項が変わる（通信待ちが支配的になる）可能性が高く、その場合は並列化の効果が本調査より大きく出るはず
3. 並列 4 の効果が 7% に留まった理由（ブラウザ内の直列化なのか、ディスク I/O なのか）を特定していない。ここが解ければ並列化の価値は変わりうる
