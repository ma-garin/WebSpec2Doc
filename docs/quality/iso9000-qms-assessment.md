### 1.3 判定の定義

| 判定 | 意味 |
|---|---|
| **適合** | 要求事項を満たす文書化した情報と、その運用の証拠がともに存在する |
| **部分適合** | 文書化した情報は存在するが運用・記録・レビューのいずれかが欠ける、または要求の一部のみを満たす |
| **不適合** | 該当する文書化した情報・記録がリポジトリ内に存在しない |
| **対象外** | 単独開発体制のため要求事項が実質的に適用されない（該当箇所に理由を記載） |

### 1.4 実施しなかったこと（明示）

- テストの実行（`pytest` / `make test` / `make verify-ui` / `make coverage`）は**未実行**。文書に記載された実測値は**転記された値としてのみ**扱い、本評価では再現していない。
- 生成された `.docx` / `.xlsx` の中身は**未確認**（Markdown 正本のみ確認）。
- CI の実行履歴（GitHub Actions のラン結果）は**未確認**。ワークフロー定義のみ確認した。

## 4. ISO/IEC 90003 の観点（ソフトウェア固有）

ISO/IEC 90003 は ISO 9001 の要求事項をソフトウェアに適用する際の指針であり、特に**構成管理・検証と妥当性確認・設計レビュー**の具体化を求める。

### 4.1 構成管理（90003 §7.5.3 / §8.5.2、IEEE 828 相当）

| 観点 | 証拠 | 所見 |
|---|---|---|
| 構成品目の識別 | `WS2D-CM-001` §2 構成品目一覧（ソースコード／設計文書／テスト資産／依存パッケージ等を、識別方法・保管場所・管理方法の表で定義）、§3.1 文書ID体系、§3.2 バージョン番号規則、§3.3 Git ブランチ・タグ規則 | **適合。**構成品目が網羅的に列挙され、それぞれ識別方法まで定義されている |
| ベースライン管理 | `WS2D-CM-001` §6、`WS2D-RL-001_リリース手順書`、`WS2D-MG-001/002`（移行計画・手順） | **部分適合。**ベースラインの定義は存在するが、実際に確定したベースライン（タグ）の一覧・再現手順の検証記録は未確認 |
| 構成監査 | `WS2D-CM-001` §7：`scripts/extract_asbuilt.py` が生成する `routes.json` / `modules.json` / `templates.json` / `schema.sql` / `licenses.json` と設計文書を突合。差分があれば「設計文書の記述漏れか、意図しない実装変更か」を切り分ける | **部分適合。**方式は 90003 の意図を的確に実装している（**文書ではなくコードを一次情報とする**）。しかし文書自身が「**構成監査専用の記録様式・記録先は本リポジトリに存在しない（要決定）**」と自認 |
| 変更管理 | `WS2D-CR-001`、`docs/adr/`、GitHub PR フロー（`AGENTS.md` 恒久ルール） | **部分適合。**§2.3 の 6.3 と同一 |
| 文書とコードの乖離検出 | `scripts/check_doc_consistency.py`（`make docs-check`）：陳腐化した数値・リンク切れ・再生成漏れ・循環依存を点検 | **適合。**乖離を機械検出する仕組みが実在する点は 90003 の要求水準を上回る |

### 4.2 検証（Verification）と妥当性確認（Validation）（90003 §8.3.4）

| 観点 | 証拠 | 所見 |
|---|---|---|
| V と Val の区別 | `WS2D-QA-001` §13：「検証＝building the product right（L0〜L3 の自動ゲート）」「妥当性確認＝building the right product（DoD Type B の REQUIRED 項目：ユーザーストーリー・受け入れ基準の充足確認、ブラウザでの実操作）」と定義し、「どちらか一方だけでは完了と扱わない」と宣言 | **適合。**IEEE/ISO 用語法に沿った正確な区別がなされている |
| 検証の網羅性 | `docs/process/functional-integrity-gate.md`：実行パス `UI → API → backend route → service/core → output → persistence → error handling → user-visible evidence` の全通過を義務化。critical / high リスク機能では happy path / failure path / timeout / cancellation / auth・login wall / robots 制限 / partial result・recovery / logs・evidence / user-visible error の**9 観点**を必須確認 | **適合。**「UI がある」「テストが通った」を完了根拠として**明示的に禁止**しており、90003 が警戒する「部分検証をもって完了とする」誤りに直接対処している |
| 妥当性確認の記録 | `docs/DEFINITION_OF_DONE.md` Type B：スクリーンショットを `tests/e2e/screenshots/` に保存、1920×1080 と 1366×768 の両解像度確認 | **部分適合。**証跡はスクリーンショットのみで、**受入基準への合否を記録する様式がない**。`WS2D-AT-001_受入テスト仕様書` は存在するが、実施結果の記録との紐付けは未確認 |
| テストの妥当性そのものの検証 | `WS2D-QA-001` §14：AutoRun 生成テストに対する**ミューテーションテスト**（`web/services/mutation_verifier.py: run_self_check`）。出力は自己検証スコアと弱いテスト一覧で、`mutation_verification.json` として `output/{domain}/qa_process/mutation_check/` に永続化。適用不能な場合は `self_check_not_applicable` と明示 | **90003 の要求水準を超える。**「カバレッジが高い＝品質が高い」という誤った等式を避ける補助線として設計されており、記録も永続化されている |
| LLM 経路の検証 | `WS2D-QA-001` §15：実測（confidence 1.0）と LLM 由来（confidence 0.9 以下）を区別して出力（`src/llm/prompt_guard.py` の `QA_PRINCIPLES`）、幻覚のフィルタ除去（`filter_hallucinated_findings`、`src/ingest/llm_extractor.py` の quote 突合）。「LLM 経路の追加はこのフィルタ実装とセットで行うことをゲートとする」 | **適合。**規格が直接扱わない領域だが、「出力の根拠の等級を区別する」という 9.1.3 の趣旨に整合する |

### 4.3 設計レビュー（90003 §8.3.4 a）

| 観点 | 証拠 | 所見 |
|---|---|---|
| レビュー体制の定義 | `WS2D-QA-001` §6「レビュー体制と観点」、§7「静的解析・動的解析の方針」、`docs/DEFINITION_OF_DONE.md` Type A REQUIRED「code-reviewer エージェントを実行し HIGH 以上の指摘なし」 | **部分適合。**体制と観点は定義されている |
| レビューの独立性 | `.claude/rules/speed-harness.md` H-4「作った本人に検証させない。生成系エージェントとは別に、検証系エージェント（レビュー・仕様との突き合わせ・構文/リンク検査）を 1 本以上、計画に含める」 | **限定適合。**独立性の確保が明文化されている点は評価できるが、**検証者も同一の LLM ファミリーであり、真の独立性ではない**。人的レビュアーは 1 名（＝作成者本人）しかいない |
| レビュー結果の記録 | 証拠なし。ADR は「決定」の記録であり「レビューでの指摘と解決」の記録ではない | **不適合。**設計レビューの実施記録（日付・参加者・指摘事項・処置・クローズ）を残す様式がリポジトリ内に存在しない |
| コーディング規約 | `docs/sdlc/30_implementation/WS2D-CS-001_コーディング規約.md`、`pyproject.toml`（ruff: E/F/W/I/UP/B、line-length 100、mypy: `warn_unused_ignores` / `warn_redundant_casts` / `no_implicit_optional`）、`make lint`（ruff ＋ mypy ＋ `scripts/check_e2e_conventions.py` ＋ `scripts/check_fetch_error_handling.py`） | **部分適合。**規約と自動検査は存在するが、`WS2D-QA-001` §16 自身が「**pre-commit が black / ruff / mypy / bandit を強制していないというギャップ**」を「当たり前品質レベルの課題」として自認している（`.githooks/pre-commit` の実装を確認したところ、実行されるのは `py_compile` と `pytest` と UI hash 照合のみで、この自認は正しい） |

## 5. 不適合一覧と是正処置の提案

重大度は「① QMS の根幹（PDCA の閉ループ）を欠く」「②文書化した基準と実態が矛盾する」を最上位とした。

### NC-01【重大】文書化した品質基準と実際の運用が矛盾している（箇条 8.1 / 8.5.1 / 7.5）

| 項目 | 内容 |
|---|---|
| 不適合の内容 | 上位文書は自動ゲートを**必須・スキップ不可**と規定するが、下位の速度規定がそれを**無効化**している |
| 証拠（規定側） | `docs/DEFINITION_OF_DONE.md`：`make test` は「MANDATORY（自動チェック・**スキップ不可**）」。`docs/TESTING_STRATEGY.md` L1/L2：「実行タイミング：**全コミット前**（pre-commit hook により自動）」「1 件でも FAIL、またはカバレッジ < 80% → コミット不可」。同 PROHIBITED：「ブラウザ確認なしにコミット・プッシュすること」 |
| 証拠（無効化側） | `CLAUDE.md`：「**pytest / make test / make verify-ui / make lint はユーザーが要求した時のみ実行する**（H-7・2026-08-22）。コミットは `--no-verify` で直行する。無断のゲート実行はフック（`.claude/hooks/block-gates.py`）が**物理的に拒否する**」。`.claude/rules/speed-harness.md` H-7：「add(パス明示) → commit `--no-verify` → push → PR 作成 → マージ。**CI は待たない**」。`.claude/hooks/block-gates.py`：`_GATE_PATTERN` に合致するコマンドへ `permissionDecision: "deny"` を返す |
| なぜ不適合か | ISO 9001 8.1 は「プロセスを**計画どおりに**実施した証拠を保持する」ことを求める。計画（DoD / TESTING_STRATEGY）が「全コミット前に実行」と定めているのに、運用は「要求時のみ」であり、両者が同一リポジトリ内で並存したまま優先関係が宣言されていない。`docs/README.md` は「矛盾がある場合は必ず『正』の文書が優先される」と定めるが、`CLAUDE.md` と `DEFINITION_OF_DONE.md` の優先関係はどこにも規定されていない |
| 是正処置の提案 | ① `docs/DEFINITION_OF_DONE.md` を改訂し、**ゲートの実行タイミングを実態に合わせて再定義する**（例：「コミット単位では実行しない。PR 単位／マイルストーン単位で `make verify-all` を実行する」）。基準を実態に合わせられない場合は、逆に H-7 を撤回する。**どちらを選ぶにせよ、二重規範を解消することが必須。**② ゲートを免除して成立させたコミットには「未検証」であることを機械的に刻む（例：commit trailer `Gates: skipped` を `--no-verify` 経路で自動付与）。③ 免除の累積を可視化する台帳 `docs/quality/gate-exemption-log.md` を新設し、免除理由・対象コミット・後追い検証の実施日を記録する |

**優先順位の考え方**：NC-01 は「文書と実態の矛盾」であり、他のすべての適合判定の信頼性を毀損するため最優先。NC-02 と NC-03 は PDCA の閉ループを作るための最小構成であり、この 2 つが入るだけで NC-05・NC-09・NC-11・NC-12 の運用は自然に駆動される。NC-13〜NC-15 は既存の仕組みへの追記で解決でき、新規プロセスを要しない。

## 6. 本評価の弱点

- **単独開発体制に組織向け要求事項を当てはめる限界**：箇条 5（リーダーシップ）・7.2（力量）・9.2（監査員の独立性）は複数名の組織を前提とした要求であり、1 名では構造的に充足できない。本評価はそれらを「対象外」ではなく「不適合」と判定したが、規格の意図（責任の所在の明確化、能力の担保、客観性の確保）に照らせば「代償措置の有無で評価すべき」という別の判定もありうる。この線引きは評価者の裁量であり、確定的ではない。
- **運用の実績を検証していない**：本評価はテスト・ゲート・CI を一切実行していないため、`.githooks/pre-commit` や `.github/workflows/ci.yml` が**実際に機能しているか**は未検証である。文書に記載された実測値（カバレッジ 84.30%、L1/L2 3,239 passed 等）も転記された値をそのまま扱っており、再現していない。したがって「適合」と判定した 8 件のうち、8.5.1・8.5.2 は**設計上の適合であって運用上の適合ではない**。
- **証拠の非存在の証明が検索語に依存する**：4.2・7.2・9.2・9.3 の不適合判定は、日本語キーワード 6 語による grep 結果（ヒット 0 件）に依拠している。英語表記（internal audit / management review 等）や別の言い回しで同等の活動が記録されている可能性は排除しきれていない。また `docs/archive/` を除外したため、過去に存在して廃止された記録は評価に含まれていない。
