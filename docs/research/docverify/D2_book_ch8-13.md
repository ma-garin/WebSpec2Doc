## 1. 第8章 模型検査入門（900行目以降: 8.4後半〜8.6）

### 要点
- 確率的・定量的検査は DTMC/CTMC/MDP の3模型。結果は「模型仮定に相対」と本書が強調。
- 反例は「贈り物」。トレース・変数値・遷移・時刻で構成し、最小化と可視化が要る。
- ツール比較の軸は「方式」ではなく「完走条件と未検査範囲」。結果は反例なし/反例/未完走を区別する。
- 空虚性の罠: assume を足して assert を通すのは修正ではない。assert と cover を対にする。

### ツール機能への示唆
- 判定は三値以上にする: 成功 / 反例あり / 未完走(timeout・unknown)。「未完走」を緑にしない。
- 検証レポートに「検査範囲・前提・未検査範囲」欄を必須化する(保証境界の明示)。
- 矛盾指摘には最小再現(短い反例)を付ける。冗長な指摘は読まれない。
- 「前提を足して通す」を検知する。前提(assume相当)の増減を差分で警告する。
- 反例DB(分類・検索・回帰確認)を持てば、指摘の再発検出とレビュー教材になる。

### 引用(各2文以内)
- 「反例は、単なるエラー報告ではありません。それは、システムの隠れた問題を具体的に示してくれる『贈り物』です。」(8.5)
- 「反例なしは境界内の結果。solver の unknown や timeout を別扱い」(8.6 比較表)

## 2. 第9章 定理証明の基礎（982行目以降: 9.4後半〜9.8）

### 要点
- 9.7: LLMが証明候補を作っても、正当性はカーネル/検証器/再実行CIが担う信頼モデル。「LLMが通したから正しい」は不可。
- AI生成物のレビュー最小観点は5つ: 主張と要件の一致 / 暗黙の前提 / 未完了マーカー / 実行ログと再現情報 / 捨象した前提の記録。
- 未完了マーカー(Admitted/sorry/axiom/assume)は「検証済み」に数えない。
- 検証コストは一律倍率で見積もらず、パイロットで実測する。
- Lean/Rocq/Isabelle は小さな信頼核が最終判定。周辺自動化は候補生成に分離する。

### ツール機能への示唆
- 商用化の中核になる設計原則: 「LLMは提案、判定は決定的な検査器」。仕様書の矛盾判定は LLM 断定にせず、規則ベース/ソルバー/再実行で閉じる。
- 「未解決穴」ダッシュボード: TBD/未定義/暗黙の前提を機械抽出し、件数を表示する(sorry検出の仕様書版)。
- 自然言語要求→形式化で捨象した前提を、レビュー記録の必須項目にする。
- 前提(import・公理・環境仮定)を明示する欄を、検証結果ごとに出す。
- コスト見積もりはパイロット実測ベースを営業資料にも反映する(一律倍率を謳わない)。

### 引用(各2文以内)
- 「『LLM が通したから正しい』ではなく、『カーネルが通ったが、主張が要件と一致しているかは別途レビューが必要』という整理になります。」(9.7)
- 「定理の主張や前提を LLM だけで確定する。」はリスクが高い領域として列挙(9.7)。

## 3. 第11章 開発プロセスとの統合

### 要点
- 選択的形式化とリスクベース(安全/セキュリティ/ビジネス/技術の4リスク)で対象を絞る。
- 段階導入は4段階(PoC 2〜4週 → 限定適用 2〜3か月 → 部門 6か月〜1年 → 全社 1〜2年)。本書の主張。
- 要求形式化は3段階: 構造化自然言語 → 半形式 → 形式。一貫性・完全性・トレーサビリティを機械検査できる。
- 一筆書きフロー: Alloy(構造) → TLA+(振る舞い) → 契約(Zod等) → TDDテスト。
- CI配置: PRは小スコープ、夜間は深く、リリース前は厳格(PR段階は30-90秒目安)。
- runtime verification: 観測トレースが対象。「違反が出なかった」は観測範囲での不検出に過ぎない。欠落・順序・重複・PIIは別契約。
- コスト便益(本書の主張・原典未確認): 開発時間+20〜50%(初期)、テスト工数-10〜30%、リリース後障害は半分以下、教育は初期40〜80h/人。業界別に回収年数も記載。

### ツール機能への示唆
- 3段階の「形式化ラダー」をプロダクトの導入段階に写す: 構造化日本語テンプレ → 半形式(条件・入力・出力・制約) → 形式。最初の価値は一貫性と網羅性の自動指摘。
- 要求文書への指摘カテゴリは本書の3種を採用: 矛盾 / 不完全(未考慮ケース) / トレーサビリティ欠落。
- 「PR→夜間→リリース前」の3層実行プランをSaaSの標準プロファイルにする(速い軽量検査+深夜の網羅検査)。
- 反例/違反を再現手順付きで出す(失敗の可視化)。ゲートは強制とソフトを重要度で使い分ける。
- 運用トレース監査(ログ照合)機能は、有限トレース意味論の注意(未決定/欠落)を結果に出す。
- ROI算定シートを提供: 式は ROI=(年間ベネフィット-年間コスト)/年間コスト。入力は顧客の実測。本書の倍率はデフォルト値にしない。
- 役割定義(仕様責任者/実装検証者/統合検証者/QA)をワークフローの承認ロールに転用できる。

## 4. 第12章 ツールと自動化

### 要点
- CI段階別の検証深度: PR(契約・軽量模型検査・静的解析) / 夜間(状態空間拡大) / リリース前(完全検証・証明再検証)。
- 運用Tips: seed固定・上限設定・結果キャッシュ(フレーク対策)。失敗時に「再現手順・最小反例・影響範囲」の3点を自動収集。
- 検証成果物のサプライチェーン管理: ツールver・検査範囲・反例・未証明部分・LLM使用・CI結果を記録(SBOM発想)。
- 結果は success / failure / timeout / unknown / flaky を区別。「未検査/不明を正しいと誤認しない」。
- 未証明部分は失敗扱いか、期限・責任者つきの例外台帳に登録。
- SATのsatはモデル再評価、unsatは証明書+独立checkerで再検査。ただしエンコード後の保証に限る。
- 12.9 AIエージェント前提のガードレール: 「AIが提案 → 検証器が判定 → 人が承認」。PR必須チェックの最小セットあり。
- 指標: MTTR、反例再現率、検出密度、偽陰性の兆候。

### ツール機能への示唆
- 商用の差別化候補: 「検証証跡パッケージ(エビデンスバンドル)」の自動出力。入力ハッシュ・設定・版・判定・反例・未検証一覧を1点にまとめ、監査に出せる。
- 例外台帳(期限・責任者・承認者固定)を標準機能にする。例外の常態化を件数推移で警告。
- 12.9.1のPR必須3項目をテンプレ化: 仕様差分に対応する仕様更新 / 検証ログ(seed・深さ・スコープ)添付 / 反例時の修正手順記録。
- AI生成の仕様草案・修正案は「未信頼入力」として扱い、採用/不採用の判断を記録する。
- PR体験: 合計90秒以内の軽量プロファイル、夜間の深いプロファイル、リリース前の承認フロー強化の3プリセット。
- 検証ダッシュボードにMTTR・再現率・トレンド・通知(重要度別)を載せる。
- ベンダーロックイン回避として標準入出力形式(JSON・ITF等)を持つ。

- 「CI が保証するのは、指定した仕様、設定、ツール、バージョン、境界で検査が通ったという事実であり、システム全体の安全性そのものではありません。」(12.7)

### 要点

- 13.10 現代産業応用:
  - Cedar(認可ポリシーをSMT解析): 「変更で権限が広がっていないか」「到達不能条件」「リファクタ後の等価性」を検査。
  - Tamarin: 欠陥版と修正版を対にして、期待結果をJSONで固定。lemma名・status・攻撃トレースを厳密照合し、終了コードだけで判定しない。
  - Bedrock Guardrails: 自然言語をルール/変数に対応づけ、LLM出力を有効/無効/曖昧/未述仮定/複雑すぎるで返す。
  - スマートコントラクト: 不変条件・事前事後条件が書きやすく、検証コストが説明しやすい領域。
- 横断の教訓: 仕様と実装を分離 / 局所・高リスクな性質から / 検証器の保証範囲と事業要求を分ける / 証跡を成果物に含める / サービス仕様の変化に追従。
- 一般ビジネスアプリは価値実感が難しく導入成功率が低い、と本書は述べる。

### ツール機能への示唆
- 差別化の最短経路: 「ポリシー/ルール表の差分検査」。Cedarの発想(許可集合の拡大検知・到達不能・等価)を、料金表・権限表・状態遷移表・業務ルール表といった表形式仕様に適用する。
- 「欠陥版/修正版の対照テストセット」を、顧客向けデモと自社の回帰テストの両方に使う(期待結果を固定して厳密照合)。
- 結果レポートは Bedrock の分類を借りる: 整合 / 矛盾 / 曖昧 / 未述の前提 / 複雑すぎて判定不能。判定不能を隠さない。
- 各検証に「形式化と保証範囲」の5欄(対象・手法・検証対象・保証・対象外)を自動生成する。営業上の誤解(過大訴求)を防ぐ。
- 想定顧客: 規制業界(金融・医療・自動車)から入る。ISO 26262等の規制要求は導入動機になる、と本書は述べる。一般業務アプリは直接訴求が難しい。
- 失敗パターン5種を導入チェックリスト/オンボーディング診断に転用できる。
- 認可・規程・業務ルールなど「実装から切り出してレビューできる性質」を最初の対象にする。
