AutoRun 入力後画面の再設計（案）

対象: URL入力／文書駆動の次の画面から実行結果まですべて

起点: 2026-07-26 のFB（アシスタント常駐・仕様書作成の不可視性・成果物一覧のデザイン・進行不能）

レビュー待ち — 承認前に実装へ進みません

1. 何が壊れているか（診断）

FBを症状ではなく原因で分類する。

#症状（FB）原因種別
F1右のQAアシスタントが常駐して邪魔使用頻度の低い機能に画面幅の1/3を常時割り当てているレイアウト
F2「仕様書作成」で何をしているか見えない進捗が「ステップ名＋スピナー」のみ。取得中URL・検出結果・遭遇した障害が一切出ない可視性
F3ログインが必要でも何も聞かれないログイン壁を検出しても停止せず、無言で「取得できた範囲」で進む制御フロー
F4成果物一覧のデザインが受け入れられない12件を均質な縦積みリスト＋同一の「プレビュー」ボタンで並べており、どれが重要か・何が分かるかの情報が0情報設計
F5この画面から先に進めない「確定する」がリスト最下部。要確認5件＋自動承認149件の下で画面外導線 （修正済み）

共通する根本原因は1つ。

「AutoRunが今なにをしていて、人は次に何をすればよいか」が画面のどこにも常設されていない。

個々の部品は揃っているが、進行の主導線が無いため、人は毎回スクロールして探すことになる。

2. 設計方針

  1. 主導線を1本にする — 画面上部に「現在地」と「次の一手」を固定表示する。人が探す状態を作らない
  2. 常駐は主導線だけ — アシスタントも成果物も、必要になったとき呼び出す
  3. 黒箱を作らない — 待ち時間のある処理は、いま何を取得しているかを逐次見せる
  4. 止まるべきときは止まる — ログイン壁・robots制限・タイムアウトは「無言で継続」せず、人に判断を返す
  5. 一覧は数字で語らせる — ファイル名の羅列ではなく、その成果物で何が分かったかを1行と主要数値で示す

3. 個別の設計

3.1 QAアシスタント（F1）

  • 右カラム常駐を廃止。メインカラムを全幅に戻す
  • 呼び出し口は2つに限定する
    • 各項目の「アシスタントに相談」ボタン（現状どおり）
    • 画面右下の常設FAB（1つだけ）
  • 開くと右からのドロワー（幅420px・オーバーレイ）。閉じると完全に消える
  • 相談対象の項目タイトルをドロワー先頭に固定表示し、何について話しているかを見失わせない

3.2 仕様書作成の可視化（F2）

「仕様書生成」ステップ実行中、以下をライブ表示する。

仕様書を作成しています（3/9ページ）
├ 取得済み  /index.html        フォーム0件・リンク6件
├ 取得済み  /login.html        フォーム1件（必須2）
└ 取得中    /mypage.html       …
  • 現在取得中のURLを必ず出す
  • 各ページで検出したもの（フォーム数・必須項目数・リンク数）をその場で出す
  • スキップしたURLは理由つきで出す（robots Disallow ／ 404 ／ タイムアウト ／ 対象外ドメイン）
  • 「取得できなかった」を隠さない。空欄で通さない

3.3 ログイン壁の扱い（F3）決定

ログインが必要と判定した時点で、進行を止めて人に返す。

判定条件（いずれか）:

  • ログインフォーム（password型input）を持つページへリダイレクトされた
  • 401 / 403 が返った
  • 対象URLに到達したが、指定した継続条件を満たさない

提示するもの:

このサイトはログインが必要です。
取得できた範囲: 3画面（未ログインで到達可能な範囲のみ）
[ ログイン情報を設定して続ける ]  [ 未ログインのまま進む ]
  • 既定はどちらも選ばせる。勝手に片方へ倒さない
  • 「未ログインのまま進む」を選んだ場合、成果物に「未ログイン範囲のみ」を明記する

3.4 成果物一覧（F4）

現状の縦積みリストを廃止し、3つの束に再編する。

束何のための束か含めるもの
いま見るべきもの結論と判断材料テスト結果レポート・横断レビュー・仕様ドリフト
中身を確かめるもの根拠の確認仕様書HTML・テストケース・テスト設計・モデルグラフ
持ち出すもの提出・再利用Excel・JSON・Playwright候補・証跡パック

各項目は「名前＋プレビューボタン」ではなく、次を持つ。

テストケース                                    47件
 うち要確認 5件 / 自動承認 42件・文書要件の94%をカバー
  • カード全体をクリックでプレビュー（ボタンの繰り返しを廃止）
  • 主要数値を必ず1つ出す。数値が出せないものは「未生成」と明示する
  • 中身が空の成果物は灰色にして最後尾へ（並びを固定して空箱を上位に置かない）

3.5 進行の主導線（F5・全体）未決 B

以下は「バーを置く」案の内容。置くかどうかは §5 未決B で判断していただきます。

画面最上部に固定バーを置く。スクロール位置に関係なく常に見える。

STEP 1 テスト目的  ─  未確認 0件  ─  [ 確定して次へ ]
  • 現在のステップ名／残タスク数／次の操作の3つだけ
  • 次の操作ボタンは、押せない場合理由をボタン脇に出す（「未確認が2件あります」）
  • 左サイドの進捗リストは現在地の表示に徹し、操作は主導線に集約する

5. 決定事項と未決事項

決定済み（2026-07-26）

決定ログイン壁を検出したら、止めて聞く 無言で「取得できた範囲」を進めない。§3.3 のとおり実装する。
決定F1〜F4 は同時並行で進める 可視性・制御フロー（F2/F3）とレイアウト・情報設計（F1/F4）を分けて出さない。

未決 A — 成果物一覧のまとめ方

現状は SDLC の工程名（計画／分析／設計／レポート）で並べている。 これは作った側の都合の並びで、見る人の「いま何を開けばいいか」には答えていない。 そこで 「いつ開くか」 で分け直すのが 3束案。中身は次のとおり。

束いつ開くか入るもの（現状の成果物名）
1. 結果を見る 実行が終わった直後。まずここだけ見れば判断できる テスト結果レポート／横断レビュー／仕様ドリフト差分
2. 根拠を確かめる 結果に納得できないとき、中身を追う 仕様書HTML／テストケース／テスト設計／テスト分析／モデルグラフ／観点スナップショット／テスト計画
3. 持ち出す 報告・提出・再利用するとき 仕様書JSON／spec.xlsx／Playwright候補／証跡パック

決めていただきたいのはここです。

案A: 3束案（「いつ開くか」で分ける）

利点: 実行直後に開くべきものが1つ目の束に絞られる。12件を毎回見比べなくてよい

難点: QA工程の呼び名（分析・設計）と一致しないため、工程名で探す人には見つけにくい

案B: 現状どおり工程順（計画／分析／設計／レポート）のまま、見せ方だけ直す

利点: 呼び名が変わらない。学習コストゼロ。カードの情報量改善（数値の表示）だけで効果は出る

難点: 「まず何を開くか」は相変わらず人が判断することになる

未決 B — 主導線バー（§3.5）をそもそも置くか

「次に何をすればよいか」を常設する手段として上部固定バーを挙げたが、置かない選択もある。

案A: 上部に固定バーを置く

STEP 1 テスト目的  ─  未確認 0件  ─  [ 確定して次へ ]

利点: スクロール位置に関係なく、現在地と次の操作が必ず見える

難点: 画面上部を常時占有する。左サイドの進捗リストと役割が重なり、「現在地の表示が2箇所」になる

案B: バーは置かず、各段階パネルの下端に確定操作を貼り付ける（sticky）

利点: 常時占有が無い。現在地の表示は左サイドに一本化される。今回の緊急修正と同じ方式で、すでに効果を確認済み

難点: 「次に何をすればよいか」の文言を出す場所が段階ごとに分散する

補足: F5（進めない）の直接原因は「確定ボタンが画面外」であり、これは案Bの方式で解消済みです。 バーはそれ以上の改善を狙うもので、置かなくてもF5は再発しません。

6. この案の弱点

  • F2/F3はバックエンドの進捗イベント設計を伴うため、見た目の変更より重い。影響範囲の見積もりが web/routes/auto_run.py の実装確認前であり、粗い
  • 成果物カードに出す「主要数値」は、成果物ごとに算出元が異なる。すべての成果物で数値を出せるかは未確認
  • E2Eスナップショットの再取得が必須になるため、UI変更ゲート（.ui-verified）の通過コストを織り込んでいない
