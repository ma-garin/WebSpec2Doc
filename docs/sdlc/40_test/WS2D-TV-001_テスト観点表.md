## 1. 観点体系の定義

WebSpec2Doc は観点（テストで確認すべき着眼点）を JSON テンプレートとして製品内部に保持し、
利用者が観点管理ビューから選択・追加・カスタマイズできる設計になっている。
`data/viewpoint_templates/` には現在 **5 つのテンプレートファイル**が存在し、
合計 **277 件の観点項目**を収録する（2026-08-02、全ファイルを Python で解析し実測）。

| テンプレートファイル | 名称 | 分類軸 | フォルダ数 | 観点項目数 |
|---|---|---|---|---|
| `common_web.json` | 共通観点（Webアプリ横断） | ISO/IEC 25010・ISTQB・OWASP ASVS・WCAG 2.2 の複合 | 13 | 250 |
| `istqb.json` | ISTQB テストレベル | ISTQB Foundation Level の4レベル | 4 | 8 |
| `iso25010.json` | ISO/IEC 25010 品質特性 | 製品品質モデル8特性 | 8 | 8 |
| `nfr2018.json` | 非機能要求グレード2018 | IPA 非機能要求グレードの6大項目 | 6 | 6 |
| `pmbok.json` | PMBOK 品質・リスク管理 | プロジェクトマネジメント知識体系 | 5 | 5 |
| **合計** | — | — | **36** | **277** |

`common_web.json` が観点の主軸であり、業種に依存しない Web アプリケーション共通の確認観点を
「画面表示」「入力フォーム」「画面遷移」「認証・認可」「入力値セキュリティ」「API・連携」
「データ整合性」「検索・絞り込み」「性能」「互換性」「アクセシビリティ」「運用・保守」
「仕様トレーサビリティ」の 13 分類（250 項目）に整理している。残り 4 テンプレートは
規格別の補助観点（プロセス・品質特性側からの確認軸）として機能する。

各観点項目は `name`（観点名）・`purpose`（確認内容）・`recommended_checks`（推奨確認方法）・
`risk_weight`（1〜5のリスク重み）・`automation`（automated/semi_automated/manual の3値）・
`standards`（準拠規格タグ）・`tags`・`category` のフィールドを持つ（JSON スキーマを実測）。

## 3. ISTQB テスト技法との対応

`data/viewpoint_templates/common_web.json` の各観点項目には `standards` フィールドに
ISTQB 技法名が付与されているものがある（本書執筆時に grep 相当の全件走査で実測）。
確認できた対応は以下のとおり。

| ISTQB 技法 | 定義 | 本テンプレートでの実例（観点名） |
|---|---|---|
| 同値分割（Equivalence Partitioning） | 入力を有効/無効クラスに分け代表値のみ検証 | 「同値分割による網羅」「選択肢の網羅」（入力フォーム） |
| 境界値分析（Boundary Value Analysis） | 有効/無効の境界値を検証 | 「最大長の境界値」「最小長の境界値」「数値範囲の境界値」（入力フォーム）、「長大な検索語」（検索・絞り込み）、「桁あふれの検知」（データ整合性） |
| デシジョンテーブル（Decision Table Testing） | 条件の組合せ→動作をテーブル化 | 「複合条件の絞り込み」（検索・絞り込み） |
| 状態遷移（State Transition Testing） | 状態×イベントの遷移マトリクスと無効遷移を検証 | 「画面遷移の網羅」「到達不能画面の検知」（画面遷移） |
| ペアワイズ（Pairwise Testing） | 全組合せでなくt因子の組合せ被覆で圧縮 | 「チェックボックスの組合せ」（入力フォーム） |
| ユースケーステスト（Use Case Testing） | 基本/代替/例外フローを網羅 | 「正常フローの完走」（画面遷移） |
| エラー推測（Error Guessing） | 経験に基づき欠陥が起きやすい箇所を推測 | テンプレート上の直接タグはないが、製品機能として `autorun_extended_techniques`（`src/autorun/error_guessing.py`）に実装済み |
| 探索的テスト（Exploratory Testing） | スクリプトなしで探索しながら学習・設計 | `exploration_capture` 機能（セッション記録・チャータ提案）が該当。テンプレート上のタグはないが製品機能として存在 |

`istqb.json` テンプレートは技法ではなくテストレベル（単体/結合/システム/受入）の分類軸で
あり、上記の技法対応表とは直交する（レベル×技法の2軸で観点を整理できる設計）。

## 4. ISO/IEC 25010 品質特性との対応表

`iso25010.json` の8特性それぞれに、`common_web.json` のどの分類が主に対応するかを整理する。

| ISO/IEC 25010 品質特性 | 主対応する共通観点の分類 | 対応する主要機能（`risk_level`） |
|---|---|---|
| 機能適合性 | 入力フォーム、データ整合性、API・連携 | discover/crawl（critical）、doc_fusion（high） |
| 性能効率性 | 性能 | 対象外方針（`docs/TESTING_STRATEGY.md` §3） |
| 互換性 | 互換性 | 全画面共通（Chromium・3解像度のみ実施） |
| 使用性 | 画面表示、アクセシビリティ | ux_review（medium）、L4 UAT 全般 |
| 信頼性 | 画面遷移（一部）、API・連携（タイムアウト系）、データ整合性 | crawl/autorun/diff_history（いずれもcritical/high） |
| セキュリティ | 認証・認可、入力値セキュリティ | account_auth/tenant_isolation/sso_oidc/autorun_security_kernel（すべてcritical） |
| 保守性 | 運用・保守、仕様トレーサビリティ | admin_audit/observability/coverage_gap_report |
| 移植性 | 互換性（環境依存性側面） | 全画面共通（PC専用方針のため対象OS/ブラウザは限定的） |

セキュリティ特性は本製品において最重点領域である。critical 機能 11 件のうち
`account_auth`・`tenant_membership`・`tenant_isolation`・`sso_oidc`・`autorun_security_kernel`
の 5 件（45%）が直接的に認証・認可・情報保護に関わる。

## 5. 観点の適用ルール

観点をどの画面・機能に適用するかは、以下の優先順位で決定する。

1. **機能契約からの決定**: `quality/feature_contracts.yml` の各機能が持つ `required_tests`
   （例: happy_path, error_path, evidence 等）は、本書 §2 の観点カテゴリのうち
   該当する `risk_weight` が高い項目を優先的に適用する。
2. **risk_level による重み付け**: `risk_level: critical`（11件）の機能には、
   認証・認可／入力値セキュリティ／仕様トレーサビリティの高リスク観点（risk_weight 4-5）を
   もれなく適用する。`risk_level: low`（2件）の機能は回帰防止観点（自動化可否: automated）を
   中心に適用し、手動観点の追加は最小限とする。
3. **画面種別による決定**: フォームを持つ画面には「入力フォーム」分類の全項目を、
   一覧・検索画面には「検索・絞り込み」分類を、認証が関わる画面には
   「認証・認可」分類を適用する（`ui_files` フィールドから画面種別を判定）。
4. **横断適用**: 「画面表示」「アクセシビリティ」「互換性」「運用・保守」の各分類は
   機能によらず全画面へ横断的に適用する。
5. **規格別テンプレートの併用**: `pmbok.json` の観点はプロジェクト管理プロセス自体の
   健全性確認に用い、個別機能には直接紐付けない（本書・`WS2D-TP-001`・`WS2D-QA-001` の
   運用状況確認に使用する）。

適用結果は観点管理ビュー（`web/services/viewpoint_store_operations.py` 等、`settings`
機能の `core_files`）を通じてテスト設計（`test_design.py`）に反映される。

## 6. 観点のメンテナンス方針

1. **追加**: 新機能実装時、`quality/feature_contracts.yml` に `required_tests`・
   `failure_modes` を追記すると同時に、該当する観点が `common_web.json` に不足していれば
   観点管理ビューから追加する（`viewpoint_proposals.py` が追加候補を提案する仕組みを持つ）。
2. **改廃**: 陳腐化した観点（対象機能が削除された等）は削除せず、`category`/`tags` を
   見直して汎用化を検討する（テンプレートは複数機能から参照されるため、機能単位の削除は
   他機能への影響評価が必要）。
3. **版数管理**: 現時点でテンプレート JSON 自体にバージョンフィールドは確認できなかった
   （**未確認**。本改訂時点のスキーマ実測では `name`/`description`/`folders` のみを
   確認した）。次回改訂でテンプレートファイルへの版数導入を検討課題とする。
4. **一貫性検査**: `risk_weight` と `automation` の組合せに矛盾がないか
   （例: risk_weight 5 かつ manual のみの項目が多い場合、自動化投資の優先候補として
   洗い出す）を定期的にレビューする。本書 §2 の代表 79 件では risk_weight 5 の項目が
   automated/semi_automated であるものは限定的であり、高リスク観点の自動化率向上が
   今後の課題である。
5. **観点とテストの往復確認**: `WS2D-TM-001` のトレーサビリティ結果を用い、
   観点が実際のテストに反映されているかを定期的に往復確認する。

## 9. 集計: 自動化率とリスク分布（全277件、実測）

`data/viewpoint_templates/*.json` の全277項目を対象に、自動化区分とリスク重みの
分布を集計した（2026-08-02、Python解析による全件走査。捏造なし、実測値）。

| 自動化区分 | 件数 | 比率 |
|---|---|---|
| automated（自動化済み） | 44 | 15.9% |
| semi_automated（半自動） | 63 | 22.7% |
| manual（手動） | 170 | 61.4% |
| 合計 | 277 | 100% |

平均リスク重みは **3.42**（1〜5の5段階評価、277件平均）である。手動確認が61.4%を
占め、特にセキュリティ・認証系（「入力値セキュリティ」「認証・認可」の両分類）は
リスク重み4〜5の項目が多いにもかかわらず自動化率が低い（大半が`manual`）。これは
意図的な設計判断（セキュリティ確認は自動判定の誤検知・誤見逃しリスクが高いため
人手を残す）である可能性があるが、本改訂ではその設計意図の裏付けまでは確認していない
（**未確認**）。自動化投資の優先候補として次回改訂で検討する。

## 10. 規格別テンプレートの実務での使い分け

| テンプレート | 主な利用場面 | 利用者 |
|---|---|---|
| `common_web.json` | 個別機能・個別画面のテスト設計の主軸として利用 | 実装者（L1〜L3設計時） |

いずれのテンプレートも観点管理ビュー（`viewpoints`）から選択・組合せが可能であり、
1つの機能に対して複数テンプレートの観点を同時に適用できる設計になっている。
