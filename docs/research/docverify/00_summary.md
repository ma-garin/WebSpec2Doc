# ドキュメント検証（System 01 docverify）商用化に向けた調査の統合（2026-10-15）

詳細: [A 競合](A_competitors.md) / [B 研究](B_research.md) / [C 規格・プロセス](C_standards.md)。
数値は各ファイルの「引用してはいけない数値」に従う。ここには数値を転記しない。

## 1. 競合が共通して持つもの（無いと商用で比較に乗らない）
- 要件文ごとの曖昧語・弱語の指摘と、該当箇所の提示
- スコアまたは優先度による品質の見える化（QuintSpect は 5 観点）
- カスタム観点・チェックリストのプリセット
- 複数文書間の矛盾検知、要件→設計→テストの追跡と完全率（QuintSpect）
- 採否は人が決める（AI は提案のみ）

## 2. 誰もやっていない空白（確認できた範囲。存在しないことの証明ではない）
1. 検出精度の公開（適合率・再現率・誤検知率）— 6 製品とも確認できず
2. 実画面・実挙動と仕様の突合 — 当製品は match で既に持つ
3. 網羅性（書かれていない要求）の扱い
4. 指摘ごとの根拠（原文引用・規則 ID）と再現可能な判定記録
5. 日本語仕様に特化した規格準拠の検査
6. 規格（IEEE 1028 / ISO/IEC 20246 / ISTQB）に沿ったレビュー工程・役割・メトリクスの管理

## 3. 研究から採る構成
- 検出は決定的なルール（辞書・パターン）で行い、LLM は説明と書き換え案の作成に使う二段構成
- EARS 型の書式パターンからのずれを指摘し、書き換えテンプレートを示す
- 同じ要求を複数回言い換えさせ、結果が揺れた箇所を曖昧さの合図として人に回す
- 矛盾・重複は「確認候補」として出し、確定扱いにしない。網羅性は常に「未検証」と表示する

## 6. 追加調査の反映（2026-10-15・E1〜E5・D〜D3）
| 論点 | 結論 | 出典 |
|---|---|---|
| 精度評価データ | 英語は PURE・ARTA | E1 |
| 日本語の評価データ | 注釈付きの公開は無い | E1 |
| 検出方式 | ルール＋LLM が有効 | E2 |
| 取り込み | docx の多くが未対応 | E3 |
| 商用の非機能 | 送信先開示・監査ログ | E4 |
| 既定しきい値 | IPA 白書の指摘密度 | E5 |
| 形式手法の本 | 用語辞書・DoD に転用 | D〜D3 |

1. 精度の公開（P5）は、英語の PURE・ARTA で先に測定する。日本語は自社で注釈セットを作る必要がある。適合率と再現率は分けて出す（E2: 誤検出は利用者の信頼を下げる）
2. デンソー 2025 も「LLM 単独では不十分で、規則と LLM の組み合わせが有効」としている。P2 の二段構成を維持し、指標は項目別に出す（全体値は項目間の差を隠す）
3. E3 の結果で P1 の前提が崩れた。docx のテキストボックス・ヘッダー/フッター・入れ子の表・文書内の順序と、xlsx の数式セルを読み取れていない（readers.py）。**P1b として、取り込みの修正を P2 より先に行う**
4. E4 の必須 11 項目のうち、送信先の開示・送信前の確認・監査ログ・精度と限界の明記の 4 つが未実装。ローカル LLM（Ollama）を選べることは、QuintSpect（Gemini に送信）との差別化材料になる（需要の大きさは未確認）
5. P4 の既定しきい値は IPA ソフトウェア開発データ白書の値を使う（基本設計の指摘密度は中央値 0.28 件/頁、通常範囲 0.12〜0.76）。書籍の付録C にある DoD 4 項目は、カスタム観点プリセットの初期値にする
