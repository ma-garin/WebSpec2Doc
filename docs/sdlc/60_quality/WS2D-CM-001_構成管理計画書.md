## 1. 構成管理の目的と適用範囲

構成管理（Configuration Management）の目的は、WebSpec2Docの開発・納品において「何がどのバージョンで、どこにあり、誰が・いつ・なぜ変更したか」を常に追跡可能にすることである。具体的には次を保証する。

1. ソースコード・設計文書・テスト資産の対応関係が追跡できる（トレーサビリティ）。
2. 変更が承認プロセスを経て記録される（変更管理）。
3. 任意の時点の「確定版」（ベースライン）を再現できる。
4. ドキュメントとコードの実態が乖離していないことを定期的に検証できる（構成監査）。

適用範囲は、本リポジトリ（`/Users/fujimagariyuki/dev/active/webspec2doc`）で管理される全ての構成品目（§2）とする。対象外は、開発者個人のローカル環境設定（エディタ設定等、リポジトリにコミットされないもの）とする。

本書は `docs/sdlc/README.md` が定める文書体系のうち `60_quality` 区分の新設文書であり、既存の `WS2D-QA-001_品質保証計画書.md`（品質保証のプロセス）とは責務を分ける。品質保証計画書は「何を・どう検証するか」、本書は「何を・どう識別し・どう変更管理するか」を扱う。

## 4. バージョン管理方針

- **ブランチ戦略**: `main`を安定ブランチとし、変更は必ずフィーチャーブランチ（§3.3の命名規則）で行い、GitHub PR経由で`main`へマージする。直接`main`へコミットする運用は`WS2D-RL-001`では想定されていない（実際のログも全てPRマージの形跡）。
- **PRの単位**: 1マイルストーン（1機能・1修正）＝1〜数コミットで1PR、という運用が`docs/DEVELOPMENT.md`§6に明記されている。
- **レビュー・承認要件**: GitHub上でのブランチ保護ルール（必須レビュー人数、必須ステータスチェック等）の設定有無は本書の調査範囲では**未確認**。導入組織の統制要件に応じて設定することを推奨する（要決定）。

- **コミットメッセージ規約**: `feat:` / `fix:` / `refactor:` / `docs:` / `test:` / `chore:` / `perf:` / `ci:`。属性表記（Co-Authored-By等）はグローバル設定で無効化されている。

## 5. 変更管理プロセス

```
起票 → 影響分析 → 承認 → 実装 → 検証 → 記録
```

| 工程 | 内容 | 判断基準・承認者 |
|---|---|---|
| 起票 | 変更の意図をブランチ作成またはIssueで明示する | 起票様式（Issueテンプレート等）の強制は本書時点で未確認。慣行としてブランチ名とコミットメッセージで意図を記録している |
| 影響分析 | `quality/feature_contracts.yml`の`risk_level`（critical/high等）と対象ファイルの種別（UI/Python）を確認し、要求されるゲートを判断する | UIファイル（`.html`/`.js`/`.css`、ただし`docs/*.html`等は除外）を変更した場合は`make verify-ui`が追加で必須になる（`.githooks/pre-commit`のロジック） |
| 承認 | GitHub PR上でのレビュー・マージ操作 | 正式なレビュー必須人数等のルールは未確認（要確認・要決定）。実運用ではPRマージがそのまま承認とみなされている |
| 実装 | フィーチャーブランチ上で実装 | `WS2D-CS-001_コーディング規約.md`に準拠 |
| 検証 | pre-commit hook（自動）＋ マイルストーン単位の`make verify-all`（手動） | `WS2D-RL-001`§2・§3のリリース判定基準を満たすこと |
| 記録 | マージコミット・PR番号・（該当する場合）SDLC文書の改訂履歴表への追記 | 変更が設計文書の内容に影響する場合は、対応する`WS2D-*`文書の改訂履歴も同一PRで更新する |

**変更の承認者・却下基準は、本書時点で正式な文書化がされていない（要決定）。** 少なくとも「PRのマージ可否を判断する者」を導入組織側で明確にすることを推奨する。

## 7. 構成監査

構成監査とは、ドキュメントに書かれた内容と、実際のコード・DB・設定の実態が乖離していないかを定期的に確認する活動である。

- **何を確認するか**: 設計文書（`docs/sdlc/20_design/`, `30_implementation/`）に記述されたAPI・画面・DBスキーマと、実装（`web/routes/*.py`, `templates/`, `docs/sdlc/_asbuilt/schema.sql`）の一致。
- **どう確認するか**: `scripts/extract_asbuilt.py`が実装から機械的に抽出した as-built 情報（`docs/sdlc/_asbuilt/routes.json`＝エンドポイント一覧、`modules.json`＝モジュール一覧、`templates.json`＝画面テンプレート一覧、`schema.sql`＝実際のDBスキーマ、`licenses.json`＝OSSライセンス一覧）を再生成し、設計文書側の記述と突合する。差分があれば、設計文書側の記述漏れか、意図しない実装変更かを切り分ける。
- **いつ確認するか**: マイルストーン区切り、およびリリース判定（`WS2D-RL-001`）の前。四半期に一度は`docs/sdlc/README.md`の実測サマリ（機能契約数、テスト件数、カバレッジ等）を再取得し、記載値を更新する。
- **併用する機械検証（機能契約）**: `python scripts/quality_harness.py` — `quality/feature_contracts.yml`の機能契約（**51件**、2026-08-02 実測）が実装と対応しているかを検証する。
- **併用する機械検証（トレーサビリティ）**: `python scripts/generate_traceability_doc.py --write` — `WS2D-TM-001_トレーサビリティマトリクス.md`を再生成する。
- **併用する機械検証（カバレッジ）**: `make coverage` — テストカバレッジを実測し、`docs/sdlc/README.md`記載の閾値80%との突合を行う。
- **監査結果の記録先**: 現状、構成監査専用の記録様式・記録先は本リポジトリに存在しない（要決定）。当面は各SDLC文書の改訂履歴表に監査実施日と結果を追記する運用を推奨する。

## 8. 依存パッケージの管理

- **ピン留め方針**: `requirements.txt`は大半のパッケージを厳密ピン留め（`==`、例: `flask==3.1.3`, `playwright==1.61.0`, `pytest==9.0.3`）している。例外は`Pillow>=11.0.0`と`numpy>=2.0.0`で、ファイル内コメントに「視覚複雑度の実測（`web/services/visual_complexity.py`）が実行時に使用。E2Eだけでなく本体コードがimportするためruntime依存として宣言する」とあり、意図的に範囲指定にしていることが読み取れる。`requirements-dev.txt`も`ruff==0.6.9` `black==26.3.1` `mypy==1.13.0`等、開発ツールを厳密ピン留めしている。
- **更新手順**: `WS2D-RL-001`§6と同一の手順を正とする。
  1. `make audit`（`pip-audit`によるPython依存の脆弱性確認、およびAutoRunのnpm環境がある場合の`npm audit --audit-level=high`）を実行する。
  2. 脆弱性または更新が必要なパッケージのバージョンを`requirements.txt`/`requirements-dev.txt`で更新する。
  3. `make verify-all`（quality-harness + test + verify-ui）がgreenであることを確認する。
  4. PRを作成し、通常の変更管理プロセス（§5）に従ってマージする。
- **依存追加時の記載規約**: 既存の`requirements.txt`はパッケージ群ごとに日本語コメント（例: `# クローリング`, `# Web UI`, `# SSO（OIDC RP）`）で用途を分類している。新規追加時もこの分類コメントの慣行に従う。
- **新規依存追加の判断基準**: 新しいサードパーティパッケージを追加する場合、ライセンス種別（`docs/sdlc/70_delivery/WS2D-LI-001_OSSライセンス一覧.md`との整合）、メンテナンス状況、既存依存との重複が無いかを確認してから追加する。
- **開発専用パッケージとランタイム依存の分離**: `requirements.txt`（ランタイム依存）と`requirements-dev.txt`（開発・CI用ツール、`-r requirements.txt`を内包）を明確に分け、本番動作に不要なツールを実行時依存に含めない方針を`requirements-dev.txt`のコメントで明示している。
- **バージョン範囲指定（`>=`）を使う場合の条件**: 原則は厳密ピン留めだが、実行時に他のモジュールから直接importされ、かつ上位互換が壊れにくいと判断されるパッケージ（Pillow, numpy）に限り範囲指定を許容する。範囲指定を増やす場合はこの判断基準に照らして都度検討する。

- **リポジトリ外バックアップ**: Gitのリモート（GitHub）自体が実質的なオフサイトバックアップとして機能する。ただし`instance/`・`output/`はGit管理外（生成データ・秘密情報を含むため）であり、これらは別経路のバックアップが必須である。
- **リポジトリのクローン先の一元化**: `CLAUDE.md`が定める正本ディレクトリ以外へのクローン・複製は禁止されており、旧複数コピーは2026-07-03に統合済みである。構成品目の所在を一箇所に保つことも広義の構成管理（保管場所の一元化）の一部である。
- **納品時のアーカイブ**: 発注先への納品物一式（`docs/sdlc/`配下の文書、必要なソースコード一式）をアーカイブとして固定する場合は、`WS2D-OP-001`§9で説明されている完全アーカイブ機構（`MANIFEST.json`によるSHA-256台帳）と同様に、ハッシュ台帳を添えることを推奨する。
- **保管期間**: 納品成果物・バックアップアーカイブの法定・契約上の保管期間は、本書時点で導入組織側の契約条件に依存するため未定義（要決定）。
- **アクセス権限**: 秘密情報を含む`.env`やバックアップアーカイブへのアクセスは、運用管理者等の限定されたロールのみに許可する（`docs/OPERATIONS_BACKUP.md`の方針と同一）。
- **世代管理との違い**: `output/`の保持ポリシー（`WS2D-OP-001`§6、`generations`/`days`モード）は運用中データの古い世代を自動的に間引く仕組みであり、本節で述べる「成果物の保管」（設計文書・リリースアーカイブ）とは目的が異なる。両者を混同しないこと。

## 12. 構成品目のライフサイクル（状態遷移）

構成品目は次の状態を持つ（IEEE 828 構成管理の一般的な考え方を踏襲した本書独自の整理であり、本リポジトリ内で明文化された正式なワークフローツールがあるわけではない）。

| 状態 | 意味 | 本リポジトリでの対応 |
|---|---|---|
| 作業中（Draft） | フィーチャーブランチ上で編集中 | ブランチにコミットされているがPR未作成、またはPRレビュー中 |
| レビュー中（In Review） | PRが作成されレビュー待ち | GitHub PRのOpen状態 |
| 承認済み（Approved） | PRがマージされた | `main`へのマージコミット |
| 却下（Rejected） | レビューで却下された | PRがCloseされ`main`にマージされない |
| ベースライン化（Baselined） | §6のタイミングでベースラインとして記録された | 現状は明示的なマーキング手段が無い（タグ未導入、§3.2参照）。将来導入する場合はGitタグに対応させる |
| 廃止（Retired） | 削除・置き換えられた | Git履歴上に残るが`main`の現行状態からは除去済み（例: 2026-07-03の旧設計ドキュメント削除） |

状態遷移を機械的に強制する仕組み（ワークフローエンジン等）は本リポジトリには無く、GitのブランチとPRの状態がそのまま構成品目の状態を表している。

## 14. 命名規則違反時の扱い

ブランチ名・コミットメッセージ・文書IDが§3の識別体系に沿っていない場合の扱いを次に示す。

- ブランチ名が`<ユーザー名>/<種別>/<内容>`の形式に沿っていない場合、PRレビュー時に指摘し、マージ前に是正することを推奨する（強制チェックの仕組みは本書調査範囲では未確認）。
- コミットメッセージの種別プレフィックス（`feat:`等）が無い場合も同様にレビュー指摘で運用する。
- 文書IDが`WS2D-{種別}-{連番}`の形式から外れる場合、または既存プレフィックスと衝突する場合は、本書§3.1の一覧に照らして新規プレフィックスの妥当性を確認してから採番する。
- 命名規則違反を機械的に検出するツール（コミットフック等）は、pre-commit hookの現行実装（`.githooks/pre-commit`）には含まれていない。導入する場合は`.githooks/pre-commit`への追加を検討する（要決定）。
- コミットメッセージ・ブランチ名の是正はレビューコメントで指摘するに留め、既にマージ済みの履歴を書き換える（`git rebase`等の履歴改変）ことは、共有ブランチである`main`に対しては行わない。
- 文書IDの連番が枝番号（例: `-050`, `-051`）を取る運用は`40_test`区分で既に存在する（§3.1参照）ため、同一プレフィックス内で複数文書を作る場合はこの前例に倣うことができる。

| 違反例 | 是正例 |
|---|---|
| `fix-login`（種別プレフィックス無し） | `ma-garin/fix/login-flow-order` |
| `update stuff`（コミットメッセージが種別・内容とも不明瞭） | `fix: ログイン後の遷移順序を修正する` |
| `WS2D-XX-001`（未定義の種別コード） | 既存一覧（§3.1）を確認し妥当なコードを新規採番、または既存コードを再利用 |

| 構成監査（Configuration Audit） | §7 |
