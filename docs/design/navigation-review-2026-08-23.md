# ナビゲーション設計の精査（2026-08-23）

局所修正を積み重ねた結果、設計原則の無いナビになった。外部基準・実製品・実装監査の
3 方向から精査し、何を捨て何を残すかを判定する。

照合した外部基準: Material Design 3 (Google 実装ドキュメント) / W3C WAI Menu Structure・
ARIA APG / Nielsen Norman Group / Azure DevOps・Jira・Datadog・GitHub Primer・
PatternFly・TestRail の公開ドキュメント。

---

## 1. 判定サマリ

| 現行の判断 | 判定 | 根拠 |
|---|---|---|
| 縦レール（親カテゴリの色面）を置く | **捨てる** | 3 システムの分類に 1 カラムは過剰。PatternFly「縦ナビは主要 5 項目以上から」。Datadog がカテゴリ分割したのは 20 製品規模。Azure DevOps は上部セレクタ＋単一リスト |
| 工程順（計画→…→完了）をナビに並べる | **捨てる** | テスト管理製品は例外なく成果物で切る（TestRail: Cases/Runs/Milestones）。工程順を並べた製品は調査範囲でゼロ。NN/g は順序処理をフロー内ステッパーで示せとする |
| 2 階層のフライアウト/パネル | **捨てる** | PatternFly が明示的に非推奨（多段フライアウトはマウス操作が困難） |
| `role="tablist"/"tab"` | **捨てる** | W3C の Tabs は同一ページ内の切替が定義。ページ遷移するナビは `nav`+`ul`/`li`+リンク、現在地は `aria-current="page"` |
| ダッシュボードを単独入口に | **残す** | 重複解消として妥当。ただしレール廃止後は自明になる |
| 工程の可視化そのもの | **残す（置き場を移す）** | ダッシュボードのステッパーへ一本化。NN/g のウィザード指針に合致 |

**否定された通説**（私が根拠にしかけていたもの）:
NN/g は「3クリック以内」も「トップ 7 項目以内」も研究に支持されないと明言。
離脱を左右するのはクリック数ではなく **information scent（項目名の手がかり）と現在地の明示**。
→ 「階層を浅くする」ことは目的にならない。**名前と現在地**が要件。

## 2. 実装監査で判明した破綻

### 実害（利用者に見える）
1. **`/run-history` `/settings` は系を判定できず保存値依存** → 直リンクで系が変わる。
   さらに `data-view` を持つナビ項目が無いためカテゴリが解決できず、
   **レールのハイライトが無関係なカテゴリを指す**（コード読解・実画面未検証）
2. **パンくず 1 段目が 3 通り**（WebSpec2Doc / ダッシュボード / テスト活動支援）。
   かつ root クリックは常に `switchView('dashboard')` = testlab から押すと docs へ出る（系跨ぎ）
3. **同一画面に最大 4 通りの呼称**。URL と表示名が体系ごとズレる
   （`/test-design`＝テストケース実装、`/test-strategy`＝テスト詳細設計、
   `/test-analysis`＝テスト基本設計、`/test-implementation`＝自動テストケース実装）

### 構造負債
- **1 画面の追加に 6 ファイルの修正が必要**（nav.html / VIEW_PATHS / VIEW_HEADER /
  system-scope の PATH 表 / Flask ルート / view partial）。今回これを 3 回落として実際にバグを出した
- **可視性ルールが二系統**（`system-scope.js` のインライン style と CSS の `:not([data-cat-open])`）。
  インラインが常に勝つため、片方だけ見ても表示可否が決まらない
- **文字列一致による分岐**（solo 判定はカテゴリ名と子ラベルの一致で決める＝文言変更で壊れる）
- **デッドコード**: `.ta2-sep` は「JS が挿す」とコメントされているが挿入コードが無い。
  `app-nav-group` は CSS で全消しなのに畳む処理が動き続けている（10 行）

### アクセシビリティ
- `role="tablist"/"tab"` を名乗るが `aria-controls`・矢印キー・roving tabindex・`tabpanel` すべて無し。
  **支援技術に「矢印で動く」と告知して実際は動かない**
- `.app-nav-item` に `aria-current` が無い（`is-active` クラスのみ）。
  同一アプリ内の他コンポーネントは `aria-current` を使っており規約が割れている
- カテゴリ切替が `aria-live` 無しで読み上げられない
- rail の `title="品質観点"` と可視ラベル「観点」が不一致

## 3. 立て直す設計原則

個々の判断はこの 4 つから導出する。以後、原則に反する要望が来たら原則ごと見直す。

1. **ナビは「物の置き場」であり「時間の順路」ではない。**
   工程の順序はダッシュボードのステッパーが持つ。ナビは成果物・機能で切る
2. **1 システムのナビは 1 列。** 系の切替は上部セレクタ（Azure DevOps 型）。
   選択中の系の画面だけを出す
3. **画面の定義は 1 箇所（レジストリ）に置き、nav・パス・パンくず・系判定をそこから導出する。**
   同じ画面を 2 箇所で名乗らせない
4. **名前は 1 画面 1 つ。** ナビ・パンくず・見出し・URL を一致させる。
   URL を見て画面が特定できること

## 4. 改修案（段階）

### Phase 1: レール撤去と 1 列復帰（本命・破壊的）
- レール・パネル見出し・カテゴリ機構を削除（`nav-two-level.*`、`.ta2-*`）
- サイドバーを 1 列に戻し、系の切替は既存の上部セレクタに一本化
- テスト活動支援の 12 画面は**成果物でグループ化**して 1 列に並べる:
  計画 / 設計（基本・詳細・ケース） / 実行（自動実装・自動実行・手動実行） /
  分析（不具合・修正提案） / 完了 / 連携設定
  → グループ見出しは `app-nav-group` を復活させて使う（フライアウトにしない）
- 工程の順路はダッシュボードのステッパーに一本化（既に実装済み・クリックで移動可）

### Phase 2: 画面レジストリ（構造負債の解消）
- `screens.py`（または JSON）に view 名・ラベル・パス・系・グループを 1 行で宣言
- nav.html / VIEW_PATHS / VIEW_HEADER / system-scope の PATH 表 / Flask ルートを**そこから生成**
- 1 画面の追加を 1 箇所の修正にする

### Phase 3: 命名とアクセシビリティの是正
- URL を表示名に合わせて改称（`/test-analysis` → `/test-basic-design` 等）＋旧 URL からのリダイレクト
- パンくず 1 段目を系トップに統一し、root クリックの系跨ぎを修正
- `role="tablist"` を外し `nav`+`ul`/`li`+`aria-current="page"` へ

---

## 5. 反証と留保

- **レール＋パネルで成功している実例（VS Code のアクティビティバー、Notion のサイドバー）を
  調査で 1 件も当たっていない。**結論は否定側の資料に偏っている。
  ただし VS Code は「1 アプリ内の機能領域が 5 以上」であり、3 システムの本件とは規模が違う
- テスト管理製品の一次確認は TestRail 1 件・検索スニペット経由のみ。含意の根拠は薄い
- NN/g の階層論は定性観察であり、効果量を伴う実験ではない。数値目標の根拠には使えない
- 監査の「6 ファイル」は Flask ルートと view partial が推定。4 箇所は実読で確定
- 「レールのハイライトずれ」はコード読解による指摘で、実画面では未検証
