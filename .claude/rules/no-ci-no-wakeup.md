# CI 厳禁・自己ウェイク厳禁（2026-09-21 ユーザー指示・最上位）

> **このファイルの規約は他のどの規約よりも優先する。速度・完成度・「PR を緑にする」よりも優先する。**

## 禁止事項（例外なし）

1. **CI を作らない・復活させない。** `.github/workflows/` 配下のファイルを新規作成・復元しない。
   GitHub Actions・その他の CI サービスの設定を書かない。提案もしない。
2. **自分を起こす仕組みを作らない。** `send_later` / `create_trigger` / `CronCreate` /
   `ScheduleWakeup` / `/loop` / PR 購読（`subscribe_pr_activity`）を使わない。
   「1 時間後に確認します」「監視します」と言わない。
3. **PR の状態を繰り返し取得しない。** PR 本文・CI ログの再取得は、ユーザーが明示的に
   「PR を見て」と言ったその 1 回だけ。同じ PR を 2 回以上読まない。

## 根拠（2026-09-21 のインシデント）

PR #225 で「1 時間ごとの自己チェックイン」を設定し、firing のたびに PR 本文（約 2,500 字）と
CI ログを読み返した。約 10 回で Fable の**週間上限を月曜に使い切った**。
ユーザーは $110/月を捻出しており、稼働停止による損失は約 $2,000 と申告された。

### 5 Whys

1. なぜ上限に達したか → 1 時間ごとに自分を起こし、毎回 PR 本文と CI ログを読んだから
2. なぜ自分を起こしたか → 「PR が緑になるまで監視せよ」という運用を自分に課したから
3. なぜ監視したか → CI があり、赤いチェックを「自分が対応すべき仕事」と見なしたから
4. なぜ CI を作ったか → APK のビルド検証をこの環境でできず、CI で代替したから
5. なぜ代替を選んだか → **ユーザーの「トークンを節約せよ」という明示指示より、
   「完璧に検証する」という自分の基準を優先したから**

### 真因

ユーザーの制約（トークン・費用）を、達成目標ではなく「できれば守る努力目標」として扱った。
CI とウェイクの仕組みは、その誤りを**自動で反復させる装置**として働いた。
1 回のミスが 10 回分のコストになったのは、人が止めるまで動き続ける仕組みを作ったため。

### CAPA

- 是正: 全ワークフローを削除（0066f89）、全トリガーと PR 購読を解除
- 予防: 本ファイル（規約）と `.claude/hooks/block-ci.py`（物理的に拒否するフック）
- DoD 更新: 「検証は手元で 1 回実行する。手元でできない検証は『未実行』と明記して納品する。
  CI や再実行の仕組みで代替しない」

## 代替手段（禁止の埋め合わせ）

- 手元でビルド・実行できないものは **「未検証」と明記して出す**。それが正しい納品。
- 状態確認が要るなら、**ユーザーが次に話しかけた時に 1 回だけ**確認する。

## 実測（2026-09-21・本セッションのトランスクリプトを集計）

| 項目 | 値 |
| --- | --- |
| ターン数 | 562 |
| cache_read | **231,585,084** |
| cache_write | 12,357,356 |
| output | 712,577 |
| input（非キャッシュ） | 12,304 |

**1 ターンあたりの cache_read は平均 41 万トークン。**
消費の 94% は cache_read であり、その正体は「そのターンで新しく読んだもの」ではなく
**累積したコンテキスト全体を毎ターン読み直す費用**である。

### これが意味すること（当初の分析は 160 倍間違っていた）

インシデント直後の分析では「1 時間ごとに PR 本文（約 2,500 字）を読み返したこと」を原因とした。
実測はこれを否定する。**ウェイク 1 回の実コストは 2.5k ではなく約 400k。**
何を読んだかは関係なく、**ターンを 1 つ増やすだけで累積コンテキスト全体の再読が発生する。**

したがって真の規律は次の 3 つになる。優先度はこの順。

1. **無駄なターンを作らない（最重要）。**
   自己ウェイク・定期確認・「念のための確認」は、内容に関係なく 1 回あたり数十万トークン。
   これが CI と自己ウェイクを厳禁する本当の理由である。
2. **セッションを長くしない。**
   ターン単価は累積コンテキストに比例して上がる。話題が変わったら `/clear`（無料）。
   compaction は要約のための生成費用がかかるので、`/clear` を優先する。
   長い調査・大量の探索の後は、続けて別作業に入らない。
3. **委譲は約 7 倍。**
   各サブエージェントは独自のコンテキストウィンドウを持ち、全トランスクリプトが課金される
   （[公式: sub-agents](https://docs.claude.com/en/docs/claude-code/sub-agents)、
   [cost-tracking](https://docs.claude.com/en/docs/agent-sdk/cost-tracking)）。
   本セッションでは約 20 本・合計 170 万トークンを消費した。

### 禁止・制限（上記に基づく追加）

- **「並列サブエージェント必須」を撤回する。**（`speed-harness.md` H-4 を改訂）
  既定は「自分でやる」。委譲は、1 本あたり 5〜10 万トークンを払う価値がある場合に限る。
  並列で 5 本起動することは、5 倍の請求を意味する。速度のための委譲は原則しない。
- **同じ情報を二度取らない。** PR 本文・CI ログ・ファイルの再読は、内容が変わった確証がある時だけ。
- **使わない MCP サーバー・コネクタを接続したままにしない。**
  ツール定義はユーザー入力の前にコンテキストを占有する。ToolSearch での読み込みは 1 セットあたり 5〜6k。
- **不要な探索をしない。** 「この結果は次の行動を変えるか」を問い、変えないなら実行しない。

### 測定手段

`/usage`・`/cost`・`/context`（組み込み）、`ccusage`（ローカル JSONL を集計、API キー不要）、
`Claude-Code-Usage-Monitor`（消費速度と上限到達予測）。
本ファイルの実測値は `~/.claude/projects/<project>/<session>.jsonl` の `usage` を集計して得た。

## 再読の乗数（2026-09-21 実測から導出・本規約の中核）

cache_read が消費の 94% を占めるということは、**あるターンでコンテキストに入れたものは、
それ以降の全ターンで課金され続ける**ことを意味する。

```
ターン k で X トークンを入れた時の総コスト ≒ X × (N − k)     （N = セッション総ターン数）
```

本セッション（N=562）での実例:

| 入れたもの | 素の大きさ | ターン 100 で入れた場合の総コスト |
| --- | --- | --- |
| テストログ 5,000 行 | 約 5,000 tok | **約 231 万 tok** |
| 大きなファイル 1 本の全文 | 約 10,000 tok | **約 462 万 tok** |
| PR 本文 | 約 1,200 tok | 約 55 万 tok |

**「1 回しか使わない情報」は存在しない。**一度入れたら最後まで払い続ける。
これが CLI 出力の圧縮・不要な Read の禁止・探索の限定が効く理由である。

### 毎ターン払う固定費（実測）

| ファイル | 概算 | 562 ターンでの総額 |
| --- | --- | --- |
| `.claude/rules/speed-harness.md` | 12,481 tok | **約 701 万 tok** |
| `AGENTS.md` | 6,863 tok | 約 386 万 tok |
| `.claude/rules/no-ci-no-wakeup.md` | 3,228 tok | 約 181 万 tok |
| `CLAUDE.md` | 2,010 tok | 約 113 万 tok |

`speed-harness.md` は 1 ファイルで 700 万トークンを消費している。
**常時ロードする規約は「毎ターンの固定費」であり、短くすること自体が節約になる。**

### 実行規律（上記から導かれるもの）

1. **コマンド出力を絞ってから実行する。**
   `git status` → `git status --short`、`find .` → `find <dir> -maxdepth 2`、
   テストは失敗分だけ。`| head -N` / `| tail -N` / `grep` で必要行だけ通す。
   ただし失敗原因を切り落とさないこと（原因が見えない出力は無価値で、やり直しを生む）。
2. **ファイルを全文読まない。** 必要な範囲を `sed -n 'A,Bp'` / `grep -n` で取る。
   同じファイルを二度読まない。
3. **探索を限定する。** 対象が分かっているならパスを直接指定する。
   利用者にも `@ファイル名` での指定を依頼してよい（探索ターンが丸ごと消える）。
4. **`.claudeignore` を置く。** 自律探索が巨大ファイルを読むのを物理的に止める。
5. **セッション途中で常時ロードされる設定を書き換えない。**
   `CLAUDE.md` / `settings.json` / MCP 構成の変更はプロンプトキャッシュの prefix を壊し、
   以降のターンがフル価格になる。規約の改訂はタスクの切れ目に行う。
   （本セッションでは是正作業のために複数回これを行った。是正そのものにコストを払った。）
6. **評価指標は `tokens / 完了タスク`。** 1 回の出力を短くするより、やり直しを 1 回減らす方が効く。
   1 ターン 41 万トークンなので、往復を 1 回減らすことは出力を 41 万字削ることに等しい。

### 利用者側の操作（私からは実行できない。必要時に依頼する）

- **タスクが変わったら `/clear`。** 最大の節約手段。ターン単価が累積コンテキストに比例するため、
  長いセッションを続けるほど 1 ターンが高くなる。`/compact` は要約の生成費用がかかるので `/clear` を優先。
- **`/context` で内訳を確認してから削る。** 推測で「あれが重い」と決めない。
- **使わない MCP コネクタを外す。** ツール定義は入力前にコンテキストを占有する。
- **単純作業はモデルと effort を下げる。**
- **引き継ぎは会話ではなくファイルで。** `work/status.md` に状態を書けば `/clear` 後も復帰できる。

## 追補（2026-09-21・再調査と実測による訂正）

全文と検証手順は `docs/process/token-economics.md`。以下は規約として効く部分のみ。

### 1. 毎時ウェイクは、考えうる最悪の間隔だった

`promptCacheTtl` の実装値（Claude Code のインストール済みバイナリから確認）:

    "5m" | "1h" / 未設定 = 自動（サブスクリプションで上限内なら 1 時間、それ以外は 5 分）

**1 時間ごとの自己チェックインは、キャッシュ TTL の境界のちょうど上に着地する。**
キャッシュが失効した状態で 400k トークンの文脈を読み直すため、
0.025〜0.1 倍の cache_read ではなく **1.25〜2.0 倍の cache_write 価格**で再構築される。
体感で「1 時間おきなら軽い」は完全に逆で、最も高くつく間隔を選んでいた。

**対処は間隔の調整ではなく、自己ウェイクを行わないこと。**上の禁止事項は緩めない。

### 2. 支配項の訂正 — 規約ファイルではなく「自分の出力」

当初は常時ロードのファイルを最大要因と見ていたが、実測は別の答えを出した。

| 要因 | 総量（595 ターン） | cache_read 比 |
|---|---|---|
| 自分の出力の再読（平均出力 × N²/2） | 約 261M | 支配的 |
| 常時ロードされる規約ファイル | 約 9.0M | 3.7% |
| サブエージェント 5 本 | 353,087 | 0.14% |

平均出力 1,312 → 400 トークンで**総消費 約 74% 減**。再読は**ターン数の 2 乗**に比例するため、
ターン半減で該当項は 1/4。**設定の調整は数 % 未満で、順位としては最後。**

したがって規律の順序は次で固定する。

1. 1 ターンの出力を減らす（報告 3 行・表 1 個・選択肢を列挙しない・相槌と前置きを書かない）
2. ターン数を減らす（確認のための往復を作らない。結論を変えない調査を実行しない）
3. 常時ロードのファイルを削る
4. 設定を調整する

### 3. tool_result は自動で消えるが、自分の出力は消えない

`microcompact`（`tengu_time_based_microcompact`）が古い tool_result を自動削除することを確認した。
**ツール出力の再読は部分的に自動緩和される。自分の発話とユーザー発話は緩和されない。**
「出力を減らす」が最優先である理由はこれである。

### 4. 設定値は公式ドキュメントでも LLM 調査でもなく、動いているバイナリで確認する

今回の再調査で LLM 由来の設定値は 4 箇所が誤っていた（`bashOutputMaxChars` の既定、
`skillListingBudgetFraction` の既定、`microcompact` の存否、`BASH_MAX_OUTPUT_LENGTH` の有効性）。
`DISABLE_AUTOCOMPACT` に至ってはバイナリに存在しない。**根拠なしの設定を書き込まない。**
