# トークン消費の実測と設計則（2026-09-21）

INC-2026-002（Fable 週次上限の枯渇）の再発防止のため、推測ではなく**実測**で
消費構造を特定し、Claude Code の**インストール済みバイナリから設定を直接検証**した。
LLM 由来の調査は 4 箇所が誤っていた（§4）。本書は検証済みの値だけを残す。

## 1. 実測（対象セッション 1 本・595 ターン）

計測対象: `~/.claude/projects/-home-user-WebSpec2Doc/<session>.jsonl` の `message.usage`。

| 項目 | 実測値 |
|---|---|
| ターン数 | 595 |
| cache_read | 244,719,225 |
| cache_write | 12,540,688 |
| output | 780,758 |
| input（非キャッシュ） | 12,370 |
| cache_read / ターン 平均 | 411,292（最大 775,312） |
| output / ターン 平均 | 1,312（最大 13,511） |

**cache_read が全消費の 95% を占める。**単発の巨大入力ではなく、
同じ内容を毎ターン読み直していることが消費の本体である。

## 2. 支配項の特定 — 自分の出力が全体を決める

自分の出力は転写（transcript）に残り、**以後の全ターンで再読される**。
ターン k に X トークン出力すると、以後 (N−k) 回読み直される。

    再読総量 ≒ Σ_k (それまでの累積出力) ≒ 平均出力 × N² / 2

実測値を入れると **261,005,783 トークン**。これは cache_read 実測の **107%** に相当する
（近似が 100% を超えるのは、microcompact による tool_result の自動削除と
thinking トークンを output に含めているため。順序は変わらない）。

**結論: cache_read の実質すべてが「自分の過去の出力の読み直し」である。**

内訳の比較（同セッション）:

| 要因 | 総量 | cache_read 比 |
|---|---|---|
| 自分の出力の再読 | 約 261M | 支配的 |
| 常時ロードされる規約ファイル | 約 9.0M | 3.7% |
| サブエージェント 5 本（今回の調査） | 353,087 | 0.14% |

### ここから導かれる唯一の優先順位

1. **1 ターンあたりの出力を減らす。**平均 1,312 → 400 トークンで**総消費 約 74% 減**。
2. **ターン数を減らす。**再読は N² に比例するため、ターン半減で該当項は 1/4。
3. 常時ロードのファイルを減らす（効果 3.7% 相当・やる価値はあるが 1・2 の後）。
4. 設定の調整（数 % 未満）。

説明・要約・進捗報告・相槌・選択肢の列挙は、**すべてこの N² の項に乗る。**
「丁寧な説明」の代金は、その場の出力ではなく残りセッション全体で払う。

## 3. キャッシュ TTL とウェイクアップの関係（INC-2026-002 の真因）

`promptCacheTtl` の実装値（バイナリから確認）:

    "5m" | "1h" / 未設定 = 自動（サブスクリプションで上限内なら 1 時間、それ以外は 5 分）

**1 時間ごとの自己チェックインは、TTL 境界のちょうど上に着地する。**
キャッシュが切れた状態で 400k トークンの文脈を読み直すため、
0.025〜0.1 倍の cache_read ではなく **1.25〜2.0 倍の cache_write 価格**で再構築される。
つまり毎時ウェイクは、考えうる最悪の間隔だった。

再発防止は「間隔を調整する」ではなく「**自己ウェイクを行わない**」。
詳細は `.claude/rules/no-ci-no-wakeup.md`。

## 4. LLM 由来の調査で誤っていた点（バイナリ実測で訂正）

| 主張 | 出所 | 実測 |
|---|---|---|
| `bashOutputMaxChars` の既定は 4096 | LLM 調査 | **30000**（4000〜128000 にクランプ） |
| `skillListingBudgetFraction` の既定は 0.04 | LLM 調査 | **0.01**（× 200000 字 = 2000 字） |
| `microcompact` は存在しないかも | LLM 調査 | **存在する**（`tengu_time_based_microcompact`・古い tool_result を自動削除） |
| `BASH_MAX_OUTPUT_LENGTH` で出力上限を変えられる | LLM 調査 | **非推奨・効果なし**。`bashOutputMaxChars` が後継 |
| `DISABLE_AUTOCOMPACT` が使える | LLM 調査 | インストール済みバイナリに**存在しない** |

**教訓: 設定値は公式ドキュメントでも LLM 調査でもなく、動いているバイナリで確認する。**

## 5. 検証済みの設定（インストール済み CLI に実在を確認）

| キー | 種別 | 既定 | 効果 |
|---|---|---|---|
| `bashOutputMaxChars` | settings.json | 30000 | 超過分はファイルへ退避。文脈に入る量の上限 |
| `promptCacheTtl` | settings.json | 自動 | `"5m"` / `"1h"`。§3 参照 |
| `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` | env | 30 | `0` で待機中の自動チェックインを停止 |
| `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | env | モデル依存 | 自動要約の閾値 |
| `skillListingMaxDescChars` | settings.json | 1536 | スキル一覧の 1 件あたり上限 |
| `skillListingBudgetFraction` | settings.json | 0.01 | スキル一覧全体の文脈予算 |
| `MAX_THINKING_TOKENS` | env | モデル依存 | thinking は output 課金かつ**文脈に残る**（Opus 4.5+ / Fable 5.1） |
| `MAX_MCP_OUTPUT_TOKENS` | env | — | MCP ツール出力の上限 |
| `ENABLE_TOOL_SEARCH` | env | — | MCP ツール定義の遅延ロード |
| `cleanupPeriodDays` | settings.json | 30 | 転写の保持期間（ディスクのみ・トークンには無関係） |

存在しない: `DISABLE_AUTOCOMPACT`。非推奨: `BASH_MAX_OUTPUT_LENGTH`・`taskOutputMaxChars`。

### 採用した設定と、採用しなかった理由

採用: `CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0`（待機中の自動チェックインを止める・
インシデントの直接要因と同種）、`bashOutputMaxChars: 12000`（超過分はファイルに残るため
情報は失われない）。

不採用: `promptCacheTtl` の固定。**1h は cache_write が 2.0 倍、5m は 1.25 倍**で、
どちらが有利かは作業の間隔分布で決まる。実測せずに固定するのは
INC-2026-002 と同じ「根拠なしの設定」になるため、自動のままとした。
決めるなら、ターン間隔の中央値が 5 分を超えるかを先に計測すること。

## 6. 価格の倍率（公式ドキュメント・参考値）

- cache_read: 標準 0.1x / **Fable 5.1・Mythos 5.1 は 0.025x**
- cache_write: 5 分 TTL 1.25x / 1 時間 TTL 2.0x
- キャッシュ済みでも**文脈ウィンドウは消費する**（課金が変わるだけで消費は変わらない）
- thinking ブロックは Opus 4.5+ / Sonnet 4.6+ / Fable 5.1 で**次ターン以降も保持され入力に乗る**

https://platform.claude.com/docs/en/build-with-claude/context-windows

## 7. サブエージェントの損得（実測）

今回の調査 5 本の実測: 58,315 / 75,829 / 90,140 / 56,855 / 71,948 = **合計 353,087 トークン**、
生成物は 27,500 バイト（約 13,750 トークン）。**25.7 倍**のオーバーヘッド。

一方、同じ調査を自分の文脈で行えば、取得した Web 内容（約 150k トークン相当）が
残り (N−k) ターン再読される。損益分岐は概ね次のとおり。

    委譲が得 ⟺ (自分の文脈に載る量) × (残りターン数) > サブエージェントの総消費

- **セッション序盤で大量の外部情報を取り込む調査 → 委譲が得。**
- **終盤、または取り込み量が 10k トークン未満 → 自分でやるほうが安い。**

`.claude/rules/speed-harness.md` の旧 H-4「複数並列起動を必須」は、この損益を
見ていなかったため撤回済み。既定は「自分でやる」。

## 8. 再現手順（この文書の数字を自分で検証する）

```bash
python3 scripts/token_report.py             # 最新セッションの消費構造
python3 scripts/token_report.py --all       # 対象セッションの一覧
python3 scripts/selftest/test_block_ci.py   # CI 厳禁フックの動作検証（52 件）
```

依存なし・ネットワーク不要・API キー不要。**規約の文章ではなく、この出力で判断すること。**
INC-2026-002 の原因分析は 1 回目が 160 倍、2 回目が支配項の取り違えで外れた。
どちらも推測で語ったためである。

`scripts/selftest/test_block_ci.py` 実測（2026-09-21）: **PASS 52 件**
（拒否 20 種 × プロジェクト/ホーム 2 箇所、許可 6 種 × 2 箇所）。
設定変更後もフックが生きていることを、この実行で確認している。

なお本テストは**シェルのヒアドキュメントでは書き出せない**。
ワークフローパスの文字列を含むため block-ci.py が拒否する。これも装置が働いている証拠である。

## 9. 常時可視化（ターンを消費せずに見る）

`.claude/hooks/statusline.py` が転写 JSONL を**差分読み**して、累計消費・1 ターンあたり
平均出力・ターン数をステータスラインに常時表示する。平均出力が 800 トークンを超えると `⚠`。

    ⚠ Σ265.9M 出力1,334/t 647t ｜ WebSpec2Doc

**私に消費を尋ねること自体がターンを 1 つ増やし、1 回あたり約 40 万トークンかかる。**
だから消費は、問い合わせずに見えていなければならない。

実測: 14MB の JSONL に対し初回 111ms、以降は差分のみで 53ms。状態は
`~/.claude/.token_state.json`（リポジトリ外）。空入力・壊れた JSON・存在しないパスは
すべて従来表示へフォールバックすることを確認済み。
