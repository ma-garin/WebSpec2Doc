1. 要件→テスト生成の LLM 研究は 2024〜2026 に急増したが、評価は小規模（n=数十〜百程度）で、産業データでは再現率が大きく落ちる（Bluetooth 0.81 に対し Mozilla 0.37）。精度は要件の書き方に依存する。

- Guo, Li, Tsuchiya／2025／arXiv 2501.14465「Boundary Value Test Input Generation Using Prompt Engineering with LLMs」。ホワイトボックスの境界値入力を LLM で生成し、従来の境界値分析と故障検出・カバレッジを比較。数値は abstract に無い。区分=主張。https://arxiv.org/abs/2501.14465
- Akbarova, Dobslaw, Feldt／2026／arXiv 2608.28230「Adaptive Strategy Generation for Boundary Value Exploration Beyond Numeric Inputs (ABEX)」。エージェント型 LLM が境界探索戦略を生成。20 関数のうち数値 11 関数中 10 で QD 手法に勝り、mutation score は 86.2% 対 61.9%。コード入力が対象で要件文書ではない。区分=実証（本文未確認）。https://arxiv.org/abs/2608.28230
- Siddeeq ほか／2026／arXiv 2607.01980「Epic-Organized vs. Requirement-Aligned Gherkin: LLM-Based Acceptance Criteria Generation」。PURE 4 文書の要件 107 件で比較。epic 単位の手法（Timeless）は意味的カバレッジ 94.3%（素朴なベースライン 92.9%）、専門家評価の正確性 4.61 対 4.14。差は小さい。区分=実証（本文未確認）。https://arxiv.org/abs/2607.01980

- Wang, Arora ほか／2025／arXiv 2508.06888「Multi-Modal Requirements Data-based Acceptance Criteria Generation (RAGcceptance M2RE)」。テキスト＋UI 画像の RAG で受入基準を生成。約 10 万ユーザーの教育システムで産業ケーススタディ。マルチモーダルで関連性・正確性・理解容易性が向上と記述。数値は abstract に無い。区分=主張。https://arxiv.org/abs/2508.06888
- Gupte, Ramesh／2025／arXiv 2511.11829「Towards Autoformalization of LLM-generated Outputs for Requirement Verification」。生成した Gherkin が自然言語要件と論理的に整合するかを形式化で検査。小実験 2 件のみで定量なし。区分=主張。https://arxiv.org/abs/2511.11829
- Yang ほか／2025／arXiv 2512.06401「LLMCFG-TGen」。ユースケースから LLM が制御フローグラフを作り、そこからテストパスとテストケースを導出。6 データセットで 2 ベースラインより網羅性・構造整合性が高いと記述。数値は abstract に無い。区分=主張。https://arxiv.org/abs/2512.06401
- Alagarsamy ほか／2024／arXiv 2402.11910「Enhancing LLMs for Text-to-Testcase Generation」。GPT-3.5 を微調整し要件からテストを生成。OSS 5 件、約 7k テストで構文正確性 78.5%、要件整合 67.09%、コードカバレッジ 61.7%。要件整合が 1/3 外れる点が重要。区分=実証。https://arxiv.org/abs/2402.11910
- Moradi ほか／2026／arXiv 2604.06946「LoRA-based fine-tuning for automated test case generation」。要件ベースのテスト生成で LoRA を比較。GPT-4o が 9 品質次元で採点。Ministral-8B が OSS 最良で、微調整済み 8B が微調整前の GPT-4.1 と同等。採点者が LLM である点に注意。区分=実証（LLM 採点）。https://arxiv.org/abs/2604.06946
- Xue ほか／2026／arXiv 2601.09762「RAFT: Auto-Formalize Requirements for Compliance Test Case Generation」。複数 LLM から暗黙の規制知識を抽出し、形式要件と testability 制約を生成。金融・自動車・電力で先行手法を上回ると記述。数値は abstract に無い。区分=主張。https://arxiv.org/abs/2601.09762
- Abboush ほか／2025／arXiv 2511.19132。機能安全要件から故障注入テストケースを生成。要件分類 F1 88%、故障テスト生成 F1 97.5%（gpt-4o）。自動車領域で一般化は不明。区分=実証（領域限定）。https://arxiv.org/abs/2511.19132
- He ほか／2026／arXiv 2602.13611「From What to How (DesBench)」。Java 30 プロジェクト、受入テスト 737 件で LLM 7 種を評価。LLM の生成した受入テストは人手と同等のカバレッジ品質だが、設計を考慮したコード生成は苦手。区分=実証（本文未確認）。https://arxiv.org/abs/2602.13611

## 勝つための示唆
1. テスト生成の前に要件の testability 欠陥（曖昧語、境界値・閾値・前提の欠落、検証不能な形容詞）を検出し、欠陥のある要件は生成せず指摘に回す。根拠: サーベイ 2606.06563（曖昧さ対処を満たす手法なし）、Rodríguez 2505.09830（有効性は要件の精密さ次第）、Alagarsamy 2402.11910（要件整合は 67%）。
2. 生成物はテスト条件から受入基準（Gherkin）まで、要件 ID への追跡リンクを必須にして出す。要件に無い条件は「推測」と表示する。根拠: Gupte 2511.11829（Gherkin と要件の整合を検査する発想）、Siddeeq 2607.01980（要件整合型の構成）。
3. 同値分割・境界値は LLM に自由生成させず、要件から抽出した変数・範囲に決定的な手順で展開し、LLM は候補の抽出と説明に限定する。根拠: Guo 2501.14465、Rodríguez 2505.09830、ABEX 2608.28230。
4. 産業文書での再現率低下を前提にし、網羅度（要件のうちテスト条件が無いもの）を利用者に見せる。根拠: Masuda 2510.03641（0.81 から 0.37）。
5. 評価は LLM 採点だけにせず、人の審査と要件カバレッジで行う。根拠: Moradi 2604.06946 が LLM 採点、Hassani 2508.20744 は n=10。日本語要件での公開評価は今回見つからず、自前で評価セットを作る価値がある（未確認）。
