# P1 LLM による要件の曖昧さ・欠陥検出の最新論文（2024〜2026）

## 結論（3 行）
- 調べた範囲では、要件の曖昧さ・欠陥「検出」で適合率/再現率を abstract に載せ、規則ベースと直接比較した論文は 1 本も確認できなかった（調査は abstract 止まり・本文未確認。検出 API が 429 で制限され網羅は不十分）。
- 最も強い実証は逆風側: 34 名の統制実験で、LLM 支援はインスペクションの smell 検出精度を下げた（2608.21298）。「LLM で検出」を売りにするだけでは勝てない。
- 勝ち筋は、LLM 単独判定でなく「複数解釈の食い違い＝曖昧」「SMT/規則による検証」「質問生成」との併用と、自前の日本語ベンチで P/R を示すこと。

## 発見
区分: 実証=abstract に実験の数値あり／主張=数値なし・または自己申告／未確認=本文を読んでいない事項。全件 abstract のみ確認（本文未読）。arXiv ID は取得結果のまま（私の記憶による裏取りなし）。

1. Broccia, Frattini, Arora, ter Beek, Fantechi, Vogelsang, Ferrari／2026-08／arXiv 2608.21298
   - 題: Human-AI Collaboration in Requirements Engineering: Evidence of the Negative Effect of LLMs on Requirements Inspection
   - 手法: 要件インスペクションの統制クロスオーバー実験、ベイズ回帰。n=34 人。LLM あり/なしを比較。
   - 効果: LLM 支援で smell 検出精度が低下。smell 分類・所要時間には有意差なし。モデル名・P/R は abstract に無し（未確認）。
   - 区分: 実証。 https://arxiv.org/abs/2608.21298
2. Hall, Eiers／2026-05／arXiv 2605.13817（VERIMED）
   - 手法: LLM＋SMT ソルバ。独立な形式化の不一致を曖昧さの兆候とし、矛盾・空疎も検出。反例誘導修復。
   - データ/効果: 血液透析の QA ベンチで検証済み正解率 55.4%→98.5%（検出の P/R ではなく修復後の正答率）。n・モデルは未確認。
   - 区分: 実証（指標が検出 P/R でない点に注意）。 https://arxiv.org/abs/2605.13817
3. Fang, Jin ほか／2026-05／arXiv 2605.01209（ClarifySTL）
   - 手法: LLM エージェントが曖昧・漠然表現を検出し、確認質問を生成して STL へ変換。DeepSTL、STL-DivEn、新規 AmbiEval で評価。
   - 数値: abstract に無し。区分: 主張。 https://arxiv.org/abs/2605.01209
4. Yang ほか／2026-04／arXiv 2604.21505（Orchid）
   - 手法: 語彙・構文・意味・漠然性の曖昧さを含む関数レベル 1,304 タスクのベンチ。全評価モデルが曖昧さで劣化し、同一要件に対し機能的に異なる実装を出す。
   - 区分: 実証（検出でなく生成への影響）。 https://arxiv.org/abs/2604.21505
5. Villamizar, Fischbach, Frattini, Ferrari, Vogelsang, Mendez ほか／2026-09／arXiv 2609.29208
   - 手法: 4 アプリでトレーサビリティ用データと smell 分類を再利用し、生成コードをシステムテストで検証。smell 密度が高いほど機能正答率が概ね低い。ただし smell が無くても欠陥コードは出る。
   - 区分: 実証（数値は abstract に無し）。 https://arxiv.org/abs/2609.29208
6. Vogelsang, Korn, Broccia, Ferrari, Fischbach, Arora／2025-01／arXiv 2501.04810
   - 手法: LLM 2 種でトレースリンク生成に対する requirements smell の影響を測定。リンク有無には小さいが有意な影響、行レベルには有意差なし。
   - 区分: 実証。 https://arxiv.org/abs/2501.04810
7. Ferrari, Abualhaija, Arora／2024-04／arXiv 2404.06371
   - 手法: ChatGPT が 28 件の要件文書から UML シーケンス図を生成する質的研究。曖昧・矛盾があると完全性/正確性が落ちる。
   - 区分: 実証（質的）。 https://arxiv.org/abs/2404.06371
8. Darif, Niu, Abdellatif, Briand ほか／2026-02／arXiv 2602.22456（LEREDD）
   - 手法: 要件間依存の検出（品質欠陥ではなく隣接領域）。813 要件ペア・3 システム。
   - 効果: 精度 0.93、F1 0.84（非依存で約 0.96）、Requires で基線比 F1 相対 +94.87%/+105.41%。モデル名は未確認。
   - 区分: 実証。 https://arxiv.org/abs/2602.22456
9. Zhou, Towey, Chen／2026-05／arXiv 2605.17926
   - 手法: 産業事例。ルールマイナーが要件の曖昧・自己矛盾・検証不能な記述を指摘し、コードを静的検証。abstract に数値無し。
   - 区分: 主張。 https://arxiv.org/abs/2605.17926
10. Huang／2026-09／arXiv 2609.33699（SpecRead）
   - 手法: OpenTitan 10 IP ブロックの 385 問＋対照 82。Ministral-3B 全体 33.2%（128/385）、ディストラクタで偽陽性率 51.2%、矛盾箇所の特定 78.9〜81.6%。
   - 示唆: 小型モデルは仕様の矛盾検出で偽陽性が高い。ハードウェア仕様で、要件文書ではない。
   - 区分: 実証。 https://arxiv.org/abs/2609.33699
11. Mu ほか／2023-10／arXiv 2310.10996（ClarifyGPT。範囲外の 2023 年だが引用元として）
   - 手法: コード整合性チェックで曖昧要求を判定し質問生成。GPT-4 の pass@1 は MBPP-sanitized で 70.96%→80.80%、4 ベンチ平均 68.02%→75.75%。要件文書の欠陥検出ではない。
   - 区分: 実証。 https://arxiv.org/abs/2310.10996
12. Wu, Fard／2024-05／arXiv 2406.00215（HumanEvalComm）、Wu ほか／2025-04／arXiv 2504.16331（ClarifyCoder）

## 勝つための示唆
1. LLM 単独の指摘を鵜呑みにさせない設計にする。人が LLM 支援で検出精度を落とした実験があるため（2608.21298）、指摘に根拠箇所・理由・確信度を付け、人が反証しやすくする。
2. 複数回・複数観点の解釈の食い違いを曖昧さの信号として使い、論理的に検証できるものは SMT 等で確認する（2605.13817）。
3. 指摘だけでなく確認質問を出し、回答で要件を更新する（2605.01209、2310.10996、2504.16331）。QA がそのままレビュー記録にできる形にする。
4. 要件間の矛盾・依存・重複は独立機能にする（2602.22456）。小型モデルは偽陽性が高い（2609.33699）ので、モデル選定は偽陽性率で評価し、抑制手段（規則との併用・再検証）を持つ。
5. 自前の日本語ベンチ（基本設計書・要件定義書、重大度付き正解）を作り、規則ベース単独、LLM 単独、併用の P/R を公表する。既存論文に日本語での比較根拠が見当たらないため、ここが差別化点になりうる（未検証）。

## 引用してはいけない数値
- VERIMED の 55.4%→98.5%: 検出の適合率/再現率ではなく修復後の QA 正答率。
- ClarifyGPT・ClarifyCoder・LEREDD の数値: コード生成/依存検出の指標で、要件の欠陥検出精度の根拠にならない。
- SpecRead の 33.2%・偽陽性率 51.2%: ハードウェア仕様・3B 小型モデルの結果。
- 2026 年論文の ID・日付は取得ツールの出力のまま。原典での再確認前に外部へ出さない。
- 本文を読んでいないため、各論文の n・モデル名・データの出所は未確認。
