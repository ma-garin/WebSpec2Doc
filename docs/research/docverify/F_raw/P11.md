# P11 AI レビュー支援の受容・信頼・説明可能性

注意: arXiv API と Semantic Scholar API が 429（レート制限）を多発し、検索は一部しか成功していない。以下は abstract レベル（本文未確認）の知見のみ。コードレビュー支援の受容研究・誤検知閾値の研究は取得できておらず「未確認」。

## 結論（3 行）
1. 説明や根拠を付けるだけでは過信は減らない。説明が検証コストを下げる設計（認知強制・反対意見の提示・事例ベース）でのみ過信が減る（実証・汎用 AI 意思決定課題）。
2. 要件品質評価で市販 LLM は、専門家指摘の約半分しか検出せず誤検知も出る（2026・1 件のベンチマーク）。見逃し前提の設計が要る。
3. 「誤検知が何 % を超えると使われなくなるか」の閾値を示す一次資料は今回取得できていない（未確認）。数値の断定はしない。

## 勝つための示唆
1. 根拠の引用は「検証を速くする」形にする。該当原文の箇所への即ジャンプと、指摘ごとの 1 クリック確認を付ける。説明の量でなく検証の容易さが過信を減らす（発見 2、1）。
2. 指摘に「見逃しがある」前提を明示する。LLM は必要性・正しさの欠陥をほぼ見逃す（発見 6）。AI の指摘ゼロを「問題なし」と見せない。網羅は QA の観点チェックリスト側で担保する。
3. 受け入れ前に QA が自分で判断する手順を入れる（先に自分の判断を入れてから AI 指摘を開示する等の認知強制。発見 1）。ただし主観評価は下がるため、既定は軽めにして切替式にする。
4. 指摘の種類を分ける（根拠付き事実／推測）。特徴量型の説明は過信を増やし得る（発見 3）。反対意見・代替解釈を出す機能は有望だが検証が不足（発見 4、5）。
5. 誤検知率・採否率を自ツールで計測して画面に出す。他社の閾値数値は未確認なので、自社データで決める（本調査では閾値の根拠なし）。

- 発見 9 の 42.9% / 34.9%: 短時間利用後の自己申告で、実際の行動ではない。
- 発見 7 は教育領域。要件レビュー担当者に一般化できない。
- 効果量（d や OR）は全論文で本文未確認。
