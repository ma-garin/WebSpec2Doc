## 1. 付録A 数学的基礎の復習

URL: https://itdojp.github.io/formal-methods-book/appendices/appendix-a/

要点:
- 集合・論理・関係と写像・状態/操作/不変条件・同値関係・帰納法の最小セット（A.1〜A.5）。
- 例「全口座の残高は非負」を `∀a : Account • balance(a) ≥ 0` と書く。
- 操作は事前条件・事後条件・フレーム条件で書く。

| 項目 | 示唆（20字以内） |
|---|---|
| 状態/操作/不変 | 仕様の要素分類 |
| 事前/事後条件 | 抜け項目の検出軸 |
| 量化（全て/存在） | 「すべて」の曖昧語検出 |
| 同値関係 | 同義語の同一視 |

- 事前条件・事後条件・不変条件の三点セットは、仕様書の「記載項目の網羅性チェック」の骨格に使える。操作の記述に「事前」「事後」「変更されないもの」が揃っているかを機械判定できる。
- 「すべての」「どれか」のような量化語が範囲（母集合）を伴っているかの指摘に使える。
- 「同じものとして扱う」単位の定義は、用語統一・識別子正規化のロジックの根拠になる。
- 引用: 「仕様では、状態（state）と操作（operation）を分離して記述します。」（A.4）

## 2. 付録B ツールインストールガイド

URL: https://itdojp.github.io/formal-methods-book/appendices/appendix-b/

要点:
- ツールを lane（pr-quick / nightly / optional / documentation-only）に分類し、版・timeout・seed・artifact 上限を台帳（tool-manifest.json）で管理する。
- 結果の artifact に「版・コマンド・入力 SHA-256・exit code・成功/反例/unknown/timeout」を分けて残す。保持 14 日。
- 「pass」と「unknown/timeout」を区別し、unknown を成功扱いしない。
- 更新は月次、版だけの専用 PR で出力契約の差分をレビューする。

| 項目 | 示唆（20字以内） |
|---|---|
| lane 分類 | 検査の深度プリセット |
| 入力ハッシュ記録 | 監査証跡・再現性 |
| unknown を区別 | 判定不能の第3状態 |
| 版固定・月次更新 | 検査ルールの版管理 |
| 保持期間 14 日 | データ保持ポリシー |

- 検査結果を「合格/不合格/判定不能」の 3 値で持つ設計は、AI 検査（確率的出力）の信頼性表示に直結する。
- 検査実行ごとに「入力ファイルのハッシュ・ルール版・モデル版・実行日時」を残す機能は、工程移行判定の根拠資料（監査証跡）になる。
- 引用: 「結果を『仕様全体の証明』とは扱わず、…」（Quint の節）。ツールの合格が保証する範囲を明示する、という方針は UI 文言（「検査したのはここまで」）に転用できる。
- 引用: 「timeoutとstdout/stderr上限はrunnerが強制し…」。実行資源の上限を明示する考え方は、契約プランの「トークン上限」表示と整合する。

## 3. 付録C 記法対照表（用語集 C.1・DoD チェックリスト C.2・記法表 C.3）

URL: https://itdojp.github.io/formal-methods-book/appendices/appendix-c/

要点:

- C.1.1 に「SAT / UNSAT / unknown」の証跡対応表。それだけでは保証しないもの（要件妥当性など）を明記。
- C.2 は AI 時代の DoD チェックリスト 4 項目。
- C.3 は同一概念を Z / Alloy / CSP / TLA+ / Quint / Lean / Rust 検証ツール等で対応づける表。コードブロックを「ツール準拠」「文脈依存」「擬似記法」の 3 ラベルで区別する。

| 項目 | 示唆（20字以内） |
|---|---|
| DoD 4 項目 | カスタム観点プリセット |
| 証跡の保証範囲表 | 「保証しないこと」欄 |
| 概念対応表 | 用語ゆれ辞書の雛形 |
| 3 ラベル分類 | 記述の厳密度ラベル |
| 反例=最小実行例 | 指摘に再現手順を付与 |

- C.2 の DoD（仕様差分に対応する仕様の更新／検証ログの再現情報／反例の修正履歴／例外承認の理由・代替・期限）は、そのままプリセット観点として登録できる。引用: 「例外承認の理由・代替策・フォローアップ期限が明記されている」。
- C.1.1 の「それだけでは保証しないもの」列は、検査レポートの免責/適用範囲欄の雛形になる。引用: 「checker が受理したのは encoded problem に対してだけ」という趣旨（要件妥当性・未モデル化仮定は対象外）。
- 同一概念の対応表（C.3.1）は、同義語・表記ゆれ辞書の設計例になる。顧客ごとに「社内語 ⇔ 標準語」の対応表を持たせ、文書間の不一致検知に使える。
- 反例（counterexample）は「性質が破れる最小の実行例」と定義される。指摘ごとに「どの条件でどう破れるか」の最小例を付ける設計の根拠になる。
- C.3.11 の「強すぎる assume は主張を空虚にする」は、AI 検査の「過度な前提を置いて問題なしと判定する」誤りへの注意になる。

## 4. 付録D 演習問題解答（提出物テンプレ・採点観点 rubric）

URL: https://itdojp.github.io/formal-methods-book/appendices/appendix-d/

要点:
- D.1 に共通の提出物と採点観点 5 つ（正確性・完全性・一貫性・再現性・妥当性）。
- 各章の演習に「ヒント／模範解答の骨子／採点観点」の三層。
- D.4（第3章）に仕様の曖昧性特定・契約記述・キュー仕様・メール不変条件・仕様検証の演習。D.2 に曖昧性の定量分析。
- D.15 に AI 利用時の提出テンプレ（プロンプト／生成仕様／検証ログ／反例と修正）。

| 項目 | 示唆（20字以内） |
|---|---|
| 5 つの採点観点 | 観点別スコアの軸 |
| 曖昧語→解釈→影響表 | 曖昧語検出の出力形式 |
| pre/post/frame 分離 | 契約記述の充足判定 |
| 不変条件の分類 | 整合性/安全/業務ルール |
| 仕様→テスト観点 | 境界/同値の自動導出 |
| 例外フロー | 承認者・期限・戻し |

- 曖昧性分析（D.2/D.4）の出力形式「曖昧語→解釈候補→影響（誤検知/漏検知/UX/運用負荷）」は、指摘カードの標準項目にできる。引用: 「『適切に』『大きすぎる』『不正な』など、閾値や判定主体が不明な語を列挙」。
- 曖昧性の見積り「分岐の積」でリスクを概算する考え方は、文書単位の「曖昧度スコア」の算出式（分岐数×影響度）に使える。
- 採点観点 5 つ（正確性・完全性・一貫性・再現性・妥当性）は、独自の観点別スコアの軸として使える。市販の競合は 5 観点（正確性・理解性・視覚性・深層性・信頼性）で採点している（6 章）。差別化するなら「完全性」「再現性」を別軸に立てる余地がある。
- 不変条件のカテゴリ分け（データ整合性／セキュリティ／ビジネスルール）は、要件の分類プリセットになる。メール例では「メッセージは受信/送信/ゴミ箱のいずれかに所属」「重複禁止」を挙げる。
- 引用: 「仕様→テスト観点（境界/同値分割/反例）へ写像」。仕様書の条件式から境界値テスト条件を自動で提案する機能の根拠。note_A の境界値例（0・1・1000・1001）と同じ発想。
- D.1 の「数字（%/倍/件数）は出典を付与するか、例示であることを明示」は、文書内の数値に出典が付いているかのチェック項目になる。
- 注意: 解答は「一意ではない」と明記されている。AI の指摘でも「正解は一つではない」前提で、採点観点（rubric）形式で出すほうが誠実。

URL: https://itdojp.github.io/formal-methods-book/appendices/appendix-f/

要点:
- F.2 信頼境界: LLM は提案者（untrusted）、検証器は判定者（trusted）、CI は執行者。
- F.3 ワークフロー: 要求→用語定義→不変条件→モデル化→反例確認→修正→再検証。
- F.4 プロンプトテンプレ 5 種（仕様抽出／Alloy／TLA+／反例要約／PR チェックリスト）。
- F.8 反例トリアージテンプレ（事実と仮説を別欄に分離）。
- F.9 品質保証チェックリスト（仕様／証明／CI）、F.10 LLM 支援証明、F.11 生成 AI 出力検査との違い、F.12 テスト戦略との責務分界、F.13 runtime monitor 証跡と LLM の真実境界。

| 項目 | 示唆（20字以内） |
|---|---|
| 事実/仮説の分離 | 指摘の根拠欄と推測欄 |
| F.9 仕様チェックリスト | カスタム観点の初期集 |
| LLM を未信頼入力 | 人の確認ステップ必須 |
| 仕様差分↔テスト差分 | 文書間トレーサビリティ |
| 個人情報の外部送信 | 送信前マスキング |

- F.9「仕様」の 5 項目が最も直接使える観点プリセット候補: (1) 用語定義が明確（同義語・境界・単位・例外条件）(2) 前提条件（環境仮定・公正性・障害モデル）が明示 (3) 不変条件が列挙され破れたときの意味が説明できる (4) 活性が定義され過剰な仮定で見かけ上成立していない (5) 数値は出典付きまたは例示と明記。
- F.8 の「観測された事実」と「仮説（原因候補）」を別欄にする型は、AI 指摘に「該当箇所の引用（事実）」と「解釈（仮説）」を必ず分けて出す UI の根拠になる。引用: 「事実欄はログ/トレースから転記し、仮説欄は別枠に分離してください。」
- F.12 の「仕様差分／テスト差分／検証差分／レビュー差分」は、要件→設計→テスト仕様の反映有無（抜け漏れ検知）の観点そのもの。「形式仕様で見つかった反例はテストケース化し、テストで見つかった欠陥は仕様の不足として見直す」という双方向の追跡を機能にできる。
- F.13 は、未加工ログに個人情報・機密が含まれるときは「外部 LLM へ送らず、最小化・pseudonymization・access policy を先に適用」と述べる。外部 LLM へ文書を送る製品では、送信前のマスキング機能と送信先の明示が信頼要件になる。
- F.13「LLM に欠落 event を補完させない。不明は不明として残す」は、AI が書かれていない要件を勝手に補って「問題なし」と判定する失敗への歯止めの考え方として使える。
- F.5 の Issue 作成時「受け入れ条件（検証で合否判定可能な形）・非目標・実行コマンド」は、要件文の書き方チェック（合否判定可能か／非目標があるか）にできる。

## 7. 用語集（Glossary）

URL: https://itdojp.github.io/formal-methods-book/glossary/

要点:
- 略語（SAT・SMT・LTL/CTL・CI・RMW 等）と A〜Z の用語。各項目に参照章を付ける（→第N章/付録X）。
- 用語は「本書での用法（最小）」と明記し、厳密な差分は付録A/C・一次情報を参照させる。
- 保証範囲の限定を各項目に書く文体が一貫している（「〜は実世界全体の正しさを意味しない」等）。

| 項目 | 示唆（20字以内） |
|---|---|
| 用語+定義+参照先 | 用語集の標準様式 |
| 範囲限定の文体 | 結果の注意書き |
| vacuity（空虚性） | 見かけ上の合格の検出 |
| unknown | 判定不能の扱い |
| 安全性/活性 | 要件の2分類 |
| 空虚な成立 | 前提が強すぎる検出 |

- 用語集機能: 顧客の用語集（略語・定義・参照先）を登録し、(1) 文書中の未定義略語、(2) 同一概念の異表記、(3) 定義と矛盾する用法を指摘する、という 3 機能に分解できる。この書籍の形式（用語＋定義＋参照先）を登録フォーマットの雛形にできる。
- 「安全性（悪いことが起きない）」と「活性（良いことがいつか起きる）」の 2 分類は、要件を「禁止/不変」と「到達/応答」に仕分けする観点として使える。活性は公平性の前提に依存しやすい、と用語集は注意する。
- vacuity（空虚性）の定義: 「強すぎる仮定や到達不能な前提によって自明に成立する状態」。AI 検査にも当てはまる。例えば、前提条件が実際には起こり得ない仕様の「異常系は網羅されている」という判定は、空虚な合格である。
- unknown の定義: 「成功でも反例なしでもなく、CI では調査対象として扱う」。AI の判定不能を合格に数えない設計の根拠。
- 引用: 「模型検査…網羅性はモデル、性質、探索設定…の範囲に相対的であり、実世界全体の正しさを意味しない。」検査結果の「適用範囲」欄の文例になる。

### 8.1 introduction / afterword / index

URL:
- https://itdojp.github.io/formal-methods-book/introduction/
- https://itdojp.github.io/formal-methods-book/afterword/
- https://itdojp.github.io/formal-methods-book/（index）

要点:

- index に「テストを置き換えるものではなく、テストで確認すべき観点を明確にする補助線」という位置づけ。
- afterword に「形式的手法の真の価値はバグを見つけることではなく、仕様の隠れた前提条件を明らかにすること」という趣旨。
- ライセンス・商用利用窓口: ITDO（knowledge@itdo.jp）。

| 項目 | 示唆（20字以内） |
|---|---|
| 責務分界表 | 検査の守備範囲の説明 |
| 隠れた前提の発見 | 製品の価値訴求 |
| 想定読者に QA | ターゲットの裏付け |
