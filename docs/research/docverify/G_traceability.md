## 結論（5 行以内）
1. 規格は双方向の追跡と、親の無い項目・子の無い項目の検出を求める（T1 発見 1・3・5、二次資料）。商用 RM は ID 付きの構造化アイテムを前提にし、ID の無い文書の扱いは確認できなかった（T2）
2. 日本語の要件→設計の自動リンク回復を測った研究は見つからない（T3 結論）。精度は外部の数値でなく、pair_v1 の trace.jsonl で自前に測るしかない
3. 構成は「本ツールが要件・設計の単位に安定アンカーを振る → 検索で候補 → 判定 → 人が承認」。AI は承認しない（T3 発見 4・10、P4b 発見 2・6）
4. 指標はカバレッジ率と suspect を分け、孤立要件・孤立設計・不整合を一覧で出す（T2 Jama、T4 発見 3・4）。率は分母と「候補のみ」の件数を添える（P4 示唆 2）
5. 現行の `trace.py` は ID の正規表現の完全一致だけで、ID の無い文書は「読み取れない」で外す。pair_v1 の基本設計書は ID を含む行が少なく、現行方式は大半のリンクを落とす見込み（未計測）

## 規格が求めること（リンクの種類・双方向性・粒度・証跡）

| 規格 | 求める追跡 | 区分 |
|---|---|---|
| ISO/IEC/IEEE 29148 | 上向き・下向き | 主張（T1-1） |
| ISO/IEC/IEEE 29119 | テストベース→記録 | 未確認（T1-2） |
| Automotive SPICE 4.0 | 双方向＋一貫性 | 主張（T1-3） |
| ISO 26262 | 双方向（Part 6） | 主張（T1-4） |
| DO-178C | 要件⇔コード⇔テスト | 主張（T1-5） |
| IEC 62304 | 要件⇔テスト | 主張（T1-6） |
| 共通フレーム 2013 | 29148 を取り込み | 主張（T1-7） |

- リンクの種類: 上向き＝導出（上位の要求へ）、下向き＝配分・展開（下位要件・設計へ）。用語は ISO/IEC/IEEE 24765 とされる（T1 発見 1）
- 双方向性: ASPICE 4.0 は全エンジニアリングプロセスで双方向トレーサビリティと一貫性を求める（T1 発見 3）。DO-178C ではコード→下位要件のリンクで「文書化されていない機能が無いこと」を確かめる（T1 発見 5）。孤立項目の検出は両方向が要る
- 粒度: 要件 1 件 ↔ 設計要素 1 件 ↔ テストケース 1 件が基本（T1 結論）。ASPICE 4.0 の PAM では「クリック可能な直接リンクでなくてよい」とされる（Jama の二次情報。T1 発見 3）。章・見出し・表の行の単位での対応づけを許す根拠になる
- 証跡: 規格横断で「トレース表＋レビュー記録」が実務の形（T1 発見 8、UL ガイド）。トレースはカバレッジ・一貫性・影響分析を支える（同）
- IPA 共通フレーム 2013 と ESPR の双方向トレーサビリティの具体記述は未確認（T1 発見 7）
- 日本の現場の Excel マトリクスの実態（ID 変更で壊れる・他ツールと同期しない）は販売系ブログと論文要旨 1 本の主張のみ。国内の実態調査は見つからない（T1 発見 9）

## 自動リンク回復の手法と精度（ID の無い日本語文書で何が期待できるか）
- 手法の流れ: IR（VSM・LSI）→ BERT 系 → 検索拡張の LLM 判定（T3 結論）。LiSSA は類似度で候補を取り、LLM が各リンクを判定する RAG 構成。著者自身が実用には追加研究が要ると述べる（T3 発見 4、主張）
- 既存リンクの検証と欠落の回復を二本立てにする TVR（自動車の要件、産業データ）が主流の一つ（P4b 発見 4、主張。数値は引用不可）
- 推移補正: 中間成果物の語を橋にして類似度を補うと IR が改善した（TRIAD、T3 発見 3、相対改善のみ）。要件→基本設計→テストの 3 段で効く可能性があるが日本語は未検証
- 多言語: 混在言語の issue-commit で、翻訳前処理＋単言語埋め込みが有効（T3 発見 1、実証）。日本語は 1 プロジェクトだけで、要件→設計ではない
- 抜けの検出: 上位要件のカバレッジ確認に LLM を使い、人工的な単一削除の欠落を高い再現率で検出（Hartl 2024、P4b 発見 5、実証）。適合率は無く、実運用の抜け検出の精度ではない
- 完全性の判定: 別領域（医療回答）で LLM による完全性判定が偶然に近い例がある（P4、実証、領域違い）。自動の網羅指標は人手評価とずれうる（P4 Siddeeq 2026）
- 人の確認: 高精度の候補行列を渡すと分析者は精度を下げ、低精度なら改善する。最終精度に効くのは初期行列の精度と確認の労力だけ（T3 発見 10、実証だが本文未確認）。UI で過修正を抑える予備研究がある（P4b 発見 6、主張）。分析者には接続先の成果物の内容が有用（T3 発見 10、Maro 2018）
- 期待できること: 日本語の要件→設計で精度を示した根拠は 0 件（T3 結論・P4 結論 1）。したがって数値目標は外部論文から取らず、pair_v1 で測った値で置く（T3 要件 5、P4 示唆 5）。翻訳前処理の効果も日本語では未検証

## 本ツールの機能要件（優先順）
評価は `quality/docverify_eval/pair_v1/<組>/trace.jsonl` を正解にし、`scripts/docverify_pair_eval.py --trace` で採点する前提。採点器はリンク（要件の行範囲と設計の行範囲の両方が重なれば一致）と「設計に反映なしの要件」の P/R/F を出す。
2026-10-18 18:42 時点で pair_v1 は作成途中（trace.jsonl は未配置、基本設計書は 7 組）。ID の形式（REQ- 等）を含む行の数は、要件定義書で 15〜17 行、基本設計書で 2〜14 行（`grep -c` で計測）。

### TR-1 ID の無い文書に安定アンカーを振る
- 内容: 見出し・表の行・段落・箇条を単位に本ツール側でアンカーを付ける。文書内 ID があれば別名として持つ。版が変わっても本文の一致で追従する
- 根拠: T2 要件 3（ID 無し文書の扱いが商用で未確認）、T1 発見 3・5（粒度は要件 1 件単位、直接リンクでなくても可）
- 現行実装との差: `trace.py` は ID を取れない文書を unreadable に入れて外す。アンカーの概念は無い
- 測り方: trace.jsonl の `req_lines` を正解の要件単位とし、ちょうど 1 アンカーが重なる割合を数える（境界一致率。自作の指標）

### TR-2 候補リンクを「検索→判定」の 2 段で出す
- 内容: 要件アンカーごとに設計アンカーの候補を類似度で絞り、判定段で採否と根拠文を付ける。ID 一致は強い手がかりとして残す
- 根拠: T3 発見 4（LiSSA）、P4b 発見 2・4、P4 示唆 3。推移補正は後段（T3 発見 3、日本語未検証）
- 現行実装との差: 正規表現の完全一致だけで、意味の対応づけは無い
- 測り方: `--trace` の links の P/R/F1。条件を 2 つ取る: 原文のまま／両文書から ID を消した版。現行 `trace.py` を同じ採点にかけ基準値とする

### TR-3 人が承認する。AI は承認しない
- 内容: リンクの状態を「候補・承認・却下・保留」で持つ。確認画面は双方の原文と一致箇所を並べ、低スコア側の一覧も出す。承認者欄は人だけが埋める
- 根拠: T3 発見 10、P4b 発見 6・7（過修正の抑止）、T2（Visure の推奨運用）
- 現行実装との差: リンクは毎回計算するだけで保存されない。状態も承認者欄も無い
- 測り方: オフラインでは確認の負荷を、正解リンクが上位 k 件の候補に入る率（Recall@k）で見る。採点器は未対応で拡張が要る。人の精度への効果は社内実験で測る（オフライン評価の外）

### TR-4 孤立要件（設計に反映なし）と孤立設計を出す
- 内容: 承認済みリンクが 0 件の要件を孤立要件、要件へのリンクが 0 件の設計アンカーを孤立設計（追加過多の候補）として一覧にする。候補しか無いものは「要確認」に分ける
- 根拠: T1 発見 1・3・5、T4 発見 3・4（欠落経路・冗長・不整合の分類）、F 要件 1
- 現行実装との差: 現行の「孤立」は上流に無い ID を下流に書いた場合だけ。ID の無い設計要素は数えない
- 測り方: 孤立要件は `--trace` の unreflected の P/R。孤立設計は採点器に無いため、どのリンクにも含まれない設計の行範囲を正解にする拡張が要る（見出しなど非要素の除き方は未決）

### TR-5 指標を率と問題の一覧で出す
- 内容: 前方・後方カバレッジ、孤立要件、孤立設計、suspect を別々に出す。率には分母と「候補のみ」の件数を必ず添え、網羅性は「未検証」と表示し続ける
- 根拠: T2（Jama が完全性と suspect を分離）、T4 発見 3・4、P4 示唆 2
- 現行実装との差: 完全率（全下流種別に ID がある上流 ID の割合）だけ。後方カバレッジと suspect は無い
- 測り方: 予測リンクから算出した各指標と、trace.jsonl から算出した値の差（絶対誤差）を組ごとに出す

### TR-6 版の取り込みで suspect を立てる
- 内容: 新しい版を取り込んだら、変わったアンカーに付く承認済みリンクを suspect にし、確認キューへ出す。解除は人が行い、解除者と日時を残す。自動では解消しない
- 根拠: T2（DOORS Next・ModernRequirements・easeRequirements）、T4 発見 6（RUP の suspect）・発見 5（自動更新は研究段階）
- 現行実装との差: inspection.json に versions はあるが、リンクを保存しないため suspect を立てられない
- 測り方: pair_v1 は 1 版のみで測れない。設計側の行を書き換えた第 2 版を作り、書き換え行に触れる正解リンクの集合を正解として P/R を取る（評価セットの拡張が要る）

### TR-7 追跡の型（必須の経路）を設定できる
- 内容: 「要件→設計」「要件→テスト」などの必須経路を宣言し、顧客の社内標準ごとに差し替える。重大度は利用者が調整する
- 根拠: T4 発見 4（トレース情報モデルとの照合）・発見 3（重大度は専門家間で割れた）、T1 発見 3・6
- 現行実装との差: 種別は要件・設計・テストの 3 つで固定
- 測り方: オフライン評価の対象外。設定の読み込みは単体テストで確かめる

### TR-8 リンク単位で一貫性を検査する
- 内容: 承認済みリンクの両端だけを比べ、数値・条件・用語の食い違いを矛盾候補として両方の原文と並べる
- 根拠: T1 要件 5・発見 3（ASPICE の一貫性）、F 要件 1
- 現行実装との差: 矛盾検査は主語が完全一致する文の数値と否定だけ。総当たりで 1,500 単位超は切り捨て（F 要件 1）
- 測り方: pair_v1 の defects.jsonl の CONTRADICTION について、正解リンク上でだけ比べた場合の再現率と誤検出数

### TR-9 証跡としてトレース表を出し、既存の Excel 表を取り込む
- 内容: 全リンク・状態・孤立・suspect・版・日付・確認者を xlsx と PDF で出す。既存の Excel マトリクスの ID 列から対応表を読み込み、候補の初期値にする
- 根拠: T1 発見 8・9、T2（Jama の PDF 出力）
- 現行実装との差: `trace.to_xlsx` はあるが状態・版・確認者の列が無く、式インジェクション対策 `_safe` も無い（地図）
- 測り方: オフライン評価の対象外。出力の行数一致と、`=` 始まりのセルが無害化されることを単体テストで確かめる

## 指標の定義
以下の式は本ツールの自作定義である。一次文献で標準の式は確認できなかった（T4 末尾の未確認）。区分の考え方は Rempel ら（T4 発見 3・4）に寄せた。
- 数える対象: 承認済みリンクだけ。候補のみのものは「要確認」として別の件数で出す
- 前方カバレッジ: 設計へのリンクを 1 件以上持つ要件アンカーの数 ÷ 対象の要件アンカーの数。分母（対象範囲）を画面に出す
- 後方カバレッジ: 要件へのリンクを 1 件以上持つ設計アンカーの数 ÷ 対象の設計アンカーの数
- 孤立要件: 下流への承認済みリンクが 0 件の要件アンカー。「設計に反映なし」の候補
- 孤立設計: 上流への承認済みリンクが 0 件の設計アンカー。「追加過多」の候補。見出しのみ・共通事項の節は対象外にできる
- suspect: 承認済みリンクの両端のどちらかが、承認より後の版で変わった状態。人が確認して「影響なし」か「要修正」に落とす
- suspect 率: suspect のリンク数 ÷ 承認済みリンク数。カバレッジとは別に出す（T2 の Jama の分け方）
- オフライン評価の指標: リンクと孤立要件の P/R/F は採点器の定義のまま（行範囲の重なりで一致、1 対 1 の貪欲照合）
