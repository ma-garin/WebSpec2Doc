# WS2D-RL-001 リリース手順書

- 文書ID: WS2D-RL-001
- 版数: 2.0 / 作成日: 2026-08-02
- 依存更新方針は `docs/specs/spec-6-2_dependency_update_strategy.md` を正本とする。本書はリリースプロセス全体（ブランチ運用〜配布物生成〜ロールバック）を統合したビューである。

## 1. リリース方針とバージョニング規則

- WebSpec2Doc は**PRマージ単位を実質的なリリース単位**として運用している。`git log`（2026-08-02実測）でMerge pull request形式のコミットが連番（例: #158, #157, #156…）で確認でき、mainブランチへの`--no-ff`マージがそのままデプロイ可能な状態を意味する。
- **セマンティックバージョニング（gitタグでのv1.0.0等の付与）の運用は、本書調査時点で確認できなかった（未確認）。** `docs/sdlc/`配下の各SDLC文書は独自の版数（例: 本書は現在版2.0）を持つが、これはプロダクト自体のリリースバージョンとは別の文書管理番号である。プロダクト全体のバージョン番号を導入するかは、今後の判断課題として残す。
- mainブランチは保護設定なしで運用している（開発運用メモ）。CIによるチェックはリリース判断の参考情報であり、マージ自体をブロックする強制力は現状ない。
- リリース＝mainへのマージであるため、mainに入った時点でその変更は「リリース済み」として扱う。ステージング環境等の中間環境は本書執筆時点で確認できず、未確認。

## 2. リリース種別ごとの手順差

過去のコミット・PR履歴（`fix/*`, `feat/*`, `refactor/*`, `chore/*`, `perf/*`のブランチプレフィックスパターン）から、本書は3種のリリース種別を定義し、手順の軽重を使い分ける。**この分類は既存の文書化されたポリシーではなく、観測された運用実績を本書が新たに体系化したものである**（出典を正直に明記する）。

| 種別 | 該当ブランチ例 | ゲートの扱い | 承認・確認の重さ |
|---|---|---|---|
| 定期リリース | `feat/*`, `refactor/*` | フルゲート必須（§3全項目） | DoD Type A/B双方をフル実施。ブラウザ目視確認省略不可 |
| 緊急（バグ修正） | `fix/*` | フルゲート必須（§3全項目は省略しない） | 影響範囲を最小化したPRで速やかにレビュー・マージ。ゲート自体は削らない |
| ホットフィックス | `fix/*`（本番障害対応） | MANDATORY項目（構文・pytest・UI変更時のE2E）は省略しない。REQUIRED項目（ブラウザ目視確認等）は障害の深刻度に応じて縮小可 | 縮小した確認項目は必ずコミットメッセージまたはPRに明記し、事後に通常水準まで確認を追完する |

**共通原則**: いずれの種別でも、`.githooks/pre-commit`が機械強制する項目（構文チェック・pytest L1/L2・UI変更時のハッシュ照合）は一切省略できない。省略できるのはREQUIRED（人間確認）項目の縮小のみであり、それも「省略した」ことを記録に残す場合に限る。ホットフィックスであっても、DoD Type BのPROHIBITED項目（pytest PASSのみでの完了判断等）は種別によらず常に適用される。

## 3. リリース前チェックリスト

コミット・マージ前に実行するコマンドと合格基準:

```bash
make lint               # ruff check --fix + mypy + check_e2e_conventions.py + check_fetch_error_handling.py
venv/bin/python -m black <変更ファイル...>   # make lint に含まれないため個別実行が必要
make security            # bandit -ll（Medium以上ゼロ）+ pip-audit
make test                # L1/L2 全PASS + カバレッジ確認
make verify-ui           # UIファイル変更時のみ。L3 E2E全PASS + .ui-verified マーカー生成
python scripts/quality_harness.py   # L0: 機能契約の機械検証（PASS必須）
make coverage             # カバレッジ80%以上を確認
```

チェックリスト（実行順・合格基準を明示）:

- [ ] `black`・`ruff`・`mypy` が全てエラーなし（`make lint`はblackを含まないため個別実行が必要な点に注意、`WS2D-CS-001`§17参照）。
- [ ] `bandit -ll`でMedium以上の指摘ゼロ、`pip-audit`で既知の脆弱性なし。
- [ ] `make test`が全PASS。
- [ ] UIファイル（.html/.js/.css）を変更した場合、`make verify-ui`実行済みで`.ui-verified`マーカーが最新（2時間以内・ハッシュ一致）。
- [ ] `python scripts/quality_harness.py`が`Functional Integrity Harness: PASS`を出力（新機能は`quality/feature_contracts.yml`に登録済みであること）。
- [ ] `make coverage`が80%以上。
- [ ] DoD該当タイプ（A/B/C）のREQUIRED項目を実施済み。
- [ ] コミットメッセージが`type: 説明（なぜ）`形式（`WS2D-CS-001`§15）。

## 4. リリース手順（番号付き）

1. **ブランチ作成**: `main`から`<type>/<説明>`形式のブランチを作成する（例: `feat/multi-tenant-auth`）。種別は§2の定期/緊急/ホットフィックスのいずれかを最初に判断する。
2. **実装**: `docs/specs/CONVENTIONS.md`と`WS2D-CS-001`（コーディング規約）に従って実装する。新機能は同時に`quality/feature_contracts.yml`へ契約を追加する（`core_files`・`failure_modes`・`required_tests`必須）。
3. **ローカルゲート実行**: 本書§3のリリース前チェックリストを実行し、全項目を満たす。
4. **コミット**: `git commit`実行時、`.githooks/pre-commit`が構文チェック・pytest・（該当時）UIハッシュ照合を自動実行する。失敗した場合は§3に戻り修正する。
5. **PR作成**: `gh pr create`でPRを作成する。タイトルは70字以内、本文にSummary・Test planを含める。
6. **CI実行**: `.github/workflows/ci.yml`（smoke・e2e-uiジョブ、ubuntu-22.04固定）等が自動実行される。CIの詳細ジョブ構成は本書執筆時点で全ジョブを読み込んでおらず、**個別ジョブの合否基準は未確認**。CI結果はマージ判断の参考情報として使う。
7. **レビュー**: `code-reviewer`エージェントの実行、および人間による最終確認（DoD Type Bの場合はブラウザ目視確認を含む）。
8. **マージ**: `--no-ff`で`main`へマージする（ロールバックの起点を作るため、fast-forwardマージは使わない）。
9. **タグ**: プロダクトバージョンタグの付与は本書執筆時点で運用実績が確認できない（§1参照、未確認）。マージコミットのハッシュとPR番号がリリースの識別子として機能している。
10. **配布物生成**: 必要に応じて`scripts/build_delivery_docs.py`（詳細は§8）でSDLC文書のWord/Excel版を再生成する。
11. **リリース記録**: 本書§9の形式でリリース記録を残す。

## 5. 依存更新の手順

`docs/specs/spec-6-2_dependency_update_strategy.md`（依存更新戦略）の要点を統合する。playwright 1.44.0固定という制約が、`src/doctor.py`・`src/crawler/playwright_runtime.py`・`.github/workflows/ci.yml`・`docs/specs/CONVENTIONS.md`§2の4箇所に分散しているため、更新時は次の判断基準と手順に従う。

**更新判断基準**:

| トリガー | 判断 |
|---|---|
| pip-audit / GitHub Advisoryが脆弱性検出 | 即時評価。対応表の検証済み範囲外なら移行検証手順を完走してから更新 |
| Python 3.13+必須の環境が発生 | cp313 wheelの存在をPyPIメタデータで実測した候補版へ移行 |
| CIランナー（ubuntu-22.04）のEOL接近 | 24.04でsmoke/e2e-uiが通るplaywright版へ移行 |
| pytest-playwright等の周辺が新版要求 | 本体と同一PRで整合バージョンへ（片方だけ上げない） |
| 上記なし | 四半期ごとに更新要否をレビュー（更新しない判断も記録する） |

**移行検証手順（7段階）**: (1)候補選定＝PyPI JSON APIでwheel有無を実測、(2)再構築＝venv再作成→`make setup-runtime`→`make doctor`全PASS、(3)全ゲート＝CONVENTIONS§3、(4)E2E全通し＝`pytest tests/e2e -v`＋smoke相当＋`make verify-ui`＋`make demo`目視、(5)新Python環境でも(2)〜(4)を繰り返す（3.13移行の場合）、(6)文書更新＝doctor対応表・CONVENTIONS§2・ci.ymlランナー固定を同一PRで、(7)ロールバック＝`git revert`→依存再インストール→`make setup-runtime`→`make doctor`→`make verify-all`。

**日常の依存脆弱性監査**: `make audit`（`pip_audit`＋`output/.playwright_env`配下のnpm環境に対する`npm audit --audit-level=high`）で確認→更新→`make verify-all` green確認後にマージする。

## 6. ロールバック手順

- **コードのロールバック**: マージは`--no-ff`のため、問題発覚時は該当マージコミットを`git revert -m 1`で戻す（2親コミットのうち1番目=マージ前mainを正として戻す）。
- **DBスキーマ変更を伴う場合**: `instance/auth.db`（利用者認証）・`instance/tenants/{slug}/viewpoints.db`（観点）のスキーマは`docs/sdlc/_asbuilt/schema.sql`にas-builtで記録されている。スキーマ変更を伴うコミットを`git revert`する場合、後方互換マイグレーションが無い変更は**コードのロールバックだけでは不十分**であり、DBファイル自体のバックアップからのリストアが必要になる。バックアップ・リストア手順は`WS2D-OP-001`（運用手順書）§4を参照する。
- **依存関係のロールバック**（playwright等）: `spec-6-2`§4-3手順7（`git revert`→`pip install -r requirements-dev.txt`→`make setup-runtime`→`make doctor`→`make verify-all`）に従う。`.runtime`に旧Chromiumが残っていれば再ダウンロード不要。
- **ロールバック後の確認**: `make verify-all`がgreenであることを必ず確認してから、ロールバックの完了を宣言する。「revertしたから大丈夫」という推測での完了宣言はFunctional Integrity Gateの禁止事項に抵触する。
- **ロールバック判断の閾値**: 本番相当環境で致命的なエラー（データ損失・認証バイパス・全機能停止）が確認された場合は即座にrevertする。軽微な表示崩れ等はfix-forward（前進修正）を優先し、ロールバックは最終手段とする。この判断基準自体も本書執筆時点では明文化された既存ルールがなく、本改訂で新たに定義したものである。

## 7. リリースノートの書き方とテンプレート

コミットメッセージ規約（`WS2D-CS-001`§15）に対応させ、変更種別ごとに整理する。テンプレート:

```markdown
## リリースノート（YYYY-MM-DD）

### 新機能 (feat)
- <説明>（関連PR: #NNN）

### 修正 (fix)
- <説明>（関連PR: #NNN）

### 変更・改善 (refactor / perf)
- <説明。perfの場合は実測の効果量を必ず記載（例: 応答時間 X秒→Y秒）>（関連PR: #NNN）

### 削除・整理 (chore)
- <説明>（関連PR: #NNN）

### 既知の問題
- <未解決の問題があれば記載。無ければ「なし」>
```

perf種別の記載では、実測なしの主観的な「速くなった」という表現を避け、コミットメッセージの実例（「無反応1.8秒→0.14秒、実時間-37%」）のように必ず数値を伴わせる。リリースノートの言語は日本語とし、`WS2D-CS-001`のコミットメッセージ規約と一貫させる。

## 8. 配布物の内容

WebSpec2Docのリリース時の配布物（納品物）として想定されるもの:

- プロダクト本体（`src/`, `web/`, `app.py`, `static/`, `templates/`のソースコード一式、通常はgitリポジトリそのもの）。
- `docs/sdlc/`配下のSDLC文書一式。Markdown版に加え、対応するWord（`.docx`）・Excel（`.xlsx`）版が各文書に存在することを確認した（例: `WS2D-CS-001_コーディング規約.docx`, `WS2D-RD-001_要件一覧.xlsx`）。これらは`scripts/build_delivery_docs.py`（946行、`docs/sdlc/_asbuilt/`配下の`modules.json`・`routes.json`・`templates.json`・`licenses.json`・`schema.sql`等のas-builtデータを元に生成すると推定される）が生成する納品用ドキュメントと考えられるが、**本書執筆時点で当該スクリプトの実行フロー自体は検証しておらず、生成過程は推定であることを明記する**。
- OSSライセンス一覧（`WS2D-LI-001_OSSライセンス一覧`、`docs/sdlc/70_delivery/`）。
- トレーサビリティマトリクス（`WS2D-TM-001`、機械生成）。
- テスト結果報告書一式（`docs/sdlc/40_test/`配下）。

納品物の生成・同梱範囲は契約・顧客要件によって変わりうるため、本書は「何が存在しうるか」の一覧であり、個別案件ごとの必須／任意の判断は別途行う。

## 9. リリース記録の残し方

- マージコミット（PR番号付き）自体がリリース単位の一次記録である。`git log --oneline`で常に参照可能。
- リリース判定の結果は`WS2D-TR-001`（テストサマリレポート、`docs/sdlc/40_test/WS2D-TR-001_テストサマリレポート.md`）に記録する。
- 障害発生時は`docs/INCIDENT_POSTMORTEM.md`形式でインシデント記録を残す（`docs/DEFINITION_OF_DONE.md`違反時の対応と共通）。
- 2026-07-26に実施された全体テスト証跡（`docs/sdlc/40_test/zero-base-20260726/`）のような、ある時点でのゼロベース評価記録は、大きな区切りのリリース（メジャーな機能追加等）の際の参考パターンとして踏襲を検討する。
- リリースノート（§7のテンプレート）は、作成した場合`docs/sdlc/`配下または別途定めるリリースノート置き場に保存する。現状、専用の保存先ディレクトリは確認できておらず、運用として今後定める。

## 10. 承認フローと責任者

- 現時点の開発体制は単独開発者（`git log`のコミッター表記は`ma-garin`のみを2026-08-02時点で確認）。複数人でのレビュー・承認体制は**現状確認できず未確認**であり、体制拡大時は本章の改訂が必要になる。
- 実質的な承認フローはPRベース: (1)`code-reviewer`エージェントによる自動レビュー、(2)人間（開発者自身）による最終確認とマージ判断。
- 責任者: 開発チーム（現状1名）。緊急・ホットフィックス種別も含め、リリース可否の最終判断者は同一人物が兼務している。

## 11. リリース後の確認項目

- `make verify-ui`実行後、`.ui-verified`マーカーの内容（gitハッシュ・UIハッシュ・タイムスタンプ）を確認する。
- 本番相当環境（`FLASK_TESTING=1 WEBSPEC2DOC_ALLOW_LOCAL=1`でのローカル起動、または`scripts/demo.sh`によるデモサイト同時起動）で主要フローを実際に操作して確認する。
- `/metrics`（Prometheus形式エンドポイント）で異常値が出ていないか確認する（`observability`機能契約）。
- UI変更を伴うリリースの場合、ビジュアル回帰ベースライン（`tests/e2e/snapshots/*.png`、gitignore対象）を意図に沿って再取得したかを確認する。
- リリース後一定期間、CI（`spec-drift.yml`によるドリフト監視）の結果を監視し、意図しない仕様変化が検知された場合は`WS2D-DL-001`へ起票する。

## 12. 環境変数とシークレット管理

- 環境変数は`WEBSPEC2DOC_`プレフィックスで統一する（`docs/specs/CONVENTIONS.md`§2）。既定値は安全側に倒す（例: ローカルURL拒否、`WEBSPEC2DOC_ALLOW_LOCAL`未設定時は127.0.0.1等を拒否）。
- リリース・デプロイ時に確認が必要な主な環境変数: `WEBSPEC2DOC_AUTH_MODE`（利用者認証モード、既定`auto`）、`OPENAI_API_KEY`（LLM機能、未設定時はルールベースにフォールバック）、`WEBSPEC2DOC_LLM_BASE_URL`/`WEBSPEC2DOC_LLM_MODEL`（Ollama等の代替LLMエンドポイント指定）、`PLAYWRIGHT_BROWSERS_PATH`（Chromium格納場所、`.runtime/ms-playwright`固定）。
- シークレット（パスワード・APIトークン・`instance/secret_key`）は`.env`ファイルまたは環境変数で管理し、リポジトリにコミットしない。`.env`の変更は`web/env_store.py`が扱う。
- ローカル動作確認時は`FLASK_TESTING=1 WEBSPEC2DOC_ALLOW_LOCAL=1`を必ず付与して起動する。付与しないと`webbrowser.open`でブラウザタブが毎回増える（開発運用上の既知の注意点）。

## 13. 環境構築とヘルスチェック

リリース作業を行う開発環境自体の健全性を、リリース前に確認する。

- `make setup`: Python依存（`requirements-dev.txt`）・Chromium・git hookを一括セットアップする。
- `make setup-runtime`: Playwright対応Chromiumを導入し実起動確認する（`scripts/manage_playwright_runtime.py install`）。
- `make doctor`: 環境不一致（Pythonバージョン・依存パッケージバージョン・Chromiumランタイム・ローカルURLガード設定）を一括診断する（`src/doctor.py`）。「リモートやCIでは動くのにローカルで失敗する」場合はまずこれを実行する。
- `make check-runtime`: Chromiumの実起動確認のみを行う軽量版。

## 14. CI構成の概要

- `.github/workflows/ci.yml`: smoke・e2e-uiジョブを持つ。ubuntu-22.04に固定（playwright 1.44のOS依存が24.04と非互換のため、`spec-6-2`のコメントに明記）。`PLAYWRIGHT_BROWSERS_PATH`をワークスペース配下へ指定する。
- `.github/workflows/spec-drift.yml`: 登録済みサイトの定期的な再クロールによる仕様ドリフト監視（`ci_drift_monitor`機能契約）。`drift_summary.json`の生成とSlack通知（Webhook経由、`web/services/notifier.py`）を行う。
- 上記2ファイルの個別ジョブ内の詳細な合否条件（タイムアウト値・リトライ回数等）は本書執筆時点で全文を確認しておらず、**未確認**。次回のリリースプロセス監査で読み込むことを推奨する。

## 15. デモ環境での最終確認

- `make demo`（`scripts/demo.sh`）で同梱デモサイトと本体を同時起動できる。リリース前の最終動作確認や、新規参加者へのデモに使う。
- デモサイトのターゲットページ（`contact.html`, `dashboard.html`, `spa.html`, `checkout.html`）はE2Eテストの標的とも一致しており、手動確認とE2E自動確認の対象を揃えている。`login.html`はログインウォール検出の関係で標的から除外する。
- デモ確認後は、自分で起動したプロセス（デモサーバ・ブラウザタブ）を必ず終了させる。本体（ポート8765）は`verify-ui`実行後の状態に戻す。

## 16. 複数環境（マルチテナント）でのリリース考慮事項

- マルチテナント運用時、リリースの影響範囲はテナント横断になりうる。スキーマ変更（`instance/tenants/{slug}/viewpoints.db`等）はテナント数だけ存在するDBファイルすべてに影響するため、ロールバック手順（§6）はテナント単位でのDB復元も想定する。
- 管理コンソール（`web/routes/tenant_admin.py`）経由の設定変更はリリースそのものではないが、リリースに伴う設定変更（例: 新機能のデフォルト値変更）がテナントごとの既存設定と衝突しないかをリリース前に確認する。
- スナップショット保持ポリシー（`web/services/retention.py`）はテナント単位（`output/tenants/{slug}/`）で適用される。リリースによってポリシーのデフォルト値が変わる場合、既存テナントへの遡及適用の有無を明確にする。
- テナント分離の境界（`web/tenancy.py: scoped_output_dir`）を破る変更は、単一テナントへの影響ではなく全テナントへの影響として扱い、通常より慎重なレビューを行う。

## 17. パッケージング・配布形式の詳細

- Pythonアプリケーション本体はDockerイメージとしては配布しない方針（運用メモ: Docker利用は有償プランのみで検討）。配布はソースコード一式（gitクローンまたはzip）＋セットアップ手順（`make setup`）による。
- `docs/sdlc/_asbuilt/`配下の生成データ（`modules.json`, `routes.json`, `templates.json`, `licenses.json`, `schema.sql`）はas-built文書の元データであり、配布物にはこれらの生成データも含めるかを案件ごとに判断する。
- OSSライセンス一覧（`WS2D-LI-001`）は配布時に必ず同梱する（第三者ライブラリのライセンス条項遵守のため）。
- 配布物にテストコード（`tests/`）を含めるかは案件ごとに判断する。含める場合は`requirements-dev.txt`も同梱する。

## 18. リリース作業のロールと引き継ぎ

- 現状は単独開発者がブランチ作成からマージ・リリース後確認まで一貫して担当する（§10参照）。
- 体制拡大時のために、本書は各手順（§4のリリース手順11段階）を誰が実行しても再現できるよう、コマンドを省略せず記載する方針を取っている。属人化を避けるため、口頭伝承ではなく本書の更新によって手順を継承する。
- 引き継ぎ時に確認すべき最低限の情報: `.env`の内容（シークレットは別途安全な経路で共有）、`instance/`配下のDBバックアップ状況、直近のリリースノート（§7）、未解決のインシデント（`WS2D-DL-001`）。
- 新規参加者への引き継ぎは、`make demo`（デモ環境、§15）を使った一連の操作説明から始めることを推奨する。

## 19. リリース頻度と区切りの考え方

- 運用メモにより、「区切りごとにマージする（未マージの成果を溜めない）」方針を採用している。弾・フェーズ完成ごとにPR→CI→マージまでを完結させる。
- 大きな機能追加は複数の小さなPRに分割し、個別にリリース（マージ）する。1つの巨大なPRを長期間未マージのまま抱えることは避ける。
- テスト実行の頻度は「単体・結合は毎回、システム/受け入れ（E2E）は実装が落ち着いた区切りのみ」という運用に従う。開発速度を優先した判断であり、リリース前チェックリスト（§3）のE2E実行タイミングと整合させる。
- CIの完了を待って手を止める空待ちループは組まない。mainは保護なし運用のため、マージ判断の根拠はpush前のローカルでの`make lint && make test && make verify-ui`実行結果とする。

## 20. UI刷新期間中のリリース運用（`.rebuild-mode`）

`.githooks/pre-commit`は「刷新モード」という特殊な運用を許容している。リリース判定の前に必ず状態を確認する。

- UIを大きく作り替えている期間、毎コミットでのE2E実行を要求すると開発速度が著しく落ちる。そのため`.rebuild-mode`ファイル（理由を1行記載）を作成すると、UI変更時のE2Eゲートを一時的にスキップできる。
- ただし「スキップ＝問題なし」ではない。pre-commitは刷新モード中、「E2Eは未実行です。この状態は未検証であり問題なしではありません」という警告を毎回表示する。
- 刷新完了後は`make verify-ui`を実行してから`.rebuild-mode`を削除し、通常のE2Eゲートに戻す。
- **リリース判定（本書§4手順6〜8）の前に`.rebuild-mode`が残っていないことを必ず確認する。** 刷新モードのままリリースする（mainへマージする）ことは、実質的にDoD Type BのMANDATORY項目を満たさないままのリリースを意味する。

## 21. 障害時のコミュニケーション

- 本番相当環境で障害が発生した場合、`docs/INCIDENT_POSTMORTEM.md`形式での記録に加え、影響を受けた機能（`quality/feature_contracts.yml`の該当`feature_id`）を特定し、`WS2D-DL-001`（不具合管理台帳）に起票する。
- 障害の深刻度に応じて、§2のホットフィックス手順を適用するかを判断する。判断基準: 利用者のログイン・データ保存・クロール実行という中核機能が停止しているか（停止していれば即ホットフィックス対応）。
- 障害対応の詳細な連絡フロー・エスカレーション手順は`WS2D-TS-001`（障害対応手順書、`docs/sdlc/50_operation/WS2D-TS-001_障害対応手順書.md`）を参照する。本書はリリースプロセスの観点からのみ障害対応に触れる。

## 22. リリース種別ごとの想定所要時間（参考値）

正式な計測記録ではなく、§2の手順から見積もった参考値である。実測ではないため目安として扱う。

| 種別 | 主な作業 | 参考所要時間の目安 |
|---|---|---|
| 定期リリース | 実装＋フルゲート＋レビュー＋マージ | 機能規模に依存（未計測） |
| 緊急（バグ修正） | 修正＋フルゲート＋レビュー＋マージ | 数時間〜1日程度（未計測） |
| ホットフィックス | 最小修正＋MANDATORY確認＋マージ | 可能な限り最短（未計測） |

**この表の時間値はいずれも実測に基づかない目安であり、正式な計測記録として扱わない。** 実際の所要時間を計測する仕組み（コミット〜マージのリードタイム計測等）は本書執筆時点で存在せず、導入を今後の検討課題とする。

## 24. 用語の対応（本書固有）

| 用語 | 本書での意味 |
|---|---|
| フルゲート | `make lint`＋`make security`＋`make test`＋`make verify-ui`＋`quality_harness.py`＋`make coverage`の全項目 |
| MANDATORY項目 | pre-commitが機械強制する項目（構文・pytest・UI変更時のハッシュ照合） |
