## 1. 章別の抜き出し

### はじめに / 第1章 なぜ形式的手法が必要なのか
- 出典: [book]/introduction/ , [book]/chapters/chapter01/
- 要点
  - 事故分析（アリアン5, Therac-25, 737 MAX）の共通原因を「仕様の曖昧性・暗黙の仮定・局所最適・検証の不完全性」の4つに整理している。
  - 「水平速度」の取りうる範囲が文書上曖昧だったことがアリアン5の根因、という整理。
  - 従来手法の限界: テストは存在証明しかできず、静的解析は「何をすべきか」を分析できない。
  - 演習に「曖昧な3文のログイン仕様から10個以上の曖昧点を列挙し、解釈数と実装バリエーション数・リスク3段階を出す」課題がある（曖昧性の定量分析）。
- ツール機能への示唆
  - 曖昧点の検出結果を「曖昧箇所 × 解釈候補数 × リスク3段階」の表で出す機能は、そのまま商品の主画面になる。
  - 「暗黙の仮定」を独立した指摘カテゴリにする（未記載の前提・範囲・単位・例外）。
  - 引用: 「テストは正しさを証明するのではなく、特定の条件下での動作を確認するだけ」（第1.3節）。これは検証ツールの位置づけ文言（テストを置換せず補完）に使える。

### 第2章 数学とプログラムの橋渡し
- 出典: [book]/chapters/chapter02/
- 要点: 事前条件・事後条件・不変条件・状態遷移・部分/全正しさを、プログラマ向けの語彙に対応づけている。比較マトリクス（Alloy/Z/CSP/TLA+）あり。
- ツール機能への示唆
  - 自然言語仕様を「状態・入力・事前条件・事後条件・不変条件」の5枠に分解して表示するだけで、抜けが可視化できる。
  - 「事後条件では変更されるものと、されないものを両方書く」という指針は、書かれていない副作用の指摘ルールになる（2.2節, 3.3節）。

### 第3章 仕様記述の基本（最重要）
- 出典: [book]/chapters/chapter03/
- 要点
  - 自然言語の曖昧性を4分類: 語彙的・構文的・意味的・実用的（例「適切な時間内に」）。
  - 仕様書の実例3つを、疑問リスト（どの入力？どの検証？いつ？失敗時は？）に展開している。
  - 「典型的な要求仕様書で1ページあたり15〜20個の曖昧表現、重要機能要求の約30%が複数解釈可、非機能要求の約50%が定量基準を欠く」とあるが、出典は示されていない（数値は引用不可）。
  - 契約の構造（前提条件・義務・保証）、例外的事後条件、フレーム問題（何が変わらないか）。
  - 不変条件はデータ/ビジネス/システムの3階層に例示。設計原則は最小性・独立性・検証可能性・理解可能性・安定性。
  - スタック仕様の完全性チェックリスト5項目: 操作網羅・状態遷移網羅・エラーケース網羅・不変条件保持・操作間関係。
  - UML↔形式仕様の往復（選択的形式化）。
- ツール機能への示唆
  - 曖昧語辞書: 「適切に」「高い」「大きすぎる」「問題がなければ」等を検出し、疑問リスト（何が・どの程度・いつ・失敗時）を自動生成する。第3章の演習文（アップロード仕様）はそのままテストデータにできる。
  - 完全性チェックリスト5項目を、仕様書1件ごとの採点軸として採用できる（QuintSpect の5観点と対比可能）。
  - 例外系の事後条件が書かれていない操作（正常系のみの記述）を指摘する。
  - 引用: 「曖昧性の完全な排除には、より厳密なアプローチが必要です」（3.2節）。一方で「クリティカルな部分は形式的に、その他は自然言語」という段階的アプローチも明言しており、全文を形式化しない製品設計の根拠になる。

### 第4章 Alloy
- 出典: [book]/chapters/chapter04/
- 要点
  - 「軽量」とは完全証明を目指さず反例探索に寄せること。保証は「指定スコープ内で反例がない」に限られる、と繰り返し明記。
  - 反例の分類: 真の設計欠陥 / 要求の不明確さ / モデルの不完全性 / 想定外だが許容可能。この4分類を反例処理の標準にしている。
  - 反例が出たら「制約の過不足 → スコープ → 抽象度」の順に見直す。
  - 例: 「ファイルを読めるのは所有者のみ」という性質に対し、共有を許す構成が反例になり、要求の確認が必要と判明する。
  - Alloy 6 は var / 時相演算子 / `for N but M steps`。実行契約（manifest runner）で再現性を担保。
- ツール機能への示唆
  - 検証結果の4分類（欠陥/要求不明確/モデル不備/許容）はそのまま指摘のトリアージ列に使える。
  - 指摘に必ず「検査範囲（スコープ・前提）」を併記し、範囲外を「未検証」とする表示（A-5 の考え方と一致）。
  - 権限・ロール・所有の関係を持つ仕様（権限表、画面×ロール表）は Alloy 的な関係表に落として矛盾検出する構想が成立する。

### 第5章 Z記法（最重要）
- 出典: [book]/chapters/chapter05/
- 要点
  - 状態スキーマ（宣言＋不変条件）と操作スキーマ（Δ/Ξ、入力`?`、出力`!`、事前/事後）。
  - 正常ケースとエラーケースを別スキーマで書き、`∨` で合成して全入力を覆う（完全な操作定義）。エラー時は Ξ で状態不変を明示。
  - 「不変部分」の明示（他口座は変化しない）でフレーム問題を解消。
  - 設計原則: 関連変数を近くに置く、制約を論理順に、意味のある名前、複雑な制約は分割。
- ツール機能への示唆
  - 操作ごとに「正常系＋エラー系の和が全入力を覆うか」を検査する観点を採用できる（入力区分の網羅チェック）。
  - エラー時に状態が変わらないこと（ロールバック・副作用なし）の記載有無を指摘する。
  - 画面仕様書でも「項目＝状態変数、制約＝不変条件、ボタン＝操作」の対応で、同形の抽出ができる。

### 第6章 CSP
- 出典: [book]/chapters/chapter06/
- 要点: 並行・同期の記述。デッドロック4条件（相互排除/保持と待機/非プリエンプション/循環待機）、活性、公平性、バッファ、タイムアウト付き通信。
- ツール機能への示唆: 文書検証としては優先度低。ただし「承認フロー・排他制御・ジョブ連携の記述で、循環待機や待ち状態の出口が書かれていない」ことを指摘するルールに転用できる。

### 第7章 TLA+
- 出典: [book]/chapters/chapter07/
- 要点
  - 安全性（悪いことが起きない）と活性（良いことがいつか起きる）の区別、公平性。
  - CAP/FLP を「結論ではなく、モデル・故障・通信仮定・保証対象の組」として読め、と説く。
  - TLC のシミュレーションで反例がなくても証明ではない。リリース判断では「検証済み」と書かず `simulation-no-violation-observed` と実行条件を記録せよ。
  - 導入経路表: Toolbox / VS Code / CLI TLC / Apalache / Quint。CI には .cfg・seed・workers・timeout を固定。
- ツール機能への示唆
  - 要件を「安全性（してはいけない）」と「活性（いつか必ず）」に分類してタグ付けし、片方しか書かれていない機能を指摘する。
  - 結果表示は「検証済み／未検出／未完走／タイムアウト」を区別（成功と混同させない）。第8章の「timeout・unknown・資源枯渇は成功ではない」と同趣旨。

### 第8章 模型検査（前半を全文、後半は抽出）
- 出典: [book]/chapters/chapter08/
- 要点
  - 模型検査の保証はモデル・性質・探索方式・設定の範囲に限る。検査報告にモデル/性質/ツール版/fairness/探索境界/近似モード/timeout/終了状態を含めよ。
  - 抽象化の副作用（検出力低下）と境界づけの副作用（偽陰性）を理解確認問題にしている。
  - 反例の解剖: トレース/状態情報/遷移/時刻。根本原因分析は4段（症状→前提条件→タイミング→設計判断）。偽の反例（Spurious）への対処、反例の最小化（二分探索・因果関係分析・状態投影）。
  - 確率的模型検査（PRISM）は、教育用の仮定（成功確率0.8・独立）を実システムの信頼性主張に使うなと注意。
  - 後半（抽出のみ）: 「検証手法を方式名ではなく完走条件と未検査範囲で比較する」「モデルの証跡をテスト・監視・実装レビューと接続する」。
- ツール機能への示唆
  - 指摘カード（反例）の固定項目: 再現手順（最短）/事実/仮説の分離/検査範囲/未検査範囲。
  - 「偽の指摘」対処のために、利用者が「許容」「前提が違う」を選べ、その理由が次回検査に反映される仕組み。

### 第9章 定理証明（前半を全文、後半は抽出）

### 付録F AI 支援の実践ガイド（最重要・全文）
- 出典: [book]/appendices/appendix-f/
- 要点
  - 信頼境界: LLM/エージェントは提案者（untrusted）、検証器は判定者（trusted）、CI は執行者。この境界を崩すと AI の誤りが品質保証の誤りに直結する。
  - 再検査フロー: LLM → 人間の要件・用語・encoding レビュー → solver/prover → model/witness または proof certificate → strict checker → CI artifact → 人間レビュー。checker が見るのは encoded statement であり、自然言語要件・元仕様・エンコーダ・未モデル化仮定そのものではない。
  - ワークフロー: 要求（目的/禁止事項）→ 用語定義 → 不変条件 → 小スコープモデル化 → 反例確認 → 修正 → 再検証。
  - 反例トリアージテンプレ（F.8）: 検証対象/実行環境（事実）/再現手順（事実）/観測された事実/仮説/修正案/再検証、で事実と仮説を分離。
  - AI 生成物 QA チェックリスト（F.9）: 用語定義、前提条件、不変条件、活性、数値の出典。証明/模型検査の再現性（スコープ・seed・上限時間）、CI ゲート設計。
  - F.12: 仕様差分/テスト差分/検証差分/レビュー差分の4種類の責務分界と PR 証跡。「どちらか一方だけを品質保証の最終根拠にしない」。
  - F.13: LLM による「違反0件」という文は monitor 出力の代替にならない。欠落イベントを補完生成させず、不明は不明として残す。個人情報等を含む生ログは外部 LLM に送らず、最小化・匿名化を先に行う。
- ツール機能への示唆
  - AI が出した指摘に「根拠（原文の該当箇所）」「事実/仮説の区別」「確信度」を強制付与する。F.8 のテンプレを指摘カードの内部構造として採用できる。
  - AI 判定を最終判定にせず、決定的な検査（用語表記ゆれ・数値整合・ID参照整合）は機械、解釈が要る指摘は人が確認、の二層構造。
  - 外部 LLM へ送る前のマスキング機能（個人情報・機密）。QuintSpect の「入力データは学習に使われない」説明より一段強い「送る前に削る」を訴求できる。
  - PR 添付用の「検証サマリ（変更仕様・検査範囲・未検証範囲・例外承認）」の自動生成。

### note B: Z言語（Z記法）入門（2026/10/06）
- URL: https://note.com/yuki_magari/n/na629587e426f
- 要点
  - Z言語は集合と論理で仕様を書く記法でプログラム言語ではない。ISO/IEC 13568:2002 が書き方・型・意味を定める。利用場面（どの開発工程でどう使うか）は規格の範囲外。
  - 読み方: スキーマ上段＝宣言、下段＝述語。`?`入力、`!`出力、`′`操作後、`Δ`前後の状態、`Ξ`前後で不変。正常/異常を別スキーマにして「または」で合成。
  - 限界: 型検査で分かるのは書き方の整合まで。fuzz は規格以前の解説書に基づき、規格には対応していないと作者が明記。道具ごとに受け付ける記法が違う。
  - 例題から出る答え: 残高ちょうど（500で500）も0ポイントも「使える」と決まる。
- ツール機能への示唆
  - 自然言語の疑問（0は可？ちょうど全額は？）を、仕様の式に直したときの答えとセットで提示する「疑問→確定値」表示。
  - 「道具によって受け付ける書き方が違う」ことへの備え（出力形式を特定の処理系に固定しない、対応版を明記する）。

## 3. QuintSpect（バルテス）全文読了

- URL: https://service.valtes.co.jp/quintspect/（2026年9月時点の記載）
- 機能（3つ）
  1. 通常分析: 5観点（正確性・理解性・視覚性・深層性・信頼性）で文書を採点し改善点をコメント付きで出力。自社のレビューチェックリスト・設計書標準を「カスタム観点」として登録可能。
  2. 矛盾検知: 複数の設計書を突き合わせ、記載の食い違いを一覧出力。
  3. 抜け漏れ検知（NEW）: 要件定義書を基準に設計書・テスト仕様書への反映を1件ずつ判定。トレーサビリティマトリクスと完全率を出力。
- 活用シーン: 設計書完成時（自社基準チェック）、設計書が揃った時（要件反映と矛盾の確認）、工程移行前（完全率とスコア＝判断材料）。例に、協力会社分担の設計書突き合わせ、公共案件の電子納品、組み込みの改版ごとのトレーサビリティ確認、ベンダー納品物の受入確認。
- 汎用AIとの違いの訴求: 観点を一度登録して毎回同じ基準でチェック、スコア・マトリクスで出力、改版前後の変化がひと目で分かる。
- 技術・運用: 2026年9月時点で Gemini を利用（API経由でファイル送信、オプトアウト設定により学習利用なし）。ファイルは国内 Google Cloud Storage、保存時・通信時とも暗号化。IPホワイトリスト対応。
- 入力仕様: Excel（.xlsx/.xls）・PDF・Markdown（UTF-8のみ）。1ファイル最大10MB。同時選択10ファイル、予約は通常分析＋矛盾検知で最大5件。
- 権限: テナント管理者/管理者/一般/ゲストの4種。同一テナント内でも他人のファイル一覧・予約・結果・カスタム分析設定は見えない。

- 契約条件: 銀行振込のみ、全期間一括請求、中途解約・返金不可、下位プランへは期間満了後、契約終了後90日はログイン可で以後データ削除、トライアルは1回限り。
- スコアの出し方: 「品質評価指標の観点内容と重要度設定」で算出（FAQ）。算出式の詳細は非公開。
- ツール機能への示唆（競合分析）
  - 競合は「AIレビュー（観点採点・矛盾・抜け漏れ）」の領域。当社が差別化するなら、(1) 指摘ごとの原文根拠と事実/仮説の分離、(2) 検査範囲と未検証範囲の明示、(3) 機械で決められる検査（ID・数値・参照の整合）は決定的処理で再現性を担保、(4) Web仕様（画面・API・実機）との突き合わせ。

## 5. 商用化への統合示唆（まとめ）

1. 検査対象を「書かれた決定」に寄せる: 暗黙の仮定・境界・上限を明示させ、持ち主の承認を取る（note A、第3章、第4章）。
2. 検査結果の意味を限定表示: 検査範囲・前提・未検証を毎回出し、成功と未完走を区別する（第7〜8章、付録F）。
3. AI を判定者にしない: 提案者として使い、決定的検査・人間確認・証跡で閉じる（付録F.2, F.9, F.13）。
