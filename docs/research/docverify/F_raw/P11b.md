# P11b 自動レビュー・静的解析の受容と誤検知

## 結論（3 行）
1. 誤検知が採用の最大の障壁という点は実証済み（Johnson 2013、n=20 の面談）。ただし「約 10% を超えると使われなくなる」という閾値の一次出典は今回確認できず、サーベイによる二次的な言及のみ。
2. 産業の AI レビューで確認できた数値は、Google の ML コメント解決の提案適用率 40〜50%（目標適合率 50% で校正）と、LinkedIn の 63.9%（二次情報）のみ。Microsoft は規模（月 60 万 PR 超・PR の 90% 超）のみで受容率は非公開。
3. ハルシネーション対策は「根拠への接地を判定する検証器」（HalluJudge、F1=0.85）が最も近い実証。根拠引用の義務化そのものを検証した査読論文は今回の検索では見つからなかった（未確認）。

## 発見

### 1. Sadowski ら Tricorder（ICSE 2015）／Lessons from building static analysis tools at Google（CACM 2018）
- 著者／年／誌: Sadowski, Aftandilian, Eagle, Miller-Cushon, Jaspan ／ 2015・2018 ／ ICSE 2015・CACM
- 手法: Google の全社コードレビューに組み込んだ解析基盤。「Not useful」ボタンで開発者が指摘に印を付け、誤検知を測る。CACM 版で「effective false positive」（開発者が指摘を見て是正行動を取らなかったもの。可読性・保守性のための修正は含めない）を定義。
- 区分: 定義は実証（検索結果の要約で確認）。「約 10% 方針」は **未確認**。2026 年の arXiv サーベイが「約 10% 超の解析器は日常的に無視・無効化された」と Sadowski らに帰属させているが、原文では確認できなかった。CACM の PDF は取得できたが本文を抽出できなかった。
- URL: https://research.google/pubs/tricorder-building-a-program-analysis-ecosystem/ ／ https://6826.csail.mit.edu/2020/papers/google-analysis-cacm.pdf ／ 二次: https://arxiv.org/pdf/2604.27000

### 2. Johnson, Song, Murphy-Hill, Bowdidge（ICSE 2013）
- 題: Why Don't Software Developers Use Static Analysis Tools to Find Bugs?
- 手法: 開発者 20 名への面談。
- 結果: 全員が静的解析は有益と答えたうえで、誤検知と警告の提示方法が利用の障壁だった。具体的な誤検知率の閾値は報告されていない（確認した範囲）。
- 区分: 実証（質的、n=20）。
- URL: https://research.google/pubs/pub43477/ ／ https://cs.gmu.edu/~johnsonb/docs/icse2013.pdf

### 3. Google: Resolving code review comments with ML（Google Research ブログ、2023-05-23）
- 数値: モデルは目標適合率 50% で校正。オフラインで人のレビューコメントの 52% を対象にできる。プレビューされた修正提案のうち 40〜50% が作者に適用される。プレビュー率はベータ約 20% から、ボタン追加後の公開時に約 40%。目標適合率を上げると提案は減り、下げると誤提案が増える。
- 区分: 企業ブログの主張（実測値だが査読なし）。12 週間 A/B の生産性結果は未掲載。
- URL: https://research.google/blog/resolving-code-review-comments-with-ml/

- 受容率・誤検知対策: 掲載なし。
- 区分: 主張（企業ブログ）。ZenML の要約経由で取得し、原文は未取得。

### 7. HalluJudge（Tantithamthavorn ら、2026、FSE'26 Industry Track）
- 手法: コードレビューコメントがコードに接地しているか（文脈整合）を、参照なしで判定する。直接判定から Tree-of-Thoughts まで 4 方式。Atlassian の企業プロジェクトで評価。
- 結果: F1=0.85、1 判定あたり約 0.009 ドル、本番の開発者の好みとの一致 67%。データ件数は未取得。
- 区分: 実証（産業・査読通過）。
- URL: https://arxiv.org/abs/2601.19072

### 8. LLM のレビュー判定の過剰訂正（arXiv 2603.00539、2026）
- 結果: 正しいコードを誤って却下する傾向がある。修正して再テストする検証フィルタで、GPT-4o の偽陰性率が HumanEval で 70.7% から 23.2% に下がり、偽陽性率は 0.0% から 1.8% に上がる（Table 4）。
- 区分: 実証。ただしコード対仕様の判定タスク。
- 関連: arXiv 2508.12358（ASE'25）は、複雑なプロンプトが誤判定を増やし得ると報告。
- URL: https://arxiv.org/pdf/2603.00539 ／ https://arxiv.org/pdf/2508.12358

### 9. 検証付きコード推論（arXiv 2509.26546）
- 結果: 20 例の小規模検証で、エージェントがハルシネーションを起こした 8 件中 6 件を検証器が検出。検証器自身の誤出力もあった。
- 区分: 実証だが n が小さい。因果は断定しない。
- URL: https://arxiv.org/pdf/2509.26546

## 勝つための示唆
1. 製品の設計目標を「誤検知率 X% 以下」と置くなら、自社の実測で決める。外部の 10% は根拠が未確認。Tricorder 方式の「Not useful」ボタンと effective false positive の計測を最初から入れる。
2. 指摘は少数・高確度に絞る。Google は目標適合率を上げると提案数が減ると明記しており、適合率と網羅率のトレードオフを設定として持たせる。
3. 全指摘を「引用した原文の箇所」に接地させ、接地を判定する第二段（HalluJudge 型）で落とす。判定コストは 1 件 0.01 ドル程度で、商用でも採算が合う。
4. 受容率は「マージ後に実際に反映されたか」で測る（LinkedIn の定義）。種別（正確性・矛盾・曖昧さ）ごとに受容率が違う前提で、受容の高い種別から出す。
5. 日本語の要件・設計文書での産業データは今回ゼロ。受容率の公開数値が無いことは、初期顧客での実測値そのものが差別化の根拠になる、という意味でもある。
