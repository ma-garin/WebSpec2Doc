## 結論（3行以内）

- 一次資料で確認できた産業・学術事例（Getafix / Repairnator / Tricorder）に共通するのは「パッチ生成は自動、マージ・適用の可否判断は必ず人間」という一点。自動マージまで行った一次資料は本調査では見つからなかった。
- Repairnator は「5 件のパッチが人間開発者に受理され恒久的にマージされた」ことのみ一次資料（arXiv）で確認できた。生成総数・却下率は未確認。

## 各事例の要点

### 1. SapFix / Sapienz
- 何を自動化したか: 一次資料に到達できなかったため詳細は未確認。一般に流布している説明（Sapienz がクラッシュ再現テストを自動生成し、SapFix がルールベース＋人間の過去修正の学習に基づき候補パッチを生成する、という構成）は本セッションでは検証できていない。
- **人の判断ゲートの位置**: 未確認（本セッションで一次資料に到達できず、この項目は空欄扱いとする）。
- 実測値（あれば。無ければ「未取得」）: 未取得。
- 本件への含意: 一次資料未到達のため、本件の設計判断の根拠としては使わない。追加調査が必要な項目として明記する（後述「見つからなかったもの」）。

### 2. Getafix
- 何を自動化したか: 過去の人間による修正の差分をクラスタリングし、静的解析の警告に対する「人間らしい」修正候補を自動提案する。「Getafix is the first industrially-deployed automated bug-fixing tool that learns fix patterns from past, human-written fixes」（一次資料より引用）。
- **人の判断ゲートの位置**: 抄録には自動適用の記述がなく「fixes in time proportional to static analysis results」と、静的解析結果と同じタイミングで提案する設計が読み取れる。ただし提示先（コードレビュー画面か別UIか）・自動適用の有無は取得した抜粋に記載がなく未確認。
- 実測値: Top-1 的中率 12%〜91%（バグカテゴリ依存）、Top-5 候補内に正解を含む割合 526/1268件（41.5%）。社内デプロイ済みである旨は一次資料で確認。受容率・マージ率は未確認。
- 本件への含意: 「提案候補と人間の意図した修正が一致した率」を追跡指標として使う発想はそのまま流用できる。本件でも「AI 修正案が人間の最終判断（承認/却下）とどれだけ一致するか」を運用後にログとして残す価値がある。

### 3. Repairnator
- 何を自動化したか: OSS プロジェクトの継続的インテグレーション（CI）で発生するビルド失敗を常時監視し、自動でパッチ候補を生成・検証するボット。「Repairnator is a bot. It constantly monitors software bugs discovered during continuous integration of open-source software and tries to fix them automatically.」（一次資料より引用）。
- **人の判断ゲートの位置**: 生成したパッチは通常の GitHub Pull Request としてプロジェクトに提出され、プロジェクトの人間メンテナが既存の PR レビュー手順の中で採否を判断する。自動マージの記述はない。
- 実測値（あれば。無ければ「未取得」）: 「5 patches that were accepted by the human developers and permanently merged in the code base」（arXiv:1810.05806 で確認）。生成した総パッチ数・却下率・レビューにかかった時間は、本セッションで取得した抜粋には含まれず未確認。
- 本件への含意: 本件の要件（検証→バグレポート化→修正→PR作成→人間が画面上で承認/却下/マージ）と構造が最も近い先行事例。「生成物を通常の PR フローに乗せ、マージ判断を完全に人間に委ねる」という設計そのものが、本件の要求仕様と一致している。

### 4. Tricorder
- 何を自動化したか: 複数の静的解析ツールをコードレビュー基盤（Critique）に統合し、レビュー時にインラインで警告・指摘を提示するプラットフォーム。修正パッチの自動生成そのものよりも、分析結果を開発者のワークフローに違和感なく統合することが主眼。「these tools can be difficult to smoothly integrate with each other and into the developer workflow」という課題意識から出発（一次資料より引用）。
- **人の判断ゲートの位置**: コードレビュー時に開発者が個々の指摘を見て対応するかどうかを判断する、という設計思想が抄録から読み取れるが、具体的な採否UI・自動非表示の仕組み等の詳細は取得した抜粋になく未確認。
- 実測値: 「an empirical, in-situ evaluation」でGoogle開発者への有用性を確認、との記載のみ。具体的な受容率・却下率・警告表示件数などの数値は未確認。
- 本件への含意: 「指摘が多すぎると無視される」問題に対し、既存のレビュー導線（本件では GitHub PR 画面）にそのまま溶け込ませる設計は参考になるが、定量的根拠として引用できる数値は本セッションでは得られなかった。

## 自動生成パッチが受け入れられる条件（研究知見）

一次資料で定量的に確認できたのは Repairnator の「人間開発者に受理・マージされたのは 5 件」という事実のみ。受理率・却下理由・差分サイズやレビュー負荷との相関を論じた一次資料には、Semantic Scholar Graph API が本セッションを通じて継続的に HTTP 429（レート制限）を返したため到達できなかった。この論点は**未確認**として扱う（捏造を避けるため、一般に流布している「差分が小さいほど・説明が付くほど受理されやすい」という言説はここでは採用しない）。

## 自律エージェントの安全設計パターン

| パターン | 何を防ぐか | Docker 無しで実現できるか | 本件への適用 |
|---|---|---|---|
| git worktree による作業ツリー隔離 | 複数修正エージェントの同時書き込み競合・本流ブランチの汚染 | できる（本リポジトリの `speed-harness.md` が同じ手法を既に採用） | 修正エージェントごとに独立した worktree を割り当て、main ブランチには直接触れさせない |
| ブランチ保護＋PR必須化（直push禁止） | 人間承認前のマージ・意図しない巻き戻し | できる（GitHub 側のリポジトリ設定のみで実現、Docker 無関係） | 修正結果は必ず PR として提示し、マージ操作は人間だけが行える状態にする |
| 最小権限のプロセス実行ユーザー／トークンスコープ | 過剰な権限による意図しないファイル破壊・外部送信 | できる（OS のユーザー権限、GitHub PAT の権限スコープ制限で実現） | 修正エージェント用の GitHub トークンはリポジトリ単位・PR作成権限のみに絞る |
| 破壊的コマンドの許可リスト外し（`reset --hard` / force push / `rm -rf` 等の禁止） | 暴走時の不可逆な損害 | できる（シェルラッパー・フックで物理的にブロック） | 修正エージェントの実行環境にも同種の禁止フックを適用する |
| 監査ログ（誰が・いつ・どのテスト失敗から・どのパッチを生成したか）の必須記録 | 事後追跡不能・責任の所在不明 | できる（git のコミット履歴＋PR本文＋実行ログファイルで代替可能） | 各修正 PR の本文に「どのテスト失敗から・どの解析結果に基づき生成したか」を機械的に埋め込む |
| 差し替え可能な並列エージェント＋タイムアウト／ツール実行回数上限 | 1エージェントの暴走・無限ループによるリソース枯渇 | できる（プロセスタイムアウト・ツール実行回数上限で代替可能） | 本件要件の「並列・差し替え可能」に直接合致。エージェント単位で実行回数上限を設ける |

（本節は一次資料の実証というより、確認できた各事例＝git worktree 隔離・PRベースのレビュー・最小権限運用に共通する設計原則を整理したものであり、個別の定量的根拠を伴う主張ではない。）

## 本件の設計に効く教訓

1. **「人間が最終承認する場」は既存のレビュー導線に乗せる**: Repairnator（PRレビュー）・Tricorder（コードレビューのインライン指摘）はいずれも新しい承認UIを作らず、開発者が既に使っている画面に統合している。本件も「GitHub の PR 画面」を承認ゲートにする現行設計は、確認できた先行事例の構造と一致する。
2. **自動化の範囲は「生成・検証」までで、「マージ」は一次資料上どの事例でも人間側に残されている**: 自動マージまで踏み込んだ一次資料は本調査では見つからなかった。本件も「マージは常に人間」を仕様として明文化し、緩めない。
3. **Docker が使えない前提での隔離は git worktree ＋ OS 権限管理で代替可能**: 確認した安全設計パターンのいずれも Docker を必須としていない（本リポジトリ自身が worktree 隔離を既に運用中）。ただし「隔離した上でどこまでの権限をエージェントに与えるか」を定量的に論じた一次資料（受容率・侵害事例数など）は本調査では確認できていない。
