1. なぜURLだけでテスト設計ができるのか

「仕様書がないのにテスト設計なんてできるのか」と思うかもしれません。できます。 理由はひとつで、画面のHTMLが、仕様の一部をすでに持っているからです。

この1行から、確認しなければならないことが機械的に決まります。

  • required があるので「空のまま送信したらどうなるか」を確かめる必要がある
  • maxlength="4" があるので「3文字・4文字・5文字」を確かめる必要がある
  • pattern があるので「数字3〜4桁のときと、そうでないとき」を確かめる必要がある

これは意見ではなく、属性から一意に決まる変換です。だからルールとして書き下せるし、 書き下せばAIに毎回同じ結果を出させられます。元ツールがやっているのは、この変換を 画面全体・サイト全体に広げて、抜けなく回すことです。

全体の流れ

チャットで再現するときも、この順番を崩さないほうが精度が出ます。 まとめて「テストケースを作って」と頼むと、AIは途中の段を飛ばして"それっぽい表"を作ります。

元ツールとチャット版の違い

  • 元ツール → ブラウザを実際に動かして観測する（ログイン後・モーダル・SPAの状態も取れる）
  • チャット版 → あなたが渡した材料の範囲でしか見えない

つまり材料の質がそのまま成果物の質になります。だからこの記事は、プロンプトより先に 「入力の作り方」に紙面を割いています。

何が確認できて、何が確認できないのか

HTMLから読み取れるのは、あくまでクライアント側の制約だけです。 サーバ側の業務ルール（「与信枠を超えたら断る」など）はHTMLに現れません。

ここを曖昧にしたまま表を作ると、「テストケースはあるのに、肝心の業務ルールが抜けている」 という一番まずい状態になります。後述の P11（未確認領域の棚卸し） は、そのための プロンプトです。飛ばさないでください。

2. 使い方（3ステップ）

  1. 材料を用意する — 対象画面のHTML（またはフォーム項目のJSON）をコピーする → 「3. 入力の作り方」
  2. プロンプトを貼る — P0（共通ルール）＋ 使いたいプロンプト＋材料、の順で1メッセージにして送る
  3. 監査する — 新しいチャットを開いて P13 を実行し、抜け漏れを潰す

初めての人はこの3本から: P2（画面仕様化） → P4（テスト条件） → P9（テストケース表）

3. 入力の作り方（ここが8割）

チャットのAIはURLを渡しても中身を見に行けないことがあります。見に行けても、ログイン後の画面やJSで描画される画面は取れません。 なので「AIに渡す材料」を自分で用意します。難しい作業はありません。

方法1: ページのソースを渡す（推奨・1分）

  1. 対象画面をブラウザで開く
  2. Ctrl+U（Mac は ⌘+Option+U）でソース表示
  3. 全選択してコピー → チャットに貼る

方法2: 表示中のDOMを渡す（SPA・ログイン後はこちら）

  1. F12 で開発者ツール → Elements タブ
  2. 一番上の <html> を右クリック → Copy → Copy outerHTML → 貼る

方法3: フォーム項目だけをJSONで渡す（軽くて実用的・おすすめ）

開発者ツールのコンソールに以下を貼って実行。クリップボードにJSONが入ります。

方法4: スクリーンショットを渡す

撮って貼るだけ。ただし桁数・必須・正規表現は写真からは読めません。 この場合は必ず P11（未確認領域）を併用してください。

渡す量の目安

  • 1回のチャットで 1画面ずつ。まとめて渡すと精度が落ちます
  • HTMLが数千行あるときは <form> の中身だけを切り出す
  • 画面が10枚以上あるなら、まず P1 で画面一覧を作り、優先度の高い画面から個別に深掘りする

機密の扱い（必読）

社内システムのHTMLには実在の氏名・メール・IDが含まれます。 貼る前に置換するか、会社が許可したAI環境（法人契約のChatGPT/Claude等）を使ってください。 個人アカウントの無料プランに社内画面のHTMLを貼るのは避けます。

4. AIに任せてよい部分／だめな部分

このプロンプト集は、AIを「賢い相談相手」ではなく変換機として使います。 線引きをはっきりさせておきます。

  • 任せてよい: 機械的な展開 → 属性からの条件生成、境界値の算出、組み合わせの列挙、表の整形、文面の定型化
  • 任せてよい: 抜けの指摘 → 「この観点が漏れている」の列挙（採否は人が決める）
  • 任せてはいけない: 仕様の断定 → 「この項目は必須のはず」「エラーメッセージはこうなるはず」
  • 任せてはいけない: 合否の判定 → 生成物は設計インプット。実行結果ではない
  • 任せてはいけない: 未観測の穴埋め → 材料に無い項目・値・画面を作らせない

AIが一番やらかすこと

「それらしい嘘」です。 maxlength が書かれていない項目に「最大50文字」と決めつけて境界値を作る。 実装依存のエラーメッセージ文言を、さも仕様であるかのように期待結果に書く。

元ツールはこれを設計で潰しています。根拠のない値は出力しない（evidence-only）という原則です。

  • 実測した属性から導いたものだけを確信度 1.0 とする
  • 正規表現から例を作ったら、その例が本当にマッチするか自分で検算する。破れたら値を捨てて「例生成不能・手動作成要」と書く
  • 打ち切り・未確認・被覆していないことを、必ず出力に載せる

プロンプト側にも同じ制約を移植してあります。P0 の「守ること」を削らないでください。 削ると出力は増えますが、増えた分がそのまま嘘になります。

6. 30分ハンズオン: 1画面を最後まで通す

読むだけだと身につきません。手元の画面を1つ選んで、この通りに進めてください。 題材は入力欄が3〜6個あるフォーム画面が最適です（お問い合わせ、申込、検索条件など）。

0〜5分: 材料をとる

対象画面を開き、「3. 入力の作り方」の方法3（フォーム項目だけをJSONで渡す）を実行します。 コンソールに貼って Enter、それだけです。取れたJSONをメモ帳に置いておきます。

5〜10分: 画面仕様にする（P2）

新しいチャットを開き、P0 + P2 + さきほどのJSON を1メッセージで送ります。

ここで必ず確認すること: 出てきた表の項目名が、JSONに実在するものだけか。 1つでも見覚えのない項目があれば、その時点でプロンプトが効いていません。P0を貼り忘れています。

10〜15分: テスト条件にする（P4）

同じチャットで P4 を送ります（材料は「さきほどの表」と書けば足ります）。

ここで必ず確認すること: maxlength があった項目に「最大長: n-1/n/n+1文字」が出ているか。 出ていなければ、変換ルールの表を削ってしまっていないか確認します。

15〜22分: テストケース表にする（P9）

同じチャットで P9 を送ります。ここで初めて「手順」と「期待結果」が付きます。

ここで必ず確認すること: 手順に、対象項目以外の必須項目を埋める行があるか。 これが無いテストケースは実行できません（必須エラーで弾かれて、確かめたい境界値まで届かない）。

22〜27分: 未確認領域を出す（P11）

同じチャットで P11 を送ります。この出力が、そのまま開発への質問リストになります。

27〜30分: 監査する（P13）

新しいチャットを開いて P13 に、さきほどの成果物と元のJSONを貼ります。 自分で作ったAIに採点させると甘くなるので、必ずセッションを分けます。

慣れてきたら

  • 画面が多いときは、先に P1 でサイト全体の画面一覧を作り、優先度の高い画面から回す
  • 組み合わせが多い画面は P6（デシジョンテーブル）と P7（ペアワイズ）を追加する
  • 検索・一覧画面は P10（メタモルフィック）が効きます。期待値が書けない画面の切り札です

A. 属性 → テスト条件文

B. 属性 → 境界値の具体値

種別発火条件生成値件数
最大長maxlength>0n-1(受理)/n(受理)/n+1(エラー)3
最小長minlength>1m-1(エラー)/m(受理) ※m≦1では作らない2
範囲number,range で min/max 両方が整数min-1/min/max/max+14
パターンpattern あり適合例/不適合例（作れなければ1件だけ「例生成不能」）1〜2
必須required=true空文字→エラー1
選択肢options あり先頭/末尾/（任意項目のみ）未選択2〜3

長さの値は半角 "a"×n。1000文字超は実値を書かず「（a を N 文字・実値は長さのため省略）」と記す。 テストケース表（P9）の手順に展開するときだけ、読みやすさのため全角「あ」に置き換える。

テストケース表を作る経路の境界値は件数が異なるので注意してください。 最大長は「上限ちょうど n 文字（有効）／上限超過 n+1 文字（無効）」の2件、 最小長は「下限ちょうど m 文字（有効）／下限未満 m-1 文字（無効・m-1≧0 のときのみ）」の2件です。 n-1 を含む3件を作るのは、上の表（境界値の値表・P5）の経路です。

自己検算ゲート: 適合例が実際にマッチし、不適合例がマッチしないことを必ず検算する。 破れたら値を捨てて「（例生成不能・手動作成要）」に倒す。→ 値をでっち上げることが構造的に不可能になる。 境界値の適合例／不適合例を作れる正規表現は次の4形だけです。これ以外は手動作成に回します （対象項目以外を埋める代表値には、別の対応表があります）。

正規表現の形適合例不適合例
[0-9]{n}"1"×n"1"×(n-1)（n=1なら "a"）
[0-9]{lo,hi}"1"×lo"1"×(lo-1)（lo=1なら "a"）
[0-9 ]{lo,hi}"1"×lo"a"×lo（桁数は合わせ文字種で外す）
`(0[1-9]\1[0-2])/[0-9]{2}`12/2813/28

F. 画面の同定（重複排除）

  • URL正規化: スキーム/ホストは小文字、末尾スラッシュ除去、フラグメントは破棄、クエリは保持
  • 同一URLでも「モーダル/タブが開いている状態」は別状態として扱う
  • 判定は類似度ではなく完全一致（URL＋landmark構造＋開閉状態のハッシュ）
  • 項目名の突き合わせだけは類似度を使い、閾値0.6未満は不一致とする

8. よくある失敗と対処

症状原因対処
それらしいが実在しない項目が出るHTMLを渡さず画面名だけで頼んだ材料を必ず添付。P0の「創作しない」制約を消さない
桁数の境界値が出ないmaxlength がHTMLに無い（サーバ側検証）P11で「制約は未観測」として出させ、開発者への確認事項に回す
正規表現の値が間違っているAIが検算していないP5の自己検算ゲートを削らない
テストケースが大量すぎる組み合わせ爆発因子8・ケース20の上限を明示（元ツールの既定値）
全画面が別画面として扱われるクエリ違いだけの同一画面正規化ルール（F）を指定
出力が毎回変わる採番と並び順が非決定的「画面IDは登場順にP001から」「項目は入力順を維持」「乱数を使わない」と明示
期待結果が実際と食い違うエラーメッセージの文言に依存させた「文言は実装依存。表示の有無で判定」に書き換える
maxlength超過なのに送信できてしまうブラウザが入力を切るため送信自体は成功する期待結果を「送信されない」ではなく「入力値の長さがn文字に制限される」にする
「テスト済み」と誤解される生成物は設計インプットであって実行結果ではない冒頭の免責文を必ず入れる

心得（AI初心者向け）

  • 出てきた表をそのまま提出しない。 これは下書きです。レビューはあなたの仕事です
  • 1つのチャットで欲張らない。 画面一覧→項目→条件→ケース、と分けたほうが速くて正確です
  • 「わからない」と言わせる。 P11を必ず回してください。ここを省くと精度が見えなくなります
  • 別セッションで批判させる。 作ったAIに自己採点させても甘くなります（P13）

9. 用語ミニ辞典（AI初心者向け）

プロンプトの中に出てくる言葉です。意味がわかると、出力の良し悪しが判断できるようになります。

  • 同値分割 → 入力を「同じ結果になるはずのグループ」に分け、各グループから1つずつ試す考え方。全部の値を試さずに済ませるための道具
  • 境界値分析（BVA） → 同値分割したグループの境目を狙って試す。バグは境目に集まるため。maxlength=50 なら 49／50／51 の3点
  • デシジョンテーブル → 条件の組み合わせと、そのときの結果を表にしたもの。必須項目が複数あるとき「どれを空にすると何が起きるか」を漏らさない
  • ペアワイズ（2-way） → 全組み合わせを試す代わりに、どの2項目の組み合わせも最低1回は現れるように選ぶ手法。件数が劇的に減る
  • 状態遷移テスト → 画面から画面への移動を、状態と遷移として扱うテスト。1ホップだけ見るのが 0-switch、2ホップ連続を見るのが 1-switch
  • メタモルフィックテスト → 正解が事前にわからないとき、2回実行して結果の関係を確かめる手法。検索・一覧・並び替えで使う
  • ロケータ → 画面上の要素を一意に指す文字列（#email など）。自動化できるかどうかはこれが取れるかで決まる
  • トレーサビリティ → 「この画面のこの項目が、このテストケースにつながっている」という追跡可能性
  • evidence（根拠） → その出力の元になった観測事実。根拠が書けないものは出さない、が元ツールの原則
  • プロンプトインジェクション → 渡したデータの中に紛れた文が、AIへの指示として解釈されてしまう攻撃。P0 の <site_data> で囲むのはこの対策

10. FAQ

Q. HTMLを貼らずに、URLだけ渡してはだめですか。 A. ChatGPT / Claude の環境によってはURLを読みに行けますが、ログイン後・JS描画の画面は取れません。 取れたつもりで出力が返ってくるのが一番危険です。材料は自分で渡してください。

Q. どのAIを使えばいいですか。 A. どちらでも動きます。長いHTMLを扱うので、入力できる文字数が多いモデルを選ぶのが実務上のコツです。 HTMLが長すぎて切れる場合は、方法3（フォーム項目だけのJSON）に切り替えます。

Q. 出力が途中で切れます。 A. 1メッセージに欲張りすぎています。画面を1つに絞り、P2→P4→P9 と段を分けてください。 それでも切れるなら「続き」と送れば続きます。

Q. プロンプトを短くしてもいいですか。 A. 変換ルールの表と、P0 の「守ること」は削らないでください。ここを削ると出力は増えますが、 増えた分は根拠のない推測です。説明文（「なぜこの形か」など）は削って構いません。

Q. 社内システムのHTMLを貼っていいですか。 A. 会社が許可したAI環境（法人契約）を使ってください。個人アカウントの無料プランは避けます。 実在の氏名・メール・IDが含まれるので、貼る前の置換も検討してください。

Q. 生成されたテストケースは、そのまま実行していいですか。 A. だめです。これはテスト設計のインプットであり、レビュー前の下書きです。 特に「期待結果」は、仕様確認を経ていないものが混ざります。

Q. 元ツールと同じ品質が出ますか。 A. 出ません。元ツールは実ブラウザで観測し、スクリーンショットや座標まで根拠に持ちます。 チャット版は「渡した材料の範囲」に限られます。ただし変換ルールは同じなので、 材料さえ揃えば、条件・境界値・ケースの形は同等になります。

Q. AIが毎回違う答えを出します。 A. 「画面IDは登場順にP001から」「乱数を使わない」「項目は入力順を維持」を明示してください。 プロンプトに入っていますが、要約して短く貼ると落ちがちな指示です。

Q. テストケースが多すぎて回せません。 A. P12（テスト計画）でリスクの高い画面から優先順位を付けてください。 決済・個人情報・認証の画面は重要度3倍で計算されます。

Q. 何から始めればいいですか。 A. 「6. 30分ハンズオン」を、いま担当している画面1つでやってみてください。 読むより速く、どこが効くかがわかります。

11. 付録: 元システムの処理順（プロンプトの並びの根拠）

チャットで再現するときも、この順番を崩さないほうが精度が出ます。

設計上の原則（プロンプトに移植した部分）

  1. 根拠のないものは出さない — 実測属性由来だけを確信度1.0とし、一般知識由来は下げる。値が作れなければ空にする
  2. 完全に決定的 — 乱数を使わない。同じ入力なら毎回同じIDと同じ並び。差分比較のため
  3. 主張の境界を明示する — 「打ち切った」「被覆していない」「未確認」を必ず出力に載せ、黙って捨てない
  4. 期待結果は観測可能な事象で書く — エラー文言は実装依存として当てにしない
  5. 副作用は既定でOFF — フォーム送信しない、submitボタンを押さない、破壊的リクエストを遮断する

副作用の原則は、チャットで使うときも同じです。AIが出した手順を本番環境でそのまま流さないでください。
