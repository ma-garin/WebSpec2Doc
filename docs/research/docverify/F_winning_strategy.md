## 結論（5 行以内）
1. 競合は単文の採点か、要件・テストの生成にとどまる。要件定義書と基本設計書の対検査を公式機能として示す例は見つからない。QuintSpect の要件トレーサビリティは「開発予定」（C1・C3・C4・C6）
2. LLM 単独では見逃しも誤検出も多い。さらに LLM 支援で人の検出精度が下がった実験がある。したがって、規則で検出し、LLM は説明を担い、人が先に判断して確定する構成が根拠と合う（P1・P1b・P6・P11）
3. 精度と採用率の公開値は全競合に無く、注釈付きの日本語公開データも無い。日本語の実文書で精度を出して公開することが、取れる空白になる（C1・C2・C5・P7・P10）
4. 勝ち筋の優先順: ①対検査 ②表の突き合わせ ③指摘を根拠に結びつけ誤検知を抑える ④AI の指摘を後から出す ⑤精度の公開 ⑥テスト条件への連結 ⑦導入しやすさ ⑧証跡の一貫性
5. 最大のリスク: 対検査の精度を日本語で示した根拠が 1 件も無い。本文を確認できた国内唯一の定量報告（単一文書・単一観点）では、表と表の不備を検出できなかった。一般化しない（P10）。

## 勝つための要件（優先順）

### 要件 1: 要件定義書⇔基本設計書の対検査を中核にする
- 内容: 2 つの文書を対で取り込み、要件ごとに設計側の対応箇所を候補として出す（検索で絞り、その後に判定する 2 段）。出すのは欠落（対応なし）、矛盾候補（両方の原文を並べる）、追加過多（設計にだけある）の 3 つ。完全率は分母と判定の閾値を明示し、「要確認」の件数を必ず添える
- なぜ勝てるか: QuintSpect は開発予定、QVscribe はロードマップ（C1 発見 3、C2 発見 6）。ALM 系と開発基盤の AI は対検査を示す例が見つからない（C3、C4。未確認を含む）。複数の設計書をまたぐ一貫性の確認に LLM が使えたという報告がある（C5 発見 4、数値なし）。要件の詳細化を難しくする主因は冗長さではなく文脈の欠落だった（P12 Wang 2026・Infineon）。2 つの文章の間では、矛盾を判定するより節を対応づける方が難しい（物語文書での結果。P3 発見 3）。LLM で完全性を判定すると偶然に近い結果になった例がある（医療チャットボット回答での例。領域が異なる。P4 2604.16383）
- 現在の実装との差: R3 の setcheck で複数文書を登録できるが、追跡表（trace.py）は REQ-001 のような ID を正規表現で拾うだけ。ID の無い日本語の設計書では対応づけができない。矛盾は、主語が完全に一致する文の数値の違いと否定の不一致だけを見る。比較は総当たりで、1,500 単位を超えた分は切り捨てる。意味で対応づけて欠落を見つける機能は無い
- 勝ちを示す検証方法: 日本語の要件定義書と基本設計書の対に、設計側の記述削除や数値の書き換えを注入し、欠落と矛盾候補の再現率・適合率を測る（P3b 示唆 2 の注入方式）。ID を振っていない文書での測定を必須にする

### 要件 2: 表を第一級に扱い、表と表を突き合わせる
- 内容: 表のセル・見出し・結合を保ったまま正規化し、要件側の表の行と設計側の表の行を対応づけて比べる。図など読めない要素は件数を出し、「未検証」と明示する
- なぜ勝てるか: 本文を確認できた国内唯一の定量報告（三菱電機、単一文書・単一観点）では、表と表を比べる不備を 1 件も検出できなかった。表の形式をそろえ、渡す記述を絞ると改善した（P10 発見 1）。QuintSpect は docx の記載が無い（C1 発見 5）
- 現在の実装との差: ingest_r3 は xlsx を再構成し、docx の見出し付きの表を行単位に分けて断片にしている。unread は画像・図形・非表示を数える。ただし表どうしを対応づけて比べる処理は無い。docx の脚注とテキストボックスは unread が数えない
- 勝ちを示す検証方法: 表に不備を注入した日本語の設計書の対で、表と表の不備の再現率を測る。表を読めなかった件数を取り込み直後に表示できているかを画面で確かめる

### 要件 3: 指摘を原文に結びつけ、少数・高確度に絞る
- 内容: すべての指摘に原文の引用・位置・規則 ID・確信度を付ける。各規則の既定の ON/OFF は、実測した適合率で決める。指摘には「役に立たない」の操作を付けて誤検知率を集計する。LLM の説明は、原文に裏付けがあるかを判定する 2 段目で落とす。辞書と除外ルールは顧客ごとに画面から調整できるようにする
- なぜ勝てるか: 規則による検出は再現率が高い代わりに適合率が低く、smell によって適合率が大きく違う（P2b 発見 1、P12 Femmer）。定着には会社ごとの調整が要る（P12b 発見 5）。誤検知は利用の障壁になる（Johnson 2013、開発者 20 名の面談。P11b 発見 2）。原文に裏付けがあるかの判定は産業データで実証されている（P11b 発見 7、HalluJudge）。コードと仕様の適合判定では LLM が過剰に不適合と判定した（P9 発見 9。RE 検証の直接例ではない）
- 現在の実装との差: 指摘には quote・location・rule・certainty があり、却下（rejected）と処置（disposition）を持つ。評価セットで適合率が 0.7 未満の規則は自動で無効になる。一方で、実運用の採用率と却下率を規則別に集計する機能は無い。語彙の調整（禁止語・許容語・同義語）は R3 だけにある。LLM の説明が原文に裏付けられているかの検査は無い
- 勝ちを示す検証方法: 実運用で規則別の採用率（採用 ÷ 採否決定済み）を集計して画面に出し、評価セットの適合率と並べる

### 要件 4: 人が先に独立して判断し、AI の指摘は後から出す
- 内容: 個別レビューの段階では AI の候補を隠し、人が指摘を登録した後で照合して見せることを既定にする。AI の指摘が 0 件でも「問題なし」とは表示しない。必要性と正しさは、QA のチェックリスト側で担保する
- なぜ勝てるか: LLM 支援で人の smell 検出精度が下がった（P1 発見 1・P6 発見 1、n=34、効果量は未確認）。理由を説明するより、判断を強いる設計の方が過信を減らした（P11 発見 1）。市販の LLM は必要性・正しさの欠陥をほぼ見逃す（C4 発見 6・P11 発見 6、要旨のみ）
- 現在の実装との差: R4 の triage に「個別レビュー中の非表示注記」がある。ただし自動候補が実際に隠れるかは、地図からは確かめられない（未確認）。人の指摘と AI の指摘の差分を見せる画面は無い
- 勝ちを示す検証方法: 社内で、AI の指摘を先に出す場合と後に出す場合を比べ、人の検出数と誤った採用の数を測る（C4 示唆 4）

### 要件 5: 日本語の実文書で精度と採用率を公開する
- 内容: 精度ページで、規則別と測定方法別（注入・自作・実文書）に再現率と誤検出率を両方出す。注釈は 2 名以上が独立して付け、一致度（κ・α）も公開する。文書間の矛盾と欠落も評価セットに入れる。顧客の実測で採用率を事例にする
- なぜ勝てるか: 競合は公開していない（空白 2）。欠陥注釈付きの英語データは非商用かライセンス不明（P7b 発見 2・3）。商用可（CC BY 4.0）の PURE は注釈なし（P7 発見・示唆 2）。abstract では注釈者数と一致度の記載が多くの研究に無い（Paska は κ=0.89・注釈者 4 人を報告。P2b 発見 2、P7 結論 3）。要件の曖昧さ注釈に特化した κ の典型値は確認できていない（P7b 発見 4）。研究の評価は管理された環境に偏り、産業での採用の証拠が乏しい（P9 発見 1・2）
- 現在の実装との差: R5 の精度ページと評価スクリプトはある。ただし評価セット ja_v1.jsonl は 99 行すべてが自作で、実文書（real）は未作成。SET.DUPLICATE と SET.CONFLICT には評価セットが無い。MULTIPLE_REQUIREMENTS は例文が検出条件と合わず、再現率が 0 になっている。注釈者数と一致度の記録は地図に無い
- 勝ちを示す検証方法: 実文書のセットで result.json を作り、注釈の一致度と一緒に精度ページへ出す。文書間の評価セットで要件 1 の数値を出す

### 要件 6: 指摘から確認質問、解消、テスト条件へとつなぐ
- 内容: 要確認の指摘は質問票へ送る。回答で解消した要件から、テスト条件（同値分割・境界値）を決まった手順で展開する。LLM は値の候補の抽出と説明だけを担う。未解消の要件には「暫定」の印を付ける。要件とテスト条件の対応表を作り、テスト条件の無い要件を出す
- なぜ勝てるか: 指摘とテストケースを双方向にリンクする例は見つからない（C7 示唆 1）。曖昧さへの対処とトレーサビリティを両立した手法は無い（C7 発見 10、P5 発見）。テスト生成の有効性は要件の精密さに左右される（P5 Rodríguez 2025）。確認質問の生成には研究の裏付けがある（P1 示唆 3）
- 現在の実装との差: 質問票（CSV・xlsx の出力と回答の取り込み）と、R2 から質問票へ送る経路はある。テスト条件の生成と、指摘 ID のテスト条件への引き継ぎは無い。追跡表のテスト列は ID で照合するだけ
- 勝ちを示す検証方法: 解消の前後でテスト条件の欠落数を比べる。先行実証が無いため、検証できるまでは主張しない（P5b 示唆 1）

### 要件 7: 導入しやすくする（価格公開・短い契約・送信先の選択・調達書類）
- 内容: 価格表を公開し、即日開始・月単位の解約・頁単位のわかりやすい課金にする。送信先は「外部送信なし（規則のみ）」「ローカル LLM」「外部 LLM」から選べるようにし、送信先と再委託先の一覧を出す。セキュリティチェックシートの回答済み資料、学習・統計作成に使わない既定、AI 事業者ガイドラインへの自己適合表を用意する
- なぜ勝てるか: QuintSpect の契約条件と比べられる（空白 6・7）。国内の競合は価格を公開していない（C5・C6）。セキュリティチェックシートが導入を遅らせる（B1 発見 13）。調達側が要件化を進めている（B2 発見 1〜8）
- 現在の実装との差: R2 に送信先の選択（openai・ollama・none）、送信前の確認（同意トークン）、監査ログがある。ただし同意トークンはプロセス内のメモリにあり、複数ワーカーや再起動で失効する。価格・契約・調達書類は製品の外の話で、地図に記載が無い
- 勝ちを示す検証方法: 申し込みから最初の検査結果が出るまでの時間を実測する。調達書類 1 式がそろっているかを数える

### 要件 8: 権限と証跡を一貫させる
- 内容: すべての更新に、同じ権限判定と楽観ロックをかける。規則・プロンプト・モデルの変更履歴と、精度の再評価の記録を出せるようにする
- なぜ勝てるか: 金融向けでは運用ルールの継続的な見直しが必要とされる（B2 発見 10）。証跡を出せる形にするのは本書の導出（B2 示唆 4）。証跡のずれは調達の段階で突かれる
- 現在の実装との差: R1 の更新系には権限も rev も無く、R4 の権限と楽観ロックを迂回できる。R3 と R5 には認可が無い。R2 は別の系統で権限を判定している。phase=closed への変更で終了条件を検査しない
- 勝ちを示す検証方法: 役割ごとに全 API の更新を試し、拒否されるべきものが 403 や 409 になる割合を数える

## ホーム画面への含意
- 取り込みの入口を、要件定義書と基本設計書の 2 枠（対）にする。根拠: 空白 1（C1 発見 3、C3 示唆 1、C4 示唆 1）。承認済みの home-v1 は 1 文書をドロップする前提
- 統計枠には、対ごとの欠落候補・矛盾候補・要確認の件数を出す。完全率は分母とセットで示し、1 つの数値で断定しない。根拠: P4 示唆 2。自動の網羅指標は人手評価とずれることがある（P4 2607.01980）
- 「網羅性: 未検証」と「AI の指摘 0 件 ≠ 問題なし」を常に表示する。根拠: P11 示唆 2、C4 示唆 3
- 「次にやること」は「自分で読む → AI の候補と照合」の順にする。根拠: P6 示唆 1、P11 発見 1
- 取り込んだ直後に、読めた表の数と読めなかった要素の数を見せる。根拠: P10 示唆 1・5
- 精度ページの実測値へ導線を置き、規則別の採用率を見せる。根拠: 空白 2・9、P11b 示唆 1
- 速さを主な訴求にしない。根拠: コードレビューでは速さは上がったが、品質の向上は示されていない（P6 発見 3・4）
- 送信先（外部送信なし・ローカル・外部）を常に表示する。根拠: C1 発見 7、B2 示唆 5
