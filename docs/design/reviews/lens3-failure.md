# レンズ3: 異常系

## 指摘一覧

### F3-1 [深刻度: 致命] 段階承認は2時間で自動的に「未承認のまま」実行へ進み、その事実がログ1行しか出ない
- 場所: web/routes/auto_run.py:373, 557-565（`STAGE_APPROVAL_TIMEOUT_SEC = 7200` / `job._stages_event.wait(...)`）
- 事実: 承認待ちが7200秒で解除され、`approved` が False でも return せず後続へ進む。ユーザーに出るのは実行ログの「承認待ちがタイムアウトしました。未承認のまま後続へ進みます（この実行の◯◯は人の確認を経ていません）。」1行のみ。主導線バー（static/js/autorun.js:813-866）にもステッパー（同 542-598）にも「未承認で進行中」を示す状態はなく、tone は通常の `busy` に戻る。完了カード（同 658-691）にも未承認の表示はない。
- 原則: User control and freedom（利用者の制御と自由）
- 影響: 席を外している間に、人が一度も承認していないテストが対象サイトへ実操作を行う。しかも完了後の成果物・レポートを見ても「これは未承認で走った」と気づけず、承認ゲート自体が実質無効になる。

### F3-2 [深刻度: 高] ログイン待ちに期限もスキップ結果も示されず、30分後に無言でスキップされる
- 場所: .playwright-mcp/04-running.png（「停止中 — ログインが必要です／あなたの選択を待っています」＋経過 0:11）、templates/partials/modal-autorun-login.html:10,26、web/routes/auto_run.py:574-583
- 事実: モーダル本文は「1件のページにログインが必要です。認証情報を入力するかスキップしてください。」のみ（auto_run.py:686）。待ち時間の上限は `job._input_event.wait(timeout=1800)`（30分）だが、画面にはカウントダウンも期限も出ていない。タイムアウト時の表示は実行ログの「入力タイムアウト。スキップしてクロールを続行します。」だけ。「スキップ」を押した場合に認証後の画面がどう扱われるか（未観測になること）はモーダルにも主導線バーにも書かれていない。
- 原則: Visibility of system status（システム状態の可視性）
- 影響: 「スキップ」と「放置」が同じ結末になることを知らずに待ち続ける。放置して席へ戻ると、ログイン後の画面を一切見ていないテスト結果が「完了」として並んでおり、どこまでが未検証か画面から判別できない。

### F3-3 [深刻度: 高] 失敗・停止からの復旧手段が「最初からやり直す」しかない
- 場所: static/js/autorun.js:951-953, 318-322、templates/partials/view-auto-run.html:258-260
- 事実: `status` が complete/failed/cancelled になると表示されるのは `#autorun-restart-area` の「新しく実行」ボタン1つ。失敗パネルの既定文言も「ログと部分成果を確認してから再実行してください。」（autorun.js:321）で、途中段階からの再開・失敗テストのみの再実行に相当する導線はコード上に存在しない。部分成果（`data.outputs`）は保持され右レールに出るが、それを入力として続きを走らせる操作はない。
- 原則: User control and freedom（利用者の制御と自由）
- 影響: テスト実行フェーズだけが落ちた場合でも、クロールと7段階の承認をすべてやり直すことになる。承認に人手をかけたジョブほど、失敗時の再作業コストが大きい。

### F3-4 [深刻度: 高] クロール0画面でも「失敗」にならず、空のまま後続フェーズへ進む
- 場所: web/routes/auto_run.py:789-808、static/js/autorun.js:665-688
- 事実: クロール後の判定は `report.json` の存在チェックのみ（auto_run.py:790-792）。`screens` が0件でも `job.step_data["crawl"] = {"screens": 0, ...}` を入れて「クロール完了」とログし、QA生成へ進む。UI側で0件を扱うのは完了カードのテスト件数だけで、「実行対象のテストがありませんでした」（autorun.js:682）と出るのみ。それが「1画面も取れなかった」のか「自動化候補が0だった」のかを区別する表示はない（コード上で両者は同じ `noTests` 分岐に落ちる）。
- 原則: Error prevention（エラーの未然防止）
- 影響: URL誤り・アクセス遮断・SPAで何も取れなかった場合に、原因を告げないまま空の成果物一式が「完了」として納品される。ユーザーは対象サイトに問題がないのか、ツールが取れなかったのかを判断できない。

### F3-5 [深刻度: 中] 段階内容の生成失敗が「まだ生成されていません」という未着手の空状態として表示される
- 場所: static/js/autorun-stages.js:386-395、web/routes/auto_run.py:418-421
- 事実: サーバー側は `_ensure_stage_content` の例外を捕捉し「◯◯の内容を用意できませんでした（手動生成は可能）: {exc}」をログへ書くだけで、段階の状態は空のまま。フロントは `stage.items.length` が0なら一律に「まだ生成されていません。「内容を生成」を押してください。」を出す。失敗と未生成を区別する分岐はこの箇所に無い。
- 原則: Help users recognize, diagnose, and recover from errors（エラーの認識・診断・回復の支援）
- 影響: LLM障害・APIキー切れで生成が落ちても「まだ押していないだけ」に見える。ユーザーは同じボタンを繰り返し押し、原因（ログの1行）に辿り着けない。

### F3-6 [深刻度: 中] 「中止する」に確認がなく、押した瞬間にジョブが破棄される
- 場所: static/js/autorun.js:864（主導線バーの `{ label: '中止する', onClick: autorunCancel, kind: 'danger' }`）、同 1008-1035
- 事実: `autorunCancel` は確認ダイアログ無しで `/api/autorun/cancel` を POST する。サーバー側は `job.status = "cancelled"` を設定してログへ「ユーザーによってキャンセルされました。」を追記する（auto_run.py:179-182）。取り消し・再開の操作は無く、F3-3 のとおり残るのは「新しく実行」のみ。
- 原則: Error prevention（エラーの未然防止）
- 影響: 主導線バーは画面最上部に常設され、承認ボタンと同じ帯に並ぶ。長時間の実行を誤クリック1回で失い、やり直すしかなくなる。

### F3-7 [深刻度: 中] robots等でスキップされた範囲が、結果側に「未検証」として集約されない
- 場所: static/js/autorun.js:600-635（ログ表示）、crawler 側の page_skipped/reason=robots（tests/test_crawl_resilience.py:40-46 で確認）、templates/partials/view-auto-run.html:151-153
- 事実: クローラーは robots 由来のスキップを `page_skipped` / `reason: "robots"` として出すが、autorun.js に robots を扱う分岐は存在しない（grep で該当なし）。クロールCLIの出力は `[cli]` 行として既定で非表示（autorun.js:610-619）。「欠陥が無いことの証明はしません／未検証と明記します」という宣言は受付画面の静的な注記（view-auto-run.html:151-153）にあるだけで、完了カード・失敗パネルには未観測範囲の表示がない。推測: 観測範囲のログ（auto_run.py:978-983）は出るが、これはページ数の要約であり robots スキップの内訳とは別。
- 原則: Visibility of system status（システム状態の可視性）
- 影響: アクセスできなかった領域と、検査して問題が無かった領域が結果画面上で同じに見える。「指摘ゼロ＝問題なし」と誤読される。

### F3-8 [深刻度: 中] ジョブのエラー文言が、実行中は非表示になっている要素へ書き込まれる
- 場所: static/js/autorun.js:964-966（`autorunSetStartStatus(data.error, true)`）、同 356（`document.getElementById('autorun-idle-msg').style.display = 'none'`）
- 事実: `data.error` の宛先 `#autorun-start-status` は受付ブロック `#autorun-idle-msg` の内側（view-auto-run.html:104-106）にあり、実行開始時に親ごと `display:none` にされる。したがってこの経路で書かれたエラー文言は画面に現れない。同じ理由は失敗パネル（autorun.js:309, 318-322）にも出るため、片方だけが見える状態になる。
- 原則: Consistency and standards（一貫性と標準）
- 影響: エラー表示の経路が二重化しており、片方は必ず不可視。今後エラー種別を追加したとき、実装者は「出したつもりで出ていない」ことに気づけない。

### F3-9 [深刻度: 低] タイムアウト時のメッセージが原因だけで、次の操作を示さない
- 場所: web/routes/auto_run.py:773-778（`proc.wait(timeout=600)` → `_mark_job_failed(job, "クロールタイムアウト")`）、同 665-666, 728-729
- 事実: クロールは600秒固定で打ち切られ、失敗理由は「クロールタイムアウト」の文字列のみ。UI 側の失敗パネルはこれを `fallbackReason` としてそのまま表示し、推奨アクションは汎用の「ログと部分成果を確認してから再実行してください。」（autorun.js:309, 321）。受付フォームには「深さ」「最大ページ」の詳細オプション（view-auto-run.html:91-103、既定 10 / 500）があるが、タイムアウト時にそれを下げるよう促す文言は無い。
- 原則: Help users recognize, diagnose, and recover from errors（エラーの認識・診断・回復の支援）
- 影響: 大規模サイトで既定値のまま繰り返し10分待って失敗する。設定を絞れば通ることに自力で気づく必要がある。
