## 1. 変更管理の目的と適用範囲

変更管理の目的は、WebSpec2Docに対するあらゆる変更（機能追加・機能改善・不具合修正・リファクタリング・文書更新）を、**起票から検証・クローズまで追跡可能な形で記録し**、実装が要件・設計・テスト・文書のいずれとも矛盾しない状態を維持することです。無秩序な変更の蓄積は、本プロジェクトが重視する「機能整合性ゲート」（`.claude/rules/functional-integrity.md`）を形骸化させるため、変更管理はその前提となる基礎規律と位置づけます。

適用範囲は次のとおりとします。

- ソースコード（`src/`・`web/`・`templates/`・`static/`）に対する変更
- SDLC文書（`docs/sdlc/`）に対する変更
- テストコード（`tests/`）に対する変更
- 設定ファイル・CI定義（`.github/workflows/` 等）に対する変更

軽微な誤字修正やコメントのみの変更など、外部に影響しない変更は本台帳への記載を省略してよいものとします。ただし、その判断自体もレビュー時に確認します。

## 2. 変更要求（CR）のプロセス

本プロジェクトはGitHub上のPull Request（PR）を単位として変更を管理しており、実績（5章）のコミット履歴もこのフローに沿って記録されています。各ステップの入出力と承認者は次のとおりです。

| ステップ | 入力 | 実施内容 | 出力 | 承認者 |
|---|---|---|---|---|
| ① 起票 | 課題・要望・不具合報告 | 変更内容をブランチ名・PR説明として明文化する | 作業ブランチ、PR起票 | 起票者 |
| ② 影響分析 | 起票内容 | 3章の分類判定、4章の観点でのチェック | 影響範囲の明示（PR説明） | 実装担当者 |
| ③ 承認 | 影響分析結果 | コードレビュー、CI結果の確認 | レビュー承認・CI green | レビュー承認者 |
| ④ 実装 | 承認された変更方針 | ブランチ上での実装 | コミット一式 | 実装担当者 |
| ⑤ 検証 | 実装済みコード | `python scripts/quality_harness.py`／`make test`／`make verify-ui` の実行 | 検証結果（pass/fail） | 実装担当者・レビュー承認者 |
| ⑥ クローズ | 検証済みの変更 | PRのマージ（`main`への統合） | マージコミット、実績台帳への記載 | マージ実施者 |

各ステップの検証で使用するコマンドは `docs/sdlc/README.md`「再現方法」に準拠します。

```bash
python scripts/quality_harness.py          # 要件契約の機械検証
make test                                  # 単体・結合テスト
make verify-ui                             # システムテスト（E2E）
```

**未確認**: 本プロジェクトは実績上、単一の開発者（Git設定ユーザー）がPRの起票からマージまでを一貫して行う体制で運用されています。複数人体制へ移行する場合の正式なレビュー承認ルール（レビュアーの指名、必要承認人数等）は、本書時点で未整備です。

## 3. 変更の分類と承認レベル

| 分類 | 定義 | 対応するコミット接頭辞 | 承認レベル |
|---|---|---|---|
| 機能追加 | これまで存在しなかった機能を新たに実装する | `feat:` | PRレビュー必須。`quality_harness.py`での要件契約追加を伴う場合が多い |
| 機能改善 | 既存機能の性能・使い勝手を向上させる | `perf:` | PRレビュー必須。改善前後の指標（実測値）をPR説明に記載する |
| 不具合修正 | 実装が仕様・期待動作と乖離している箇所を正す | `fix:` | PRレビュー必須。再発防止のためのテスト追加を原則伴う |
| リファクタリング | 外部から見た挙動を変えずに内部構造を整理する | `refactor:`、および実装整理を伴う`chore:` | PRレビュー必須。既存テストの全件通過を承認条件とする |
| 文書のみ | コード変更を伴わない文書更新 | `docs:`、および文書のみの`chore:` | 簡易レビュー可（CIのdocsスキップ対象） |

分類に迷う変更（例: 文書整理の過程でコード変更を含む、あるいは`docs:`接頭辞でも実装を伴う）は、**主たる目的**で分類し、副次的な内容はPR説明に明記します（5章 CR-028 参照）。

## 4. 影響分析の観点

変更を実装する前に、次の観点で影響の有無を確認します。該当がない場合も「影響なし」と明示し、確認漏れと区別します。

| 観点 | 確認内容 |
|---|---|
| 要件 | `quality/feature_contracts.yml` の機能契約（51機能）に追加・変更が必要か |
| 設計 | `docs/sdlc/20_design/` の該当設計書（画面設計書・API設計書・データ設計書等）との整合性 |
| 実装 | 影響を受ける `src/`・`web/` のモジュール・関数の特定（`docs/sdlc/_asbuilt/modules.json` の突合） |
| テスト | 既存テスト（`tests/`）への影響、新規テスト（単体/結合/E2E）の要否 |
| 文書 | ユーザー向け文書（`docs/userguide.md`・`WS2D-UM-001`等）・運用手順書への反映要否 |
| 運用 | スケジュール・通知・監査ログ・バックアップ運用（`WS2D-OP-001`）への影響有無 |
| セキュリティ | 認証・認可・入力検証・SSRF対策等のチェック要否 |
| 権限・テナント分離 | テナント間のデータ分離（`web/tenancy.py`）を横断する変更でないか |
