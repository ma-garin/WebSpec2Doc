# 軽量 QMS 運用（R-13・2026-08-23 決定）

`docs/quality/iso9000-qms-assessment.md` の不適合 NC-02（内部監査の不在）・NC-03（マネジメントレビューの不在）・
NC-04（利害関係者と顧客満足の監視の不在）に対する是正。

**方針**: 1 人開発 + AI エージェント運用という実態に合わせ、ISO 9001 の組織的要求を**最小の記録で満たす**。
形式を整えることが目的ではなく、**次の判断を変える情報を残す**ことが目的である。

## 実施タイミング

R-12 で決めた「マイルストーン毎の手動フルゲート」に**相乗りさせる**。
独立した月次サイクルを作ると、それ自体が実行されずに腐る（NC-02 が発生したのと同じ機序）。

| タイミング | やること | 記録先 |
|---|---|---|
| マイルストーン（フルゲート実行時） | 下記 3 点を確認し 1 ファイルに追記 | `docs/quality/reviews/YYYY-MM-DD.md` |

## 確認する 3 点

### 1. 内部監査の代替（NC-02 / 箇条 9.2）

フルゲートの結果そのものを監査証拠として扱う。加えて次を 1 行ずつ記録する。

- ゲートの結果（PASS / FAIL の件数）と、前回からの差分
- **前回のマイルストーンから今回までに、ゲートが検出できなかった不具合があったか**
  （あれば、それを検出できるテストが無いこと自体が発見事項）
- 文書と実装の乖離を 1 件でも見つけたか（例: 4 システム化にテストが追随していなかった件）

### 2. マネジメントレビューの代替（NC-03 / 箇条 9.3）

次の 3 問に 1 行ずつ答える。答えが「変化なし」ならそう書く。

- 品質目標（カバレッジ 80% 以上・ゲート全緑）は達成されているか
- 前回決めた是正処置は完了したか。未完了なら理由は何か
- **次のマイルストーンまでに優先して閉じる課題は何か**（`docs/quality/remediation-roadmap.md` の更新で代替可）

### 3. 顧客満足の監視（NC-04 / 箇条 4.2 / 9.1.2）

収集機構は実装済み（`web/routes/feedback.py:32` → `feedback.jsonl`）だが、**見る運用が無かった**のが不適合の実体。

- `feedback.jsonl` の新規件数と内容を確認する
- **0 件なら「0 件」と記録する**（見ていないことと、見て 0 件だったことは別）
- 内容があれば、ロードマップへ課題として起票したかを記録する

## テンプレート

```markdown
# 品質レビュー YYYY-MM-DD（マイルストーン: <名称>）

## 1. 監査（ゲート結果）
- L1/L2: N passed / M failed（前回比 ±）
- L3 E2E: N passed / M failed（前回比 ±）
- 静的解析・脆弱性:
- ゲートが検出できなかった不具合:
- 文書と実装の乖離:

## 2. レビュー（判断）
- 品質目標の達成:
- 前回の是正処置:
- 次に優先して閉じる課題:

## 3. 利用者の声
- feedback.jsonl 新規: N 件
- 内容と対応:
```

## この運用の限界（明示）

- **実行はマイルストーンの判断に依存する。**判断を怠れば記録も残らない。自動化（週次実行・CI 必須化）は
  2026-08-23 の決定で採用しなかった
- 1 人開発のため、監査の**独立性（箇条 9.2.1 の「客観性及び公平性」）は満たさない**。
  作成者と監査者が同一である点は ISO 9001 の要求を厳密には満たしていない
- 顧客満足の測定は `feedback.jsonl` への自発的投稿のみで、能動的な調査は行わない
