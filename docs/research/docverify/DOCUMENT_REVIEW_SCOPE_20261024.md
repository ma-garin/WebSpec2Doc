# 文書レビューの対象と比較単位の一次資料確認

確認日: 2026-10-24（Asia/Tokyo）
目的: 「2文書対比」を「要件定義書と基本設計書」に固定する業務上の根拠を点検する。
終了条件: 一次資料の記述と製品設計上の判断を分け、対象・関係・目的を整理する。
範囲: 指定節とレビュー目的の確認。ローカル実装の対応能力は本書では未検証。

## 一次資料が述べること

ISTQBシラバスは知識体系の資料であり、本製品の要件を直接定める規格ではない。
以下は日本語要約。英語本文の逐語引用は行わない。

- CTFL 1.4.3（冊子p.20）: テストウェアはテスト活動の成果物。名称・構成・管理方法は組織で異なり、例示は網羅的ではない。計画、条件、ケース、手順、データ、ログ、欠陥報告、完了報告等を含む。[CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=20)
- CTFL 1.4.4（pp.20–21）: テストベースの要素、関連テストウェア、結果、欠陥の追跡関係を維持する。網羅性・変更影響・残存リスク等の評価に用いる。文書二冊の照合だけを述べたものではない。[同資料](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=20)
- CTFL 3.1.1（p.33）: 読んで理解できる成果物をレビュー対象とし、要件、コード、テスト計画・ケース、バックログ、チャーター、契約、モデル等を例示する。機械的な静的解析には検査可能な構造が必要になる。[同資料](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=33)
- CTFL 3.2.2・3.2.4（pp.35–37）: 目的、対象、品質特性、重点、終了基準、補助情報を計画時に定める。レビュー目的には異常検出、品質評価、合意形成等があり、発見した異常を直ちに欠陥と確定しない。[同資料](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf#page=35)
- 補助資料 CTAL-TA v3.1.2 1.3・5.2.1（pp.13–14・48）: テストベースは要件・ユーザーストーリー等の知識で、文書不足時には関係者との議論も条件抽出源となる。レビュー例には要素の識別子、版、業務要求からの追跡を含む。これは指定した旧版の確認であり最新版の主張ではない。[CTAL-TA v3.1.2](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TA_Syllabus_v3.1.2.pdf#page=13)

## 資料から判断できる範囲

確認した節に、対象を「要件定義書＋基本設計書」に限定する根拠も、比較を必ず2件またはN件にする規定もない。
単体レビューも、関連する複数成果物を参照するレビューも、目的から定める設計が整合的である。
ただし、この資料から「任意の文書を自動で正確に検査できる」とは導けない。
追跡は要素間の関係であり、冊数・画面枠数・ファイル数と同義ではない。

## 製品設計としての推奨（一次資料の要求とは別）

汎用入口は、利用者の検査目的と成果物の関係を先に選び、必要な入力を案内する。
最初に固定二種を要求すると、同種文書の版比較、契約との整合、テスト網羅性等を入口で排除してしまう。
一方、「要件から基本設計への反映検査」という専用検査器なら、固定種別と固有ルールは妥当である。
専用検査器は汎用入口から選べる検査の一つとし、名称・受理条件・検出範囲を明示する。

| 分離する属性 | 記録例 | 判断理由 |
|---|---|---|
| 文書種別 | 要件、契約、テスト | 内容の分類 |
| 検査での役割 | 対象、基準、参照 | 実行ごとに変わる |
| 版 | 改訂番号、取得時点 | 比較時点を固定 |
| 関係 | 改訂、実現、検証 | 要素と向きを特定 |
| 目的 | 差分、整合、網羅 | 判定基準を選ぶ |

ここでの役割は文書の検査上の用途であり、利用者の職務・権限・承認権限ではない。
同一文書も、ある検査では基準、別の検査では対象になり得る。

- 1成果物: 明確さ、矛盾、規約適合等。参照資料の有無も記録する。
- 2成果物: 同種の新旧版、上位要求と設計、契約と要件等。関係と判定方向を指定する。
- 複数成果物: 要求→設計→ケース→結果→欠陥等。全組合せ照合ではなく、指定した関係の要素単位で追跡する。

2件の検査から始める判断は、操作・計算・実装コストを抑える段階導入として可能である。
その場合も、2件は現時点の対応上限として説明し、業務全体やISTQBの制約と取り違えない。
内部では文書集合と関係を表せる形にしておくと、後から多成果物へ拡張する作り直しを減らせる。
未対応の種別・関係・目的は実行前に示す。入力受付と検査能力は別々に検証する。

## 現行実装との照合・実行結果

`web/services/docverify/pair/engine.py` のinspectは、基準側をsegment.requirement_unitsで抽出する。
`pair/segment.py`の抽出条件は「機能要件／非機能要件」の見出し、またはREQ形式のIDである。
ファイルを2つ受理することと、任意の2文書を検査できることは一致していない。

同じ応答時間の30秒／60秒の食い違いを3つの書式で実行した。埋め込みはoffで、外部送信は行っていない。

| 入力 | 抽出した基準要素 | 矛盾検出 | エラー |
|---|---:|---:|---:|
| 要件形式→設計 | 1 | 1 | 0 |
| API仕様→API仕様 | 0 | 0 | 0 |
| テスト仕様→実行結果 | 0 | 0 | 0 |

実測値は `/tmp/ws2d-document-capability-probe.json`。
さらにpair_review._judgeへ指摘0・対応抜け0を渡すとpass=Trueになった。
この判定関数には、検査対象を抽出できたか・検査器が目的に適合するかの材料が渡らない。
ISTQB severity High相当: 対象外の文書を無検出のまま合格扱いにできる構造がある。実案件での発生頻度は未確認。

## 設計判断

- 現行検査器は「要件を設計へ反映したか」の専用検査として扱う。汎用の「2文書の対比」と表示しない。
- 汎用レビューは成果物集合を入力とし、種別、検査上の役割、版、対象間の関係、検査目的を個別に保持する。
- 同じAPI仕様同士、新旧の同種文書、ケースと結果などを、要件→設計へ読み替えない。
- 検査器は対応する目的・入力構造・前提を宣言し、実行前の適合確認を行う。非対応・抽出0・実行失敗は判定不能とし、無検出や合格に変換しない。
- 確認は入力受理に留めず、対象を抽出し、検査し、根拠付きの結果が最終画面・報告書へ出るまで同じ反例で行う。
