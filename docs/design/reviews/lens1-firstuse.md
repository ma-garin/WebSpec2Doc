# レンズ1: 初回利用者

## 指摘一覧

### F1-1 [深刻度: 高] 「URLか仕様書を渡すだけ」と書いてあるが、文書駆動でもURLは必須
- 場所: AutoRun受付画面のリード文（view-auto-run.html:22）と生成モードのラジオ（同33-39行）
- 事実: リード見出しは「URLか仕様書を渡すだけ」。しかし `autorunStart()`（static/js/autorun-document.js:124-125）は最初に `if (!url) { 'URLを入力してください。' ; return; }` を実行し、モード判定より前にURLを必須にしている。文書駆動を選んでも `対象URL` 欄は隠れず、文書だけでは開始できない。
- 原則: 一貫性と標準（画面の宣言と実際の入力要件が一致していない）
- 影響: 「仕様書だけ持っている」初回利用者が文書駆動を選び、文書をアップロードしてから開始で弾かれる。URLが要る理由（実測画面と結合するため）は文書駆動の説明文（39行「要件文書と実測画面を結合」）にしか書かれておらず、見出しと矛盾したまま試行錯誤する。

### F1-2 [深刻度: 高] 「全自動」と書かれているが、開始後に人間の承認が必要なことが受付画面に一切書かれていない
- 場所: 見出し（03-autorun.png のH1「AutoRun — 全自動テスト実行」）、受付リード文、11ステップの流れリスト（view-auto-run.html:108-135）
- 事実: 受付に並ぶ流れは「見立て1-4／設計5-7／実行・納品8-11」の11項目で、承認・確認という語は1つもない。一方 dom-stage1.json の実画面には「承認して次へ」「確定する」「未確認が 4 件あります」「STEP 1 / 8」が存在し、コックピット（view-auto-run.html:188-192）にも「承認」ステップがある。
- 原則: システム状態の可視性（これから起きることの予告が実際の進行と一致しない）
- 影響: 初回利用者は「押したら放置でレポートが出る」と理解して開始する。実際は途中で停止して人の確認を待つため、席を外して待ち時間を無駄にするか、止まっている理由を障害と誤認する。開始前に「所要時間」と「自分の関与が要るか」を判断できない。

### F1-3 [深刻度: 高] 既定が全ページ対象（深さ10・最大500ページ）だが、その数値も所要時間の目安も閉じた中にしかない
- 場所: 「詳細オプション（既定は全ページ対象）」の折りたたみ（view-auto-run.html:91-103、03-autorun.png で閉じた状態）
- 事実: `autorun-depth` の value は 10（max=10）、`autorun-max-pages` の value は 500（max=500）で、いずれも上限が既定値。閉じている間は具体的な数値が画面に出ない。ホーム画面（02-home.png）には「目安: 10画面で約2〜3分」という所要時間表記があるが、AutoRun受付には所要時間表記が一切ない。
- 原則: 認識と再生（recognition rather than recall：判断に要る値を思い出させず画面に出す）
- 影響: 初回利用者は「開始」が数分で終わるのか数時間かかるのか見積もれないまま押す。対象が他社サイト・本番環境の場合、最大500ページのクロールを無自覚に走らせる。

### F1-4 [深刻度: 中] URL未入力でも「開始」が押せ、押して初めてエラーが出る
- 場所: 「開始」ボタン（view-auto-run.html:104）と `autorun-start-status`（105行）
- 事実: `autorun-start-btn` に初期 disabled 属性はなく、入力欄の変更で活性/非活性を切り替える処理もない（活性制御は観点セット取得の成否のみ／static/js/autorun.js:239,243）。未入力時は押下後に `autorunSetStartStatus('URLを入力してください。', true)` でボタン下に赤字が出る。同じく文書駆動の文書未添付、`reached_target` 選択時の画面ID未入力も、すべて押下後に初めて判明する。
- 原則: エラー防止
- 影響: 必須項目が事前に分からないため、初回利用者は「押す→怒られる→直す」を必須項目の数だけ繰り返す。エラーはボタン下に出るため、フォーム上部にある不足項目（文書アップロード欄など）との距離が離れ、どこを直せばよいか探すことになる。

### F1-5 [深刻度: 中] 「事前確認」を押すべきかどうか判断できず、押すと本実行と同じ時間を2回払う
- 場所: 対象URL欄右の「事前確認」ボタンとその下のヒント文（view-auto-run.html:50-52）
- 事実: ヒント文は「範囲は**本実行と同じ**（既定は全ページ対象）なので、規模によっては時間がかかります」と明記している。一方で、事前確認が任意なのか、開始の前提なのか、押さずに開始できるのかは書かれていない。`autorunStart()` は事前確認の実行状態を参照しておらず、押さなくても開始できる。
- 原則: 柔軟性と効率（初回利用者が近道か必須手順かを判断できない）
- 影響: 慎重な初回利用者は「まず確認すべき」と考えて事前確認を実行し、全ページのクロールを待ってから、同じ規模のクロールをもう一度開始で走らせる。逆に読み飛ばした利用者は到達不可のURLでいきなり本実行を始める。

### F1-6 [深刻度: 中] AutoRunにいるのに、左サイドバーに現在地がない
- 場所: 03-autorun.png の左サイドバー全体とパンくず
- 事実: AutoRun表示中でも、サイドバーの項目は「ホーム／新規解析／テストケース／品質観点／観点管理／ユーザーガイド／参考／設定」で、AutoRunという項目自体が存在せず、どの項目もハイライトされていない（02-home.png ではホームがハイライトされている）。サイドバー上部のシステム表示も「ドキュメント作成」のまま。パンくずは「ダッシュボード › AutoRun」で、サイドバーに「ダッシュボード」という名前の項目はない（該当するのは「ホーム」）。
- 原則: システム状態の可視性
- 影響: 初回利用者は自分が今どのシステムのどこにいるのか、AutoRunに戻る導線がどれなのかを画面から読み取れない。一度ホームへ戻ると、AutoRunへの再入口はホーム中央のカード（02-home.png）だけになる。

### F1-7 [深刻度: 中] 開始後に中止できることが、受付画面のどこにも書かれていない
- 場所: 受付画面全体（view-auto-run.html:19-153）と、非表示化された停止ボタン（同14-16行）
- 事実: 停止操作は `#autorun-cancel-area` が `hidden style="display:none"` で画面から外され、コメントに「主導線バーの『中止する』に一本化した」とある。主導線バー `#autorun-leadbar` も受付時は `style="display:none"`。したがって開始前の画面には「停止」「中止」という語が1つも表示されない。
- 原則: ユーザーの制御と自由度
- 影響: 所要時間の目安（F1-3）がなく、かつ後戻りできるかも分からないため、初回利用者は「一度押したら最後まで走り切るのでは」と警戒し、開始を保留するか、影響の小さいダミーURLで試すことになる。

### F1-8 [深刻度: 中] 対象サイトにログインが必要な場合、途中で認証情報を求められることが事前に告知されない
- 場所: 受付画面の説明文・詳細オプション（view-auto-run.html:19-153）
- 事実: dom-stage1.json の実行ログに「画面分析完了: 7件 (要ログイン: 1件)」「ログインが必要なページが検出されました。認証情報の入力を待っています。」があり、`_autorunShowLoginModal()`（static/js/autorun.js）が実行中にID/パスワード入力を求める。受付画面にはログイン、認証、ID、パスワードという語が一切ない。
- 原則: エラー防止
- 影響: 会員制サイトを対象にした初回利用者は、認証情報を手元に用意しないまま開始し、途中で処理が待ち状態になる。「全自動」の説明（F1-2）とも重なり、放置している間ずっと止まったままになる。

### F1-9 [深刻度: 中] 観点セットの読み込みに失敗すると「開始」が押せなくなるが、理由はボタンの近くに出ない
- 場所: 観点セット欄（view-auto-run.html:82-90）と「開始」ボタン（104行）
- 事実: 観点セット取得に失敗した場合、`static/js/autorun.js:242-243` が `note.textContent = '観点セットを固定できません: … 観点管理で既定公開版を確認してください。'` を出したうえで `autorun-start-btn` を disabled にする。メッセージは観点セット欄の下（`#autorun-viewpoint-recommendation`）に出るのみで、ボタン側には理由が表示されない。初期表示は「公開済み観点セットを確認しています…」（88行）。
- 原則: システム状態の可視性
- 影響: 初回利用者にとって観点セットは意味の分からない専門用語であり、そこに出た文言と、押せない「開始」ボタンを結び付けられない。「壊れている」と判断して離脱する。

### F1-10 [深刻度: 低] 選択中モードの説明が同じ画面に二重に出ている
- 場所: モード表示バッジ `#autorun-mode-current`（view-auto-run.html:30）とラジオ内の説明（34行）
- 事実: 03-autorun.png では、ラジオの上に「URL駆動を選択中 — 実測した画面からテストを生成します。」というバッジが出ており、直下の選択済みラジオにも「URL駆動／実測した画面からテストを生成」が同じ内容で並んでいる。
- 原則: 最小限の設計
- 影響: ラジオ自体が選択状態を示しているのに同じ文が繰り返されるため、初回利用者は「バッジ側が別の何かを表しているのでは」と読み直す。フォーム最上部の一等地を新情報のない要素が占めている。

### F1-11 [深刻度: 低] 受付で予告される工程数（11）が、実行後に見える工程数（8／6）と一致しない
- 場所: 受付の流れリスト（view-auto-run.html:108-135）、コックピットのステッパー（同172-203）、段階承認レール（dom-stage1.json）
- 事実: 受付は「1 受領 …… 11 レポート納品」の11ステップ。コックピットは「仕様書生成／QA成果物／スクリプト生成／承認／テスト実行／完了」の6項目。dom-stage1.json のサイドバーは「1 テスト目的 …… 8 Playwright 自動化」の8項目で、本文は「STEP 1 / 8」と表示する。3つの番号体系に対応関係の説明はない。
- 原則: 一貫性と標準
- 影響: 開始前に「11工程」と記憶した初回利用者が、開始後に「1 / 8」を見て、別の処理が始まったのか、工程が減ったのかを判断できない。受付の説明を進捗の予測に使えなくなる。

## 見落としの自己申告

- ブラウザ操作が禁止のため、実挙動は未確認。以下はコードとスクリーンショットからの推定を含む: 未入力時のエラー表示の実際の見え方、事前確認押下後の表示、観点セット読み込み失敗時の実画面。
- 文書駆動を選択した状態の画面を見ていない（`#autorun-document-options` が開いたときのレイアウト、ファイル選択UIの実物、フォームの縦の伸び方）。
- 「詳細オプション」を展開した状態の実画面を見ていない。ⓘツールチップが実際にホバー/フォーカスで読めるかも未確認。
- キーボード操作のみでの到達順序、フォーカスリング、スクリーンリーダーでの読み上げは未確認。
- 初回ツアー（01-entry.png）はホーム画面のもので、AutoRun受付でツアーが出るかどうかは未確認。全4ステップの2枚目以降の内容も未確認。
- 「開始」押下から最初の承認要求までの実所要時間、およびダークモード時の表示は未計測・未確認。
- 対象読者を「初めて使う人」に限定しているため、2回目以降の利用者にとっての効率（URL候補 datalist など）は評価していない。
